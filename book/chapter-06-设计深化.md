# 第6章：第4步——设计深化

> **本章在全书中的位置：** 第3步的原型验证回答了一个问题——"核心循环好玩吗？" 如果答案是"好玩"，你就进入了第4步。第4步回答另一个问题："做完这个游戏到底需要多少工作量？" 这是从"探索者"到"规划者"的切换点，也是独立游戏最常见的死亡线——不是设计错了，是算错了。

---

## 本章解决什么问题

Core Loop 验证通过后，你会获得一股巨大的动力——"我要把它做成完整的游戏！" 这股动力极其珍贵，但也极其危险。它会让你跳过估算直接开干，而三个月后你会发现自己完成了 40% 的内容却用光了 100% 的时间。当这本该在研发前发现的问题直到研发中才暴露，沉没成本已经让你无法回头。

第4步的任务是：**在开写正式代码之前，用十页纸把模糊的"想法"翻译为可计算的"工作量"，建立起整本书中最核心的一道防火墙。**

> **编程类比：** 如果 Step 3（原型验证）= 验证一个算法是否可行（写 MVP 代码跑通核心逻辑），那么 Step 4（十页纸）= 写技术设计文档（TDD）+ 项目排期表——把你已验证的核心算法，扩展到全系统的架构设计和工作量估算。Scope Budget 就是你用"内容类型 × 数量 × 单位成本"算出来的总人天。

---

## 6.1 从验证到执行的心态转变

> **这一节解决什么问题：** 为什么 Step 3 到 Step 4 的切换是最容易翻车的心理关口？

### 两种角色的切换

Step 3 的设计师角色是**探索者**。你的工作是不停地问"如果……呢？"——加一个新机制、拆掉一个旧想法、换一种操作方式。你的产出是"可玩的原型"和"验证过的假设"，你的失败成本很低——一个做了两天被砍掉的机制，只浪费了两天。

Step 4 的设计师角色是**规划者**。你的工作是停止问"如果……呢？"，开始问"做完它需要什么？" 你的产出是"十页纸设计文档"和"Scope Budget 总表"，你的失败模式变了——一个估算错了的工作量模块，会导致整个项目延期数周或永久搁浅。

| 维度 | Step 3（探索者） | Step 4（规划者） |
|------|----------------|----------------|
| 核心问题 | "这个核心循环好玩吗？" | "做完这个游戏需要多少工作量？" |
| 思维方式 | 发散：试一切可能 | 收敛：锁定可执行范围 |
| 允许的错误 | 机制失败（砍掉重来） | 估算错误（调整预算，不是调整梦想） |
| 产出形式 | 可玩原型（灰盒） | 十页纸文档 + 预算表 |
| 时间检查 | 由项目检查点和风险决定 | 由项目检查点和产出决定 |
| 最大风险 | 方向错误 | 范围失控 |

### 为什么这个切换如此困难

**第一个原因：动力陷阱。** Core Loop 验证通过带来的喜悦会让你产生"这个游戏太棒了，我要把一切好点子都放进去"的冲动。这正是 Scope Creep（范围蔓延）的心理根源——你每一次"再加一个系统"，都以为自己在让游戏更好，实际上是在往项目里埋炸弹。

**第二个原因：估算恐惧。** 很多设计师潜意识里害怕做 Scope Budget，因为他们知道——一旦算出来，就会发现自己想要的东西远超自己的时间预算。于是他们选择"不算"，用"I'll figure it out as I go"来逃避。这不是敏捷开发，这是不做开发规划。

**第三个原因：角色惯性。** 在 Step 3 里你已经习惯了"边做边改""灵感驱动"的工作方式。突然让你坐下来写十页文档、画表格、算人天——这感觉像是在给激情泼冷水。但请记住：**这盆冷水是在保护你的项目，不是杀死它。** 在 Step 4 暴露“做不完”并及时调整，通常比在生产中途才发现范围问题更容易处理。

> **Pillar 在这一步的新角色：** 在 Step 2 中，Design Pillars 是你的“方向指南”。在 Step 4 中，Pillars 可以作为**取舍判断器**——每当你纠结“要不要加这个新系统”，问自己：“它支持哪条 Pillar？代价、依赖和替代方案是什么？”如果支持关系说不清，先暂停或做低成本验证，而不是自动加入或自动砍掉。

## 6.2 十页纸结构详解

> **这一节解决什么问题：** 十页纸到底怎么写？每一页写什么内容？格式上有什么坑要避开？

### 十页纸的来源与定位

"Ten-Pager"（十页纸）的概念来自 Scott Rogers 的经典教材《通关！游戏设计之道》。它不是 10 页 Word 文档，而是**10 个必须回答的设计要点**——有些半页就能写完，有些需要 2 页+ 的图表。核心原则是：**可读性 > 完整性。** 用概念图、流程图和箭头代替大段文字。

十页纸的定位介于 Step 2 的"一页纸概要"和正式的 GDD（游戏设计文档）之间：
- **一页纸** = 说服投资人/自己"为什么该做"（为了销售）
- **十页纸** = 告诉实现者"怎么做完"（为了构建）
- **GDD** = 记录所有细节供协作参考（为了记录）

### 十页纸总览

| 页码 | 标题 | 核心问题 | 输出形式 | 常见错误 |
|------|------|---------|---------|---------|
| **P1** | 标题页 | "这是什么游戏？" | Logo草图、平台、受众、评级、目标发布日期 | 只写游戏名，缺失平台和受众 |
| **P2** | 故事与玩法 | "玩家在做什么？为什么？" | 故事梗概（3-5句）+ 玩法流程箭头图 | 故事和玩法各说各的，不关联 |
| **P3** | 游戏流程 | "玩家如何成长？" | 成长系统图 + 挑战递增曲线 | 只列功能，不画"从弱到强"的弧线 |
| **P4** | 角色与控制 | "玩家控制什么？怎么控制？" | 主角能力列表 + 控制映射图（手柄/键盘） | 控制说明用文字而非图示 |
| **P5** | 核心玩法概念 | "最独特的玩法是什么？" | 玩法模式列表 + USP 展开（每一条 USP 配一例子） | USP 写成"好玩的战斗"这种废话 |
| **P6** | 游戏世界 | "玩家在什么世界里行动？" | 环境/关卡列表 + 连接方式图（线性/枢纽/分支） | 只列关卡名，不画空间关系 |
| **P7** | 界面 | "玩家看到什么？怎么导航？" | Shell 导航图 + HUD 布局草图 | 直接画完整 UI 而不先画导航结构 |
| **P8** | 机制与道具 | "玩家能用什么？" | 核心机制规则（精确到数值范围）+ 道具效果表 | 规则写得太模糊（"伤害很高" vs "伤害 = 50"） |
| **P9** | 敌人与 Boss | "玩家打什么？" | AI 行为类型 + Boss 机制 + 奖励 | 所有敌人用同一套 AI，没有差异化 |
| **P10** | 过场/奖励/竞品 | "玩家为什么持续玩？" | 过场形式、二周目内容/解锁、竞品对比表 | 竞品对比只写"我们更好"而无证据 |

### 各页详细说明

#### P1：标题页

这是十页纸的封面。但它不是装饰——它是**强制你回答基本商业问题**的工具。

**必填内容：**
- 游戏名称（暂定名也可以）
- Logo 草图（手绘即可，这一步不需要高品质美术）
- 目标平台（PC / 主机 / 移动 / 多平台）
- 目标受众（年龄、游戏习惯、一句话描述"谁会玩这个游戏"）
- ESRB/IARC 预期评级
- 目标发布日期（年份+季度即可，不确定就写"TBD"但要标注原因）
- 联系信息（如果是团队项目）

**常见错误：** 跳过受众和评级，觉得"这不关设计师的事"。但受众决定了你的复杂度设计（儿童游戏的操作不能复杂），评级决定了你的内容边界——这些都直接影响 Scope。一个"全年龄"游戏和一个"成人向"游戏，在内容量相同的情况下，工作量和测试成本完全不同。

#### P2：故事与玩法

这一页有两个任务：让读者在适合本项目的阅读时间内理解“这个世界发生了什么”，以及“玩家在里面干什么”。30 秒可以作为短 Pitch 的参考，不是所有项目的硬门槛。

**故事梗概格式（3-5 句）：**
```
[背景]：在 [世界/时代] 中，[发生了什么导致现状]。
[主角]：你扮演 [谁]，ta 的 [动机/目标]。
[冲突]：但 [障碍/敌人] 挡在中间。
[赌注]：如果失败，[后果]。
```

**玩法流程格式：**
用箭头图画出一个典型关卡/一次典型对局的流程结构。例如一个平台动作游戏：
```
进入关卡 → 探索 → 遭遇敌人 → 击败敌人 → 获得能力/道具 → 抵达出口 → 评分/结算
         ↑                                    ↓
         └──────── 回头探索（如果有新能力）←───┘
```

**常见错误：** 故事是"在一个魔法世界里拯救公主"，玩法是"收集 500 种鱼"——故事和玩法完全脱节。玩家会产生认知撕裂：我在干什么？为什么？

#### P3：游戏流程

这一页回答"玩家从开始到通关，能力、挑战和内容如何递进"。

**必画内容：**
- **成长曲线草图：** X 轴 = 游戏进度（关卡/时间），Y 轴 = 玩家能力/挑战难度。画出两条大致曲线
- **解锁节点：** 在曲线上标注关键解锁点——新能力、新区域、新敌人类型分别在什么时机出现
- **节奏变化：** 标出"喘息点"（低难度关卡/Boss 战后的宁静区）和"高峰点"（Boss 战 / 剧情高潮）

**常见错误：** 把所有成长系统（技能树、装备、等级）全部画在同一页，但忘了标注"这些东西在哪个关卡/时间点解锁"——时序信息是这一页的核心，比系统名称更重要。

#### P4：角色与控制

这一页必须包含一张**控制映射图**——不是文字描述，是视觉化的手柄/键盘图。

**必画内容：**
- 手柄或键盘的按键布局图，在每一个按键旁边标注功能
- 主角的核心能力列表（跳跃高度、移动速度、HP 等关键数值——如果你已经验证过，用真实值；如果还没，用设计值加 `[待验证]` 标记）

> 来自《通关！》的 3C 原则：**角色（Character）、镜头（Camera）、操控（Control）应在前期形成稳定基线，但不应被写成绝对不可修改。** 它们确实会影响关卡距离、视觉引导和敌人检测范围；如果测试发现根本问题，应记录受影响范围、评估返工，再做受控变更并重新验证。十页纸的 P4 是当前版本的基线，而不是永久锁定。

**常见错误：** 控制映射只写了键盘，忘了检查目标平台的手柄、触屏或其他输入方式；实际优先级应由目标玩家和平台数据决定。

#### P5：核心玩法概念

这一页展开你在 Step 2 中定义的 Unique Selling Points（USP）。

**格式要求：**
- 列出 3-5 条 USP
- 每一条 USP 下面用 1-2 句话说明"玩家具体感受到什么"
- 每一条 USP 旁边配一个游戏内场景的微型例子

```
USP 1：时间倒流战斗
→ 玩家感受：每次失误不是"死亡"而是"回到 3 秒前再试一次"
→ 例子：玩家被 Boss 击中 → 按住 L2 倒流 → 看到自己在 3 秒前的虚影位置 → 松开后重置到那个位置，Boss 的 HP 也回退

USP 2：所有墙壁可攀爬
→ 玩家感受：关卡没有边界，天花板也是路
→ 例子：地下洞穴中，玩家不走正路而选择爬上天花板的钟乳石绕过敌人
```

**常见错误：** 把 USP 写成"爽快的战斗""精美的像素画面""动人的故事"——这些不是卖点，是每个游戏都应该有的。真正的 USP 是你的游戏能做到但别人做不到或没做过的东西。

#### P6：游戏世界

这一页的核心输出是一张**世界连接图**——不是美术概念图，而是结构图。

**三种连接方式：**
| 类型 | 图示 | 代表游戏 | 适合场景 |
|------|------|---------|---------|
| 线性 | A→B→C→D | Celeste | 叙事驱动的关卡制游戏 |
| 枢纽 | 中心连接多个分支 | Super Mario 64 | 玩家有选择权但不过度开放 |
| 分支/网状 | 多路径交叉连接 | Hollow Knight | 类银河城，需要探索和回溯 |

**必画内容：**
- 每个区域/关卡的名字和主题（一句描述）
- 区域之间的连接线（什么样的门/传送点/机制连接两个区域）
- 标注哪些连接需要特定能力/道具解锁（P3 中的解锁节点在这里得到空间化）

**常见错误：** 列出 20 个关卡名但没有任何空间关系图。没有连接图的关卡列表只是一堆名字，不是游戏世界。

#### P7：界面

这一页的核心输出是**Shell 导航图** + **HUD 布局草图**。

**Shell 导航图示例：**
```
[游戏 Logo / 主菜单]
    ├── 新游戏 → [难度选择] → [开场动画/加载] → [游戏中 HUD]
    ├── 继续 → [存档列表] → [加载] → [游戏中 HUD]
    ├── 设置 → [音频 / 画面 / 控制 / 语言]
    ├── 制作人员
    └── 退出游戏

[游戏中 HUD]
    ├── 暂停 → [继续 / 设置 / 返回主菜单 / 退出]
    ├── 背包/状态 → [装备 / 技能 / 地图]
    └── 商店/对话界面
```

**HUD 布局草图：**
手绘一个游戏画面的矩形框，标出各个 UI 元素的位置。不用画精美，但要标清楚"左上角 = HP 条 + 数字""右上角 = 金币数""底部中央 = 技能冷却图标"。

**常见错误：** 直接打开 Figma 做高保真 UI，跳过了导航结构图。结果做出了漂亮的界面，但玩家找不到"存档"按钮在哪里。

#### P8：机制与道具

这一页的规则描述应精确到**可执行的数值范围或条件**；尚未验证的数字要标注为假设。

**格式要求：**
- 每个核心机制写出：（1）触发条件 （2）执行过程 （3）结果范围
- 每个道具有：名称、图标描述（文字即可）、效果（精确范围，如"回复 20-35 HP"）、获取方式、出现频率

```
机制：弹反（Parry，以下数值仅为格式示例）
- 触发条件：在敌人攻击命中前 0.15 秒内按下防御键
- 执行过程：播放 8 帧弹反动画（主角无敌）+ 6 帧硬直（敌人）
- 结果：反弹 150% 敌人原本伤害 + 眩晕敌人 1.5 秒
```

**常见错误：** 写"弹反很强""伤害很高"——这不是设计，这是愿望。精确的数值范围才会让你在后面的平衡工作中发现自己当初的假设有多离谱。

#### P9：敌人与 Boss

**敌人设计表格模板：**
| 敌人名称 | 出现区域 | AI 行为类型 | 攻击方式 | HP | 掉落 |
|---------|---------|-----------|---------|----|----|
| ... | ... | ... | ... | ... | ... |

**AI 行为分类（简化版）：**
| 类型 | 描述 | 例子 |
|------|------|------|
| 巡逻型 | 在固定路线巡逻，检测到玩家后追击 | 横版关卡中的杂兵 |
| 哨兵型 | 站着不动，视野内检测到玩家后攻击 | 炮台/弓箭手 |
| 追击型 | 主动追踪玩家位置 | 飞行敌人/Boss |
| 脚本型 | 按预设时间轴/血量节点切换行为 | Boss |

**Boss 单独页面要求：** 每个 Boss 至少描述：出现关卡、阶段数（Phase 1/2/3）、每个阶段的独特机制、击败奖励、战斗场地特征。

**常见错误：** 所有敌人用同一套 AI（"看到玩家 → 走过去 → 攻击"），没有行为差异化。这会导致所有战斗体验完全相同。

#### P10：过场 / 奖励 / 竞品

**过场形式选择：**
- 静态插画 + 文字（低成本，适合独立游戏）
- 游戏内实时演出（中成本，需要动画工具链）
- 预渲染动画（高成本，不推荐独立游戏）

**二周目/通关后内容：** 如果没有，写"无"。这本身就是一个重要的设计决策。不要因为"别的游戏都有"而强行添加 New Game+。

**竞品对比表：**
| 维度 | 竞品A | 竞品B | 我们的游戏 |
|------|------|------|----------|
| 核心机制 | ... | ... | ... |
| 时长 | ... | ... | ... |
| 差异化 | ... | ... | ... |

**常见错误：** 竞品对比只拿自己的优点跟别人的缺点比——这是自欺欺人。诚实的竞品对比会标注"竞品在这一点上比我们好"，然后你会知道该在哪里用力。

### Macro Chart：所有关卡/系统数据在一页表格

Macro Chart 的概念来自 Mark Cerny 在 *Ratchet & Clank* 开发中首创的方法。它的本质是：**把十页纸分散在各处的关键数据汇总到一张表里，让你一眼看出全局结构。**

| 关卡 | 主题 | 新敌人 | 新机制 | 新道具 | Boss | 预计时长 | 难度 |
|------|------|-------|-------|-------|------|---------|------|
| 1-1 | 森林 | 蘑菇怪 | 基础移动 | 无 | 无 | 3 min | ★ |
| 1-2 | 森林深处 | 蘑菇怪+ | 二段跳 | 生命药水 | 小Boss | 5 min | ★★ |
| 1-3 | 地洞 | 蝙蝠 | 攀爬 | 无 | 关底Boss | 8 min | ★★★ |
| ... | ... | ... | ... | ... | ... | ... | ... |

Macro Chart 的一个隐藏价值：**如果某一列在多个连续节点中都是空的，可能说明那一列的内容分布需要检查。** 比如一段较长内容没有引入新机制，或同一敌人变体重复出现，都可能造成疲劳；具体窗口应按游戏类型、关卡长度和体验目标判断。这些结构性问题在十页纸的文字描述中很难发现，但在 Macro Chart 中更容易看见。

## 6.3 Scope Budget：做完需要多少时间？

> **这一节解决什么问题：** 如何把十页纸的游戏内容翻译为可执行的时间预算？为什么独立游戏最常见的失败原因是"做不完"而不是"设计错"？

### 独立游戏的死亡公式

```
梦想的 Scope × 乐观的估算 + 零缓冲 + 无 Kill Criteria = 烂尾项目
```

独立开发者（尤其是单人）有一个普遍的认知偏差：**我们擅长估算一件"能理解"的事需要多久，但我们不擅长估算一件"没做过"的事需要多久。** 做一个敌人的 AI 行为，你以为 2 天能搞定——因为你脑子里想的是"写完行为树"。但你没算调试时间、边界情况、数值调优、测试反馈。实际需要 8 天。10 个敌人就是 80 天 vs 你估的 20 天——这个差距足够杀死任何项目。

### Scope Budget 计算表

| 内容类型 | 数量 | 单位成本（范围） | 小计（范围） | 备注 |
|---------|------|---------------|------------|------|
| **关卡/场景** | | | | |
| 普通关卡 | | 4-10 天/关 | | 取决于模板化程度 |
| Boss 战场地 | | 2-3 天/场 | | 通常比普通关简单（空间小） |
| 枢纽/菜单场景 | | 1-2 天/场景 | | |
| **敌人** | | | | |
| 普通敌人（模板化） | | 2-5 天/个 | | 基于模板改数值+外观 |
| 全新敌人（含 AI） | | 8-15 天/个 | | 从零写行为 |
| Boss | | 5-30 天/个 | | 复杂度差异极大 |
| **道具/装备** | | | | |
| 简单道具（纯数值） | | 0.5 天/个 | | 改数值即可 |
| 复杂道具（新机制） | | 2-5 天/个 | | 需要新代码+特效 |
| **UI 页面** | | | | |
| UI 页面（含逻辑） | | 1 天/页 | | 设计+实现 |
| **过场/动画** | | | | |
| 静态过场 | | 0.5-1 天/段 | | 插画+文字 |
| 实时过场 | | 2-5 天/段 | | 需要脚本/镜头 |
| **音效/音乐** | | | | |
| 音效 | | 0.2-0.5 天/个 | | 自制或选购 |
| 音乐曲目 | | 1-3 天/首 | | 自制曲目 |
| **系统功能** | | | | |
| 新系统（微原型验证过） | | 3-10 天/系统 | | |
| 新系统（未验证） | | **不做——先做微原型** | | |
| **总计** | | | | |
| 以上小计之和 | | | **A 天** | |
| 缓冲 | | | **B 天** | 按历史数据、风险清单和返工可能性估算 |
| **总工期** | | | **A + B 天** | |

> **重要警告：** 以上单位成本是**结构示例**，不是行业基准。设计阶段的估算本质上是“占位符”（placeholder）——它的作用是暴露数量级、依赖和不确定性，而不是精确排期。真实的单位成本应在 Step 5（垂直切片）中通过**代表性样本的产能**回填。参见 6.4 节了解项目自己的检查点。

### 为什么设计阶段的估算是"占位符"

来自 *Practical Game Design* 的估算原则：**Fermi 估算（费米估算）**——当你不确定精确值的时候，用上下界的平均值作为第一次近似。例如你不知道做一个 Boss 要多久，但你知道"肯定不少于 5 天，不太可能超过 30 天"——那就先用 (5+30)/2 = 17.5 天作为占位符。等到垂直切片阶段（Step 5），你实际做了 1-2 个 Boss 之后，再用实测天数替换这个占位符。

占位符的另一个作用是**暴露风险**。如果即使用最乐观的估算（所有内容取单位成本下界），总工期仍然超出你的可用时间——那你不需要等到 Step 5 才知道要砍内容。现在就可以砍。

### 游戏结构对 Scope 的影响

来自 *Practical Game Design* 的结构分析：不同游戏结构对内容量的需求差异巨大。

| 游戏结构 | 内容需求特点 | Scope 风险 | 典型代表 |
|---------|------------|-----------|---------|
| **线性关卡制** | 每个关卡都是独特内容，不可复用 | 高——每关都新做 | Celeste, Inside |
| **枢纽式** | 关卡可部分复用（回到旧区域） | 中——可复用降低内容需求 | Super Mario 64 |
| **Roguelike/随机生成** | 系统深度替代内容广度 | 低——一套系统 + 随机参数 = 无限内容 | Spelunky, Hades |
| **开放世界/沙盒** | 世界大但密度低 | 极高——需要大量环境资产 | Terraria（2D 例外） |
| **涌现式系统** | 简单规则 × 交互 = 复杂行为 | 低——内容从系统交互中自然产生 | RimWorld, Dwarf Fortress |

**关键洞察：** 如果你在做一款线性关卡制平台游戏，你的 Scope 几乎完全由"关卡数 × 每关时长"决定——砍一个关卡就是砍一次性的工作量。但如果你在做一款 Roguelike，你的 Scope 由"系统数 × 系统交互维度"决定——加一个系统可能等于加 N 种新组合。因此 Roguelike 的 Scope Budget 重点不在内容数量而在系统数量。

### 真实案例：估算一款类银河城独立游戏

假设你要做一款类银河城游戏，参考 *Hollow Knight* 的体量但缩到单人可完成的规模。以下是一个 Scope Budget 的填写示范：

| 内容类型 | 数量 | 单位成本（估） | 小计（范围） | 备注 |
|---------|------|-------------|------------|------|
| 区域/关卡 | 6 | 8-12 天/区 | 48-72 天 | 每个区域含美术、关卡设计、敌人布局 |
| 普通敌人 | 15 | 模板化 3-5 天 | 45-75 天 | 10 种基于模板 + 5 种全新 |
| Boss | 4 | 10-20 天/个 | 40-80 天 | 含战斗场地设计、阶段机制、测试 |
| 道具/能力 | 8 | 2-4 天/个 | 16-32 天 | 每获得一个新能力需要修改之前关卡提供新路径 |
| UI 页面 | 12 | 0.5-1 天/页 | 6-12 天 | 主菜单、地图、物品栏、商店、设置等 |
| Boss 战场地 | 4 | 2-3 天/场 | 8-12 天 | Boss 战专属空间 |
| 过场动画 | 3 | 1-2 天/段 | 3-6 天 | 开场 + 结尾 + 1 段中间高潮 |
| 音效 | 40 | 0.3 天/个 | 12 天 | |
| 音乐 | 8 | 2 天/首 | 16 天 | 6 区域 + 主题曲 + Boss 曲 |
| 系统功能 | 4 | 5-8 天/系统 | 20-32 天 | 存档、地图、成就、语言切换 |
| **小计** | | | **214-349 天** | |
| **风险缓冲（示例）** | | | **按已识别风险与情景另行估算** | |
| **总工期** | | | **278-454 天** | |

**这个数字意味着什么：** 这组数值只是演示如何把内容量映射到资源情景，不代表任何团队的工期基准。把估算与实际可用投入、外部依赖、品质档位和发布窗口比较；若保守情景不可行，再比较砍内容、改变方案、增加资源或延后发布等选项。

**砍内容的原则：先砍数量，后砍类型。** 把 6 个区域缩减到 4 个，远比"取消 Boss 战"对游戏体验的伤害小。砍数量保持结构完整，砍类型会在结构中留下空洞。

## 6.4 时间预算总表

> **这一节解决什么问题：** 七步流程中每一步应该花多少时间？什么时候触发 Kill Criteria？

### 各阶段的检查点与资源边界

| 阶段 | 检查点/资源边界 | 说明 |
|------|----------------|------|
| Step 1 概念孵化 | 价值主张、目标玩家、竞品和验证链足够清楚 | 不以研究数量或日历自动判定，通过证据缺口决定下一步 |
| Step 2 一页纸概要 | Core Loop、范围边界和主要风险可被团队复核 | 复杂项目可附补充页，重点是可取舍和可验证 |
| Step 3 原型验证 | 关键体验假设获得目标玩家或替代证据支持 | 若长期没有可解释证据，拆分假设、调整实验或重新评估方向 |
| **Step 4 十页纸深化** | 主要内容、依赖、产能区间和收缩情景可解释 | 文档服务于决策；若信息仍不足，补风险样本而不是追求形式完整 |
| Step 5 垂直切片 | 代表性品质、管线、产能和整合风险已取样 | 由最大未知数决定样本数量与范围 |
| Step 6 生产开发 | 稳定基线、变更记录和生产区间持续更新 | 新证据可触发受控回流 |
| Step 7 打磨 | 发布目标、关键风险和剩余返工成本可接受 | 依据发布标准和风险接受做 Go/No-Go 判断 |
| **Step 1-3 合计（→ 可玩原型）** | **由项目范围和风险决定** | 早期应出现能验证最大不确定性的可玩形式，不以统一月份判定成败 |

> 以上是决策结构，不是行业基准或自动 Kill 条件。复杂系统型游戏可以按最大不确定性增加验证周期；如果超出原计划，应检查 Scope、依赖和实验价值，而不是只用“超过两倍”判定。

### 为什么要有上限

检查点不是“到了就失败”——它是触发 Kill Criteria 复盘的信号。当你触达检查点时，系统性地检查：
1. 这一步的产出是否已经足够支撑下一阶段的决策？（如果是，进入下一步）
2. 这一步为什么花了这么久？是 Scope 太大，还是效率问题？
3. 后续步骤的预估时间是否需要因这一步的延迟而全面上调？

**最危险的情况：** 每个阶段都"稍微"超时一点点——Step 1 花了 5 周（超 1 周），Step 2 花了 3 周（超 1 周），Step 3 花了 70 天（超 10 天）……看起来每步都"只差一点点"，但累积起来，到 Step 5 你已经比原计划晚了 2 个月以上。这是计划逐渐腐化的过程——每次"只差一点点"都会让你习惯超时，直到你不再把超时当回事。

## 6.5 微原型：第4步的原型线任务

> **这一节解决什么问题：** 十页纸中写了新系统，如何确保这些系统不会在生产阶段才发现"根本行不通"？

### 为什么第4步还需要原型

Step 3 的原型验证了 Core Loop。但 Core Loop 只是游戏的核心循环——你的游戏里有更多系统：背包系统、技能树、对话系统、地图系统……这些系统虽然在 Core Loop 之外，但如果设计不当，同样会导致玩家流失。

微原型（Micro-Prototype）的概念是：**对每一个十页纸中定义的新系统，用与其复杂度和风险匹配的低成本投入做极简原型，验证"这个系统的基本逻辑是否成立"。**

| 系统 | 微原型验证什么 | 原型形式 |
|------|-------------|---------|
| 背包系统 | 物品的可拖拽/使用/丢弃逻辑是否顺畅 | 一个灰色矩形 + 几个方块，测试交互流 |
| 技能树 | 技能之间的依赖关系是否合理 | 纸上画节点和连线，用骰子模拟解锁 |
| 对话系统 | 选项分支的结构是否清晰 | 写 5 条对话的文本脚本，让朋友点选测试 |
| 地图系统 | 信息呈现是否足够（不迷路）也不过多（不无聊） | 画一张手绘地图，让测试者找到指定位置 |

### 微原型的核心纪律：一次只加一个系统

这是第 4 步原型线和第 3 步原型线的关键区别。在第 3 步，你主要验证核心体验假设；在第 4 步，微原型要检查新系统如何接入目标循环。通常一次只引入一个主要系统或实验包，以便定位影响；如果系统彼此不可分，应把它们作为一个整体记录并复测。Core Loop 是当前基线，不是不可修改的合同。

**操作流程：**
1. 在 Core Loop 原型的基础上，**只加一个新系统**的灰盒版本
2. 在与问题匹配的观察窗口内测试，回答："这个系统让 Core Loop 变好玩了，还是变复杂了？"
3. 如果变好玩了 → 保留，进入下一个系统
4. 如果变复杂了 → 简化或砍掉，不要犹豫
5. 重复，直到所有十页纸中定义的系统都经过微原型验证

> **来自 *Practical Game Design* 的 KISS 原则：** "系统在它被设计得尽可能简单时运行得最好。" 微原型是 KISS 原则的防火墙——当你做一个系统的最简版本时，如果它已经让人困惑，那加了美术和特效之后只会更困惑。反过来，如果一个系统在灰盒阶段就让人想反复操作，那你知道它的骨架是坚实的。

### 微原型的交付物

每个微原型结束后，你不需要写文档——只需要在 Scope Budget 表的"单位成本"那栏旁边加一个标记：
- ✅ = 验证通过，原估算合理
- ⚠️ = 验证通过但比预期复杂，单位成本需上调到 ___ 天
- ❌ = 验证失败，系统需要重新设计或砍掉

这个简单的标注系统让你在进入 Step 5 之前，用实际数据替换掉 Scope Budget 中所有的"猜测"。

## 6.6 Kill Criteria

> **这一节解决什么问题：** 什么信号说明你的十页纸计划不可执行——需要停下来调整？

Kill Criteria 不是让你"放弃游戏"，而是让你**停止自欺欺人**。当一个计划的执行基础不成立时，继续往前走不是执着，是浪费。

### Kill Criteria 表

| 触发条件 | 严重性 | 行动 |
|---------|-------|------|
| **预算明显超过可用资源** | 🔴 高风险 | 用区间和依赖拆解超支来源，优先砍内容、拆分交付或降低高风险复杂度；只有在替代方案不足时才停止项目。不要用单一倍数替代分析。 |
| **系统数量持续增加** | 🟠 严重 | 暂停无依据的扩展，锁定当前候选列表，确认每个系统支持哪条 Pillar、依赖和验证计划；缺乏价值或证据的系统先砍掉或延后。 |
| **无法估算生产总时间** | 🔴 致命 | 说明当前范围或依赖仍不可解释。回到 Scope Budget，按内容类型、样本、区间和情景拆解，而不是强行给出单点工期。 |
| **Macro Chart 出现明显空洞** | 🟡 警告 | 如果 Macro Chart 显示后半段关卡没有新机制/新敌人/新道具——这是一款"前半好玩后半重复"的游戏。重新设计后半段内容分布，或者缩短总关卡数。 |
| **十页纸长期无法形成可执行基线** | 🟡 警告 | 检查是否在追求形式完整、范围过大或关键未知未验证；可以先带着已知缺口进入针对性样本，再同步文档。 |

### 最危险的 Kill Criteria：预算无法解释或持续失控

这条规则看似简单，但它反直觉。当一个独立开发者发现 Scope Budget 的保守情景超出可用时间时，常见反应是压低单位成本或删掉风险缓冲，强行凑出一个可行数字。

这就是**自我欺骗型估算**——你不是在计算可能性，你是在给自己一个"看起来可行"的数字。正确的做法是反过来：从 200 天倒推，用 Scope Budget 的公式反算你最多能做多少内容，然后砍掉超出部分。

```
你的可用时间：[项目可用投入]
单位成本（按样本记录的区间）：[区域/敌人群/Boss群……]
反推结果：[基准情景与保守情景]
结论：[砍内容、拆分交付、改变方案、增加资源或延后发布]
```

这不是"妥协"，这是"执行"。世界上每一款完成的游戏，都是从"梦想版本"砍到"可行版本"的结果。区别只在于：你在第 4 步砍（零成本），还是在第 6 步发现做不完后烂尾（全盘皆输）。
