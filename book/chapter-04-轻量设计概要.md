# 第4章：第2步——轻量设计概要（One-Pager）

> **本章在全书中的位置：** 第1步（概念孵化）产生了创意方向和初步的市场判断，第3步（原型验证）需要用可玩代码测试核心假设。本章是两者之间最关键的一座桥——将模糊的概念翻译成一张可以指导建造的蓝图。如果说概念文档是"推销性"的，一页纸GDD就是"建造性"的。

---

## 本章解决什么问题

概念孵化阶段结束时，你的脑袋里可能塞满了各种想法：这个机制很酷、那个画面很美、再加一个系统会不会更丰富。这些想法在概念阶段都是财富，但到了建造阶段，它们如果在没有过滤的情况下涌入原型开发，就会变成灾难。

**本章的核心问题：** 如何把概念蒸馏成一张纸，让这张纸既足够具体（能指导原型方向），又足够锋利（能砍掉一切不必要的东西）？

**编程类比：** 如果概念文档是产品需求文档（PRD），那么一页纸GDD就是架构设计文档。它不规定每个函数怎么写，但它定义了不可违反的架构原则——类比于SOLID原则之于面向对象设计，Design Pillars之于游戏设计。没有架构原则的代码会腐烂成意大利面条；没有Design Pillars的游戏会膨胀成功能坟场。

## 4.1 一页纸的力量

**这一节解决什么问题：** 为什么写得越少，设计反而越好？为什么"限制为一页纸"不是懒惰，而是纪律？

### 篇幅压缩 = 思考压缩

写一份50页的设计文档不难——你只需要把你想到的所有东西全部倒出来。但写一份1页纸的GDD极难——你必须对每一个字做生死裁决。这个裁决过程本身，就是设计。

| 文档类型 | 作用 | 核心问题 | 读者 |
|---------|------|---------|------|
| 概念文档 | 推销 | "为什么有人会想要这个游戏？" | 投资人、出版商、团队、你自己 |
| 一页纸GDD | 建造 | "这个游戏到底是什么？怎么做第一个可玩版本？" | 你（开发）和你的合作者 |
| 完整GDD | 执行 | "每个系统的每个参数是多少？" | 团队（生产阶段） |

概念文档允许模糊——"一个充满探索感的开放世界"。一页纸不允许——你必须在"开放"后面接上"怎么做"和"不做"。

你刚从第 3 章过来，手里有一份填写完整的「概念要素表」。翻到这一页，发现一页纸 GDD 只有 6 个模块。不是遗漏——概念文档是推销工具（回答"这个想法值得做吗"），一页纸是建造蓝图（回答"第一步怎么做"）。Target Fantasy、Key Feature Set、Genre、Target Audience 在概念阶段已经完成了它们的使命——帮你选定了方向。到了建造阶段，你不再需要一遍遍告诉自己卖给谁、卖什么，你需要的是 Pillars（砍功能的刀）、Core Loop（施工图）、Scope Boundary（边界墙）、Art Direction（视觉预算）和 Razor Statement（一句话定海神针）。概念文档在对世界说"我觉得这个值得做"，一页纸在对自己说"我知道怎么做了，也知道哪些绝对不做"。

### 为什么一页纸比详细GDD更适合独立开发

**1. 你不需要跟自己沟通。** 大团队需要详细文档是因为设计者和实现者是不同的人。你既是设计者又是实现者——你需要的是决策框架，不是沟通文档。

**2. 设计在实现中会变。** *Rules of Play*明确指出：设计文档在开发开始的那一刻就过时了。一份100页的GDD在第一行代码运行后可能被推翻一半——你只是不知道是哪一半。一页纸给出的不是"结论"，而是"原则"——当原型告诉你"这个方向不对"时，原则帮你判断该往哪改。

**3. 篇幅限制 = 专注力保护。** 独立开发者最稀缺的资源不是时间，是专注力。一页纸GDD像一个"抗干扰过滤器"：每当你想到一个新功能、一个酷点子，把它往这一页纸上放——放得下吗？支持Pillar吗？在Scope内吗？90%的新想法在这一步就被合理拒绝了。

### 一页纸GDD的结构总览

```
# [游戏名]

## Pitch（1-2句）
[一句话定义这个游戏是什么，以及为什么它值得存在]

## Design Pillars（2-4条）
[不是功能列表，是体验原则——每条都是砍功能的刀]

## Core Loop（箭头图）
[玩家每30秒做什么 + 回报是什么]

## Scope Boundary
### 必须有：
[完成核心体验不可缺失的功能]
### 明确不做：
[Non-Goals——比Goals更重要]

## Art Direction
[视觉原则 + 3-5张参考图链接 + 色板]
```

六个模块，一张纸，砍掉一切不必要的东西。下面逐一展开。

## 4.2 Design Pillars的科学定义与验证

**这一节解决什么问题：** 大部分设计师的Pillars是错的——它们不是Pillars，是功能分类。这一节告诉你真正的Pillars长什么样，以及如何验证你的Pillars不是自欺欺人。

### Pillars不是功能列表

这是最常见的Pillar陷阱。看看下面两组对比：

| 错误的Pillars（功能分类） | 正确的Pillars（体验原则） |
|------------------------|------------------------|
| "战斗、潜行、社交" | "每一次接敌都是一场生死博弈" |
| "跳跃、射击、收集" | "移动本身就是一种奖励" |
| "卡牌、肉鸽、构筑" | "每次选择都在定义你是谁" |

左边的写法是游戏系统分类——它告诉你游戏里"有什么"。右边的写法是体验描述——它告诉你玩家会"感受到什么"。**Pillars是关于"为什么"的，不是关于"是什么"的。**

> **编程类比：** 功能分类Pillars就像把代码架构原则写成"数据库模块、前端模块、API模块"——这是目录结构，不是架构原则。真正的架构原则是SOLID——"单一职责、开闭原则、依赖反转"——它们不规定有什么模块，但规定了所有模块必须遵守的约束。

### Pillars的四大特征

一条合格的Design Pillar应该同时满足以下四个条件：

| 特征 | 含义 | 反面案例 |
|------|------|---------|
| **体验导向** | 描述玩家的情绪状态，而非游戏内的功能类别 | "卡牌收集系统"→ 这是功能，不是Pillar |
| **可砍功能** | 能用它做一个"删"vs"留"的决定 | "沉浸感"无法用来砍任何具体功能——太模糊 |
| **相互独立** | 每条描述不同的体验维度，不重叠 | Pillar1="快节奏战斗" Pillar2="速度感"——重复了 |
| **2-4条** | 少于2条=游戏太单薄，多于4条=没有取舍 | 有6条Pillar的游戏等于没有Pillar |

### 真实游戏Pillar解析

| 游戏 | Design Pillars | 每条如何砍过功能 |
|------|---------------|-----------------|
| **God of War (2018)** | (1) 每一次攻击都有重量 (2) 父与子的羁绊贯穿一切 (3) 世界在召唤你去发现秘密 | Pillar(1)砍掉了所有"轻飘飘"的动作选项（无空中连段、无二段跳、无闪避取消）；Pillar(2)砍掉了传统ACT的关卡选择界面——一切通过父子在船上的对话自然发生 |
| **Hades** | (1) 死亡不是终点，是回家的路 (2) 每次逃脱都是独一无二的 (3) 希腊神话的鲜活人格 | Pillar(1)直接催生了"死亡回府后NPC对话更新"的核心系统——如果在其他游戏中这个会被砍掉（"太贵"）；Pillar(2)砍掉了固定Build推荐，强制随机神祇 |
| **The Last of Us** | (1) 每一颗子弹都是决定 (2) 信任是挣来的，不是给的 (3) 绝望中的人性微光 | Pillar(1)砍掉了无限弹药和自动回血；Pillar(2)决定了Ellie的AI行为必须从"无用"进化到"可靠"——如果Pillar写成"AI同伴"就只能得到跟随脚本 |
| **Celeste** | (1) 攀登的挫败是成长的一部分 (2) 速度感来自精准 (3) 内心的山比外界的山更难爬 | Pillar(1)砍掉了"简单模式"——死亡必须频繁且无惩罚；Pillar(3)砍掉了冗长过场动画——叙事通过关卡设计和快速重生来表达 |
| **《炉石传说》** | (1) 每次对战是一场心理博弈 (2) 5分钟内分出胜负 (3) 每张牌都有故事 | Pillar(2)砍掉了复杂连锁系统和长回合制——任何会让单局超过10分钟的设计必须被移除 |

### Pillar的浓缩：Razor Statement

来自《Video Game Design For Dummies》的建议：在写完Pillars后，把它们浓缩为一句话——这就是你的**Razor Statement（剃刀宣言）**。它如同奥卡姆剃刀，每当你的游戏面临"加还是不加"的决定时，用它一刀切下去。

> **Razor Statement = 你的游戏最不可妥协的那一句话。**

| 游戏 | Razor Statement |
|------|----------------|
| God of War (2018) | "一个父亲教儿子如何在北欧诸神的世界中生存——斧子的每一次挥动都必须有意义" |
| Hades | "逃出地狱本身就是奖励" |
| Celeste | "你死得越快，你爬得越高" |
| Portal | "一把不能杀人的枪，和一间教你恨自己的实验室" |

### Pillar有效性测试

写完你的Pillars后，做这个测试——通过不了就回去改：

**测试一：能不能用它砍掉至少一个已有计划中的功能？**

如果你列了3条Pillar，每条问自己："基于这条Pillar，我们的游戏里有什么东西应该被砍掉？"如果答案是"没有"——这条Pillar等于没写。它没有做出任何取舍。

**测试二：给一个不认识的人读你的Pillars，问他"这个游戏玩起来是什么感觉？"**

如果他读到"战斗、潜行、社交"后说"是一个动作游戏？"——这是无效读取，因为他读完后没有得到任何关于**体验**的信息。如果他读到"每一次接敌都是一场生死博弈"后说"这好像是个很紧张、不能失误的战斗？"——你的Pillar起作用了。

**测试三：你自己能否用一句话解释每条Pillar为什么"不是另一条Pillar"？**

如果两条Pillar之间界限模糊（例："压迫感"和"紧张感"），合并它们。独立的Pillars才构成独立的决策维度。

## 4.3 从Pillar到机制的推导流程

**这一节解决什么问题：** Pillars是"感觉"，原型需要的是"代码"。怎么把"侵略性战斗"翻译成"冲锋时移速+15%，处决回血30%"？这一节给出五步推导法。

### 骨架-血肉-灵魂在这个时刻的作用

在第0章中，我们建立了三层模型：骨架（机制与规则）、血肉（表现与反馈）、灵魂（叙事与情感）。在一页纸GDD阶段，我们实际上是**从灵魂倒推骨架**：

```
通常视角（玩家）：灵魂（感受） ← 血肉（行为） ← 骨架（规则）
设计视角（你）：  灵魂（目标感受） → 血肉（期望行为） → 骨架（设计规则）
```

你从你希望玩家感受到什么（灵魂 = Pillars）出发，推导出玩家在每一秒需要经历什么即刻体验（血肉——包括行为上的纠结和感官上的反馈），再推导出你需要设计什么规则（骨架）来驱动那些体验。注意：这里的"血肉"同时包含行为动态（玩家做什么决策、陷入什么纠结）和感官反馈（看到什么、听到什么、感受到什么）——两者都是玩家即刻体验的一部分，只是来源不同。详见第 0 章的三层模型定义。

> **编程类比：** 这就像先写集成测试（"玩家应该感受到侵略性"），再倒推实现代码（"处决回血 + 移速奖励"）。先定义期望的输出，再推导需要的输入。

### 五步推导法

| 步骤 | 名称 | 做什么 | 示例（Pillar = "侵略性战斗"） |
|------|------|--------|---------------------------|
| 1 | **Pillar → 玩家感受** | 描述玩家体验到这条Pillar时的**具体情绪状态** | "停不下来、越打越强、主动找敌人、不想防御" |
| 2 | **感受 → 玩家动作** | 问"玩家在这种情绪下在**做什么**" | 不停前进、近战处决、不掩护、不换弹、不撤退 |
| 3 | **动作 → 系统支持** | 什么**规则**让这些动作成为最优解 | 处决回血、弹药自动从尸体补充、连续击杀移速奖励、远程伤害递减 |
| 4 | **检查整合度** | 这个系统是否服务**多条**Pillar？ | 处决回血同时服务"侵略"和"力量感"——整合度高的机制是设计质量的信号 |
| 5 | **写进Core Loop** | 用推导出的机制填充核心循环 | 探索→发现敌人→冲锋→近战击杀→处决回血→继续前进 |

### 完整案例：以"侵略性战斗"Pillar推导一个战斗系统

假设你的游戏有两条Pillar：
- **Pillar 1：侵略性战斗**——不停歇的前进和摧毁
- **Pillar 2：力量反馈**——每一次攻击都让玩家感到自己在输出毁灭

**第1步：Pillar → 感受**

| Pillar | 目标感受 | 反面感受（我们的游戏不要什么） |
|--------|---------|---------------------------|
| 侵略性战斗 | "停不下来" "越打越强" "主动寻找敌人" | 龟缩掩体、等待时机、拉锯消耗 |
| 力量反馈 | "每一击都很重" "敌人被击飞" "屏幕在震动" | 轻飘飘的打击、敌人反应延迟、数值飘字替代物理反馈 |

**第2步：感受 → 动作**

目标感受指向以下玩家行为：
- 不停向前移动
- 主动接近敌人（而非等待敌人接近）
- 近战优先于远程
- 不换弹，不停火
- 不撤退、不找掩体

**第3步：动作 → 系统**

现在问：什么规则能让"不停向前冲"成为玩家自然选择的最优策略？

| 期望动作 | 支持系统（机制规则） | 否决的设计 |
|---------|-------------------|-----------|
| 不停向前移动 | 连续移动3秒后移速+15%；停止移动则移速加成归零 | 掩体系统（鼓励停留） |
| 近战优先 | 处决回血30%；远程武器伤害随距离递减20%/米 | 狙击系统（鼓励远程） |
| 不换弹 | 近战击杀自动补充弹药；弹匣容量设得小以鼓励近战 | 弹药箱收集（鼓励绕路） |
| 不撤退 | 脱离战斗超过5秒，所有伤害Buff清零 | 脱战回血（鼓励逃跑） |

**第4步：整合度检查**

| 系统 | 服务Pillar 1（侵略性） | 服务Pillar 2（力量感） | 整合度 |
|------|----------------------|----------------------|--------|
| 处决回血 | 鼓励近战，不停下 | 处决动画=力量展示 | 高 |
| 移速奖励 | 鼓励持续前进 | 高速移动=力量感 | 高 |
| 远程递减 | 鼓励靠近 | — | 中（只服务一条） |
| 弹药自动补 | 鼓励近战，不停火 | — | 中 |

整合度高的系统（处决回血、移速奖励）是你的**核心机制**——它们在多条Pillar上交汇，砍掉它们会同时损害多个体验维度。整合度中的系统可以作为辅助。**如果某个系统只服务一条Pillar且整合度不高——考虑它是否真的必要。**

**第5步：写入Core Loop**

```
移动加速 → 发现敌人 → 快速接近 → 近战击杀 → 处决回血+弹药补满 → 寻找下一群敌人 → (循环)
           ↑                                                             ↓
           └─────── 脱离战斗5秒 → 移速Buff清零 ←──（玩家自然避免）─────────────┘
```

## 4.4 Core Loop：30秒内的最小可玩单元

**这一节解决什么问题：** 你的游戏可能有很多系统，但玩家每30秒在重复什么？那个"重复单元"就是Core Loop——它是你的游戏设计的第一性原理。

### Core Loop的定义与作用

**Core Loop（核心循环）** 是玩家在游戏中每30秒内重复的最小行为-回报周期。它不是"玩家可能做什么"，而是"玩家在最基础的层面上，1分钟里会反复经历什么"。

*Rules of Play*将Core Loop定义为**有意义选择的微循环**：每一个循环中包含一个可辨识、可整合的选择。玩家做了某个动作，得到一个可感知的结果（可辨识性），这个结果会影响他下一步的选择（可整合性）。

如果你的Core Loop中包含的选择不满足可辨识和可整合两个条件，你的游戏在30秒的尺度上就不是在制造"有意义的游玩"——它只是在制造"操作"。

> **Core Loop vs Core Mechanic：** Core Loop 是循环结构（30秒级的行为-回报闭环），Core Loop 中的每个节点又由更原子的 **Core Mechanic（核心机制）**构成——Loop 是"为什么玩"，Mechanic 是"玩什么动作"。第1章 §1.4 有完整的概念层级梳理，第10章有 Core Mechanic 的系统化设计方法。在一页纸阶段，你主要定义 Core Loop；在原型验证阶段（第5章），你需要把 Loop 中的每个 Core Mechanic 做成可玩的灰盒。

### 箭头图表示法

Core Loop用箭头图表示，每个节点是一个动作或状态，箭头表示流向。基础结构：

```
[动作A] → [动作B] → [回报] → [增强能力/资源] → 回到[动作A]（循环）
```

它通常包含三个要素：
1. **玩家做了什么**（动作）
2. **系统给了什么反馈**（回报）
3. **回报如何改变下一次循环**（成长/变化）

### 不同游戏类型的典型Core Loop结构

| 游戏类型 | Core Loop结构 | 循环周期 | 关键决策点 |
|---------|-------------|---------|-----------|
| **Roguelike动作**（*Hades*） | `进入房间 → 战斗 → 清场 → 选择奖励 → 进入下一房间` | 30-60秒/房间 | 奖励选择（门的选择） |
| **卡牌构筑**（*Slay the Spire*） | `抽牌 → 出牌 → 敌人行动 → 回合结束 → 抽牌` | 5-10秒/回合 | 每回合出哪几张牌 |
| **平台跳跃**（*Celeste*） | `进入屏幕 → 观察 → 尝试 → 死亡 → 重生 → 再尝试 → 通过` | 5-30秒/屏幕 | 路线选择 + 执行 |
| **生存建造**（*Don't Starve*） | `白天探索收集 → 夜晚回到基地 → 建造/烹饪 → 新一天探索` | 8分钟/天 | 去哪里探索、造什么 |
| **银河城**（*Hollow Knight*） | `探索新区域 → 遭遇敌人/平台挑战 → 发现捷径/能力 → 回到旧区域解锁新路径` | 数分钟-数十分钟 | 岔路选择 + BOSS战 |
| **模拟经营**（*Stardew Valley*） | `起床 → 浇水/收获 → 探索/社交 → 回家睡觉 → 第二天` | 13分钟/天 | 今天优先做什么 |

> **关键观察：** 越是重度游戏，Core Loop周期越短。*Hades*的房间级循环30秒，*Slay the Spire*的回合级循环5秒。这不是偶然——短循环意味着高密度的有意义选择，高密度选择意味着高参与度。

### Core Loop作为诊断工具

如果你的Core Loop画出来后发现某个环节没有"有意义的决策"，那一环就是你的设计缺口：

```
错误示例：探索 → 战斗 → 拾取金币 → 探索 → ...
        问题：拾取金币不是决策，没有改变循环
修正后：探索 → 战斗 → 选择"升级武器 or 购买药水" → 增强能力的探索 → ...
```

### Core Loop设计的四条铁律

| 铁律 | 含义 | 反面案例 |
|------|------|---------|
| **每条循环必须包含至少一个有意义的选择** | 玩家做的是一个在多种有意义的选项之间的决策 | "按A键捡金币"不是选择——你没有其他选项，或者所有选项等价 |
| **循环必须有明确的回报** | 循环结束后，玩家得到了什么（资源、进度、信息、情感） | 打完一波敌人什么都没给——玩家问"我为什么要打" |
| **回报必须改变下一次循环** | 上一轮的结果影响下一轮的条件或选项 | 关卡制游戏打完一关→下一关完全相同没有新东西——没有成长感 |
| **循环必须能独立运行** | 单独的Core Loop应该已经是可玩的了 | 需要等3个系统都做好才能玩——你的原型验证被阻塞了 |

## 4.5 Scope Boundary：明确不做比明确要做更重要

**这一节解决什么问题：** 做游戏最大的诱惑不是不做，是"顺便也做一下"。这一节教你Scope Boundary的填写策略——Non-Goals才是真正的设计决策。

### 为什么Non-Goals比Goals更重要

一个游戏在概念阶段往往有50+个想做的功能。你不会全做——你需要砍掉至少40个。但砍的标准是什么？

有两个标准：
1. **预算不够**——这是被动的砍，痛苦且纠结
2. **不符合Pillars**——这是主动的砍，清晰且合理

Scope Boundary的作用是把砍功能这件事**从"预算妥协"变成"设计选择"**。你不是"因为没时间所以不做多人模式"，你是"因为这个游戏是关于孤独探索的，所以不做多人模式"。前者让你觉得亏欠，后者让你更清晰地定义了游戏。

> **编程类比：** 好的架构设计文档不仅有"我们用什么技术栈"，更有"我们明确不用什么"——不用微服务（因为规模不够）、不用NoSQL（因为需要事务）。这些否定句比肯定句更能定义系统边界。

### Non-Goals填写策略

**策略一：每个Pillar对应至少一个Non-Goal。**

| Pillar | Non-Goal |
|--------|---------|
| "每一次攻击都有重量" | 不做浮空连段、不做二段跳、不做动作取消 |
| "父与子的羁绊贯穿一切" | 不做传统菜单式关卡选择、不做独狼模式 |
| "世界在召唤你去发现秘密" | 不做小地图指针导航、不做任务列表 |

**策略二：从竞品差异中提取Non-Goal。**

问自己："那些同类型游戏都在做但我不想做的东西是什么？"这是最有信息量的Non-Goal。

| 如果你的游戏是…… | 同类型的默认期待 | 你的Non-Goal |
|----------------|---------------|-------------|
| 一个类Roguelike | 永久升级系统 | "不做永久属性升级——每次开局从零开始" |
| 一个类银河城 | 地图系统 | "不做自动地图填充——玩家需要自己记忆路径" |
| 一个类动作RPG | 技能树 | "不做技能树——所有能力通过装备获得" |

**策略三：把Non-Goal写成用户视角的否定句。**

| 弱 | 强 |
|----|----|
| "不做PVP" | "你永远不会遇到另一个玩家" |
| "没有技能树" | "你的角色不需要升级就能应对所有挑战" |
| "不做开放世界" | "选了一条路就不能回头——每一个岔路都是真正的决定" |

### Scope Boundary填写模板

```
## Scope Boundary

### 必须有（未完成这些 = 游戏不成立）：
- [核心机制A]：为什么必须有 / 对应哪条Pillar
- [核心机制B]：为什么必须有 / 对应哪条Pillar
- [核心机制C]：为什么必须有 / 对应哪条Pillar
（不超过5项）

### 明确不做（这些在概念阶段就被排除）：
- [不做X]：因为与Pillar [ ] 冲突 / 或者：因为这是另一个游戏想做的
- [不做Y]：因为超出我们2人12个月的能力范围
- [不做Z]：因为同类型竞品已经做得足够好，差异化空间为零
（建议3-8项）
```

## 4.6 美术方向（Art Direction）

**这一节解决什么问题：** 独立游戏的美术不是"画得好看"的问题，是"在有限资源下建立独特视觉辨识度"的工程问题。这一节告诉你：风格选择 = 时间预算，约束 = 高级感。

### Art Pillars与Design Pillars平行

Art Pillars是Design Pillars在视觉维度的翻译。它们不是技术规格（"分辨率1920×1080，3D渲染"），而是**视觉体验原则**。

| 游戏 | Design Pillars（体验） | Art Pillars（视觉） |
|------|----------------------|-------------------|
| *Hades* | 每次逃脱独一无二、希腊神话鲜活人格 | 希腊陶绘风格 + 高对比色 + 流畅逐帧动画 |
| *Limbo* | 未知的恐惧、孤独感 | 剪影可读性 + 单色恐怖 + 留白引导 |
| *Hollow Knight* | 探索被遗忘的王国 | 手绘线稿 + 蓝灰色调 + 发光粒子点缀 |
| *Return of the Obra Dinn* | 推理、还原真相 | 1-bit 单色渲染 + 老式Macintosh美学 |
| *What Remains of Edith Finch* | 每个故事是一扇窗 | 每个家族成员的场景用不同的艺术风格 |

> **关键规律：** 这些游戏的美术策略不是"尽力画得最好看"，而是**选择一个独特的约束，在约束内做到极限**。

### 风格选择 = 时间预算

3-5人团队能否在预算内完成，更多地取决于视觉策略而非美术功底。这是一个被无数独立项目验证过的残酷事实：

| 视觉策略 | 时间成本（相对） | 适用场景 |
|---------|--------------|---------|
| 逐像素手绘动画 | 极高 | 有专业像素画师的团队 |
| 3D写实渲染 | 极高 | 有3D美术团队且工期充裕 |
| 低多边形（Low Poly）风格 | 中 | 节省建模时间，靠光影和色彩出效果 |
| 手绘2D + 骨骼动画 | 中 | 折中方案——画一套部件，骨骼驱动动画 |
| 极简几何图形 | 低 | 以玩法为核心的游戏（*Thomas Was Alone*） |
| 单色/1-bit | 极低 | 零预算也能做出强烈风格（*Return of the Obra Dinn*） |
| 摄影/拼贴/现成素材改造 | 极低 | 零预算的实验性方案 |

**选择规则：** 先确定你能投入多少美术时间，再从对应的成本层级中找风格。**不要先选风格再算时间——等你算清楚已经晚了。**

### 色彩约束理论

AAA游戏的秘密之一：**看起来越高级的画面，独立颜色数越少。** 不是"多用颜色 = 更丰富"，而是"少用颜色 = 更统一"。

**操作步骤：**
1. 选择3-5个**主色**（占据60%画面的颜色）
2. 选择3-5个**辅色**（占据30%画面的颜色）
3. 选择2-3个**强调色**（占据10%画面的颜色，用于UI高亮和关键信息）
4. 使用 Coolors.co 或 Lospec 生成并**锁定**色板——导出为引擎可导入的色板文件

| 游戏 | 主色 | 辅色 | 强调色 |
|------|------|------|------|
| *Hollow Knight* | 深蓝、深灰、黑 | 蓝灰、暗紫 | 白色发光、橙色（感染） |
| *Hades* | 红、黑、金 | 紫、深蓝 | 白（发光效果） |
| *Celeste* | 蓝、紫、白 | 绿、棕 | 红（Madeline的头发） |

### 金标准（Gold Standard）建立方法

Gold Standard是你选择的一个代表性场景、角色或道具，画到**最终品质**。后续所有资产都以此为参照。

**建立步骤：**
1. 从你的游戏中选一个"最具代表性"的场景——它包含90%会在其他场景中出现的美术问题（光照、材质、角色、环境、UI叠加）
2. 将这一场景画到最终品质——不是草图，是"可以截图放Steam页面"的水准
3. 从中提取一套可复用的**视觉规范**：形状语言、渲染方式、色彩盘、细节密度、线条粗细
4. 分别为角色、环境、道具建立独立的Gold Standard——三者在规范上统一但在细节密度上可能有差异

**金标准的作用：**
- 它是所有外包/合作美术的**答案**——不需要反复沟通"我要什么风格"
- 它是你自己的**品味标尺**——新画的东西和它放在一起，差距一目了然
- 它是Steam页面的**第一印象**——在你有完整游戏之前，这个场景就能告诉世界你的游戏长什么样

### 反例清单

列出3-5种"我们的游戏绝对不用的视觉方向"——这种否定比参考板更锋利。

> "参考板告诉美术'往哪边走'，反例清单告诉美术'哪边是墙'。"

| 反例方向 | 为什么不用 |
|---------|-----------|
| 华丽的UI特效覆盖游戏画面 | 游戏是关于宁静和留白，UI应该退到背景中 |
| 饱和度高到刺眼的霓虹灯色 | 色板已锁定为大地色系，任何荧光色都会破坏统一性 |
| 3D写实比例角色 | 2D风格化已确定，写实3D资产无法与手绘背景融合 |

## 4.7 Kill Criteria：两个致命的停止信号

**这一节解决什么问题：** 一页纸写完了，怎么判断它"够不够好"？如果不够好，是该修改还是该回到上一步？这一节给出两个不可商量的Kill Criteria。

### Kill Criterion 1：可读性测试失败

**测试方法：** 把你的One-Pager给两个不认识你游戏的人读。不解释，不补充。读完后问他们一个问题：

> "所以这是什么游戏？用你自己的话说。"

**判定标准：**

| 结果 | 判定 |
|------|------|
| 两个人的描述高度一致，且与你的意图匹配 | 通过——进入第5章 |
| 两个人的描述差异很大，或者都很模糊 | 警告——Pillars或Pitch不够锋利，修改后重新测试 |
| 有人完全无法描述出这个游戏是什么 | 失败——回到第3章（概念孵化），你的概念还没结晶 |
| 描述的体验与你的意图相反 | 严重失败——Pillars写错了或者Pillars与机制脱节 |

### Kill Criterion 2：Scope明显失控

把你的"必须有"列表快速估算所需工期：

| 条件 | 判定 |
|------|------|
| 单人 ≤ 6个月 / 3人 ≤ 4个月 | 健康 |
| 单人 6-12个月 / 3人 4-8个月 | 边界——重新审视Non-Goals是否够锋利 |
| 单人 > 12个月 / 3人 > 8个月 | **失控——立即缩减Scope**。砍掉至少一个"必须有"，或者将一个"必须有"降级为"如果有时间做" |

**缩减的优先级：**
1. 砍掉只服务一条Pillar的系统（低整合度）
2. 砍掉同类型竞品都有的系统（不做"标配"，做"差异"）
3. 砍掉需要依赖其他系统才能运行的系统（链式依赖 = 工期不可控）

## 实操清单

在进入第5章（原型验证）之前，请确认：

- [ ] 从概念文档浓缩到一页纸——每一句话都经得起"为什么要写它"的审问
- [ ] Design Pillars通过三项有效性测试：能砍功能？读的人能感知体验？相互独立？
- [ ] 写完了Razor Statement——一句话就能说清楚游戏的核心
- [ ] 每条Pillar完成了五步推导（感受→动作→系统→整合度→Core Loop）
- [ ] Core Loop的每个节点都包含一个有意义的玩家选择
- [ ] Core Loop能在30秒内完成至少一次完整循环
- [ ] Scope Boundary列出至少3项Non-Goals，每项有明确的"为什么不做"
- [ ] 完成了美术方向六要素：Art Pillars、色板锁定、参考图收集、反例清单、金标准描述、时间预算估算
- [ ] 找2个人做可读性测试——"这是什么游戏？"的回答一致且符合预期
- [ ] Scope估算在安全范围内：单人≤12个月，3人≤8个月

## 骨架-血肉-灵魂自查

用三层分析框架检查你的一页纸GDD是否完整：

| 层级 | 检查项 | 通过标准 |
|------|--------|---------|
| **骨架（机制）** | Core Loop箭头图是否闭合？是否有至少一个有意义的选择？Pillar→机制的推导是否完整？Scope是否在预算内？ | Core Loop的每个节点都可解释为"玩家在做什么决策"，且这个决策的结果会影响下一次循环 |
| **血肉（表现）** | Art Pillars是否与Design Pillars平行？色板是否锁定？是否有金标准描述？反馈系统（音效、视觉、UI）是否在Core Loop中被标注？ | 有人读完Art Direction后能用一句话描述"这个游戏看起来像什么" |
| **灵魂（情感）** | Pillars是否以玩家情绪而不是功能来描述？Razor Statement是否传达了一种独特的情感承诺？读完一页纸的人是否会感到"我想玩这个"？ | 可读性测试中，对方描述的游戏体验与你的意图一致——不只是"什么类型"，更是"什么感觉" |

**三层脱节的警告信号：**
- 骨架缺位 = Core Loop无法独立运行
- 血肉缺位 = 美术方向模糊、色板未锁定
- 灵魂缺位 = Pillars写成功能分类、Razor Statement没有情感承诺

如果你的自查发现某层有明显缺口——不要跳到第5章。一页纸GDD是建造蓝图，蓝图上有缺口，建出来的墙一定是歪的。
