# 第5章：第3步——原型验证

> **本章在全书中的位置：** 第2步完成了 One-Pager（轻量设计概要），定义了 Core Loop 和 Design Pillars。本章是全流程中最重要的质变点——从"纸上谈兵"到"动手验证"。原型验证是双螺旋模型中设计线与原型线交汇最密集的阶段，你的所有设计假设将在这里被现实击穿或证实。

---

## 本章解决什么问题

你已经有了一个看起来不错的设计概要——Pillars 清晰、Core Loop 画得漂亮、Scope 控制得也不错。但你**仍然不知道**这个游戏好不好玩。写在纸上的"玩家攻击→获得资源→升级装备→再攻击"和一个真正好玩的游戏之间，隔着一条无法用推理跨越的鸿沟。

**原型验证**就是用最低成本、最短时间，让目标玩家的真实行为来回答那个终极问题：
> **目标玩家觉得这个核心机制好玩吗？**

对程序员读者来说，本章的类比是：**原型 ≈ 最小可行代码**，Playtest ≈ 用户测试，Kill Criteria ≈ 测试用例失败条件。

---

## 5.1 原型是什么

> **这一节解决什么问题：** 很多开发者把原型做成"半成品游戏"，或者用"还在原型阶段"作为推迟决策的借口。本节重新定义原型的工作目的——它是一个信息获取工具，不是提前开发。

### 原型不是"简陋的游戏"

原型和游戏的关系，就像实验室里的试管和市售药品的关系。试管的唯一目的是验证一个假设（"这种化合物能抑制细菌吗？"），验证之后它就可以扔掉了。**原型也一样——它的价值不在于功能完整，而在于它能回答一个明确的问题。**

Katie Salen 和 Eric Zimmerman 常被引用的“20% 规则”可以作为一种项目纪律提醒：

> “尽早让项目进入可玩验证，而不是等设计文档全部完成。”

这个提醒的本质不是精确计时，而是一种**纪律**：在设计假设仍可低成本修改时尽早测试，而不是等完整文档或大量内容完成后才发现假设不成立。不同项目应按风险、工具、团队和验证成本设置自己的检查点。

### Kyle Gabler 的短周期框架

Kyle Gabler（*World of Goo* 联合设计师）是独立游戏圈内“快速原型”理念的代表人物之一。以短周期完成实验可以帮助压缩范围，但“几天足够验证大多数玩法假设”不应被当作普遍保证；验证难度取决于问题类型和实现成本。

但这个框架需要区分游戏类型：

| 常可用短周期原型先行 | 通常需要更长或分阶段验证 |
|---|---|
| 平台跳跃 / 射击 / 解谜 | MMO / 沙盒 |
| 塔防 / 卡牌 / 肉鸽 | UGC / 社交游戏 |
| 街机 / 跑酷 / 节奏 | 经济模拟 / 4X |

对于复杂系统型游戏（如 *RimWorld* 式的殖民地模拟），单个核心机制的验证可能需要数周或分阶段完成，不应勉强套用短周期框架。这里的关键纪律不是某个天数，而是：**当原型长期没有减少关键不确定性时，要重新检查问题、范围和下一步决策。**

如果经过较长时间仍在无明确假设地“调原型”，你可能是在用“原型”这个词掩盖一个事实：你不想面对“这个机制可能不对”的结论。

### James Margaris 的警告（2025）

GameDiscoverCo 的 James Margaris 在 2025 年 GDC 演讲中发出了一个尖锐的警告：**"原型可能成为掩盖优柔寡断的借口。"**

> 原型的正确用法是“信息获取工具”。如果若干轮原型后仍然没有明确结论，先检查每轮是否验证了不同且清晰的假设；如果已经用多种低成本实现反复验证，目标玩家仍持续否定核心价值主张，才有理由回到概念层或停止。

这与 *Practical Game Design* 中反复强调的"原型不是终身项目"完全一致。原型的目的是**终结不确定性**，而不是**推迟决策**。

### 编程类比

| 编程概念 | 游戏设计对应 |
|---|---|
| 写一个最小可运行代码片段来测试一个 API 的行为 | 做纸上原型来测试核心规则是否产生有趣决策 |
| Code review 发现的逻辑错误 | Playtest 中玩家困惑/放弃的位置 |
| 测试用例失败 → 改代码 | Kill Criteria 触发 → 改设计或停止 |
| 重构代码以提高可维护性 | 迭代原型以验证修改方向 |
| 把 prototype 代码扔进垃圾桶、重新写生产代码 | 验证完成后废弃原型、从零开始搭建项目 |

底线：**如果在原型阶段没有产生让你决定"改方向"或"停止"的信息，那这个原型就不是在验证——是在逃避。**

### Balatro 的原型哲学：用最少信息解决最关键的不确定性

*Balatro* 的开发者 LocalThunk 在原型阶段只做了一个极其简单的决策：在已知扑克牌规则上叠加 Roguelike 的"小丑牌"修正器。他没有做精美 UI（原型的画面几乎就是纯文字+数字），没有做音乐音效，甚至没有做完整的牌组动画。他只需要验证一个假设：**"用扑克牌打 Roguelike——玩家是否愿意重复'选牌→得分→买牌→再来'这个循环？"**

原型出来后，开发者持续自测并据此继续完善。自测中的重复游玩可以说明开发者感受到吸引力，但不能替代目标玩家证据，也不能回答完整产品、市场和生产风险。理想的原型应以最低成本回答当前最关键的问题，并明确仍未知的部分。

## 5.2 原型的四个阶段

> **这一节解决什么问题：** 很多开发者一上来就打开引擎开始写代码——跳跃、移动、碰撞，三周后发现自己做了一个"能跑能跳的角色"但完全不知道好不好玩。本节提供一个严格分层的四阶段原型流程，确保每一步都在验证最核心的假设。

### 四阶段总览

```
纸上原型 (A)  ──→  Toy First (B)  ──→  Toy→Game (C)  ──→  Juicy (D)
 按问题设定         按问题设定           按问题设定           按问题设定
 "规则能产生      "核心交互无目标     "加上最简目标       "加上反馈层
  有趣的决策吗"     时好玩吗"          后循环闭合吗"      感觉对了吗"
```

| 阶段 | 产出 | 时间 | 核心问题 | 通过标准 |
|---|---|---|---|---|
| **A. 纸上原型** | 纸笔/骰子/筹码模拟核心规则 | 按规则复杂度 | 规则本身能产生有趣的决策吗？ | 你自己在模拟中感到乐趣或有意外发现 |
| **B. Toy First** | 核心交互（无目标、无胜利条件） | 按交互复杂度 | 单纯操作这个"玩具"本身有趣吗？ | 目标玩家主动重复、探索或形成可观察的兴趣 |
| **C. Toy→Game** | 核心交互 + 最简单目标 | 按目标复杂度 | 加上目标后，循环闭合了吗？ | 玩家能理解目标并自主重复循环 |
| **D. Juicy** | 核心交互 + 目标 + 反馈层 | 按反馈和实现成本 | 核心体验的"感觉"对了吗？ | 测试者的行为和表达支持当前体验假设 |

> **重要区分：** A-B 阶段属于 **Prototype 范畴**（单机制验证），C-D 阶段开始向 **MVP 收敛**（组装闭合循环）。B 阶段的 Toy 如果在目标玩家和预期体验范围内没有产生主动重复或有意义反馈，应先定位原因，再决定改实验、加入最小必要情境、换机制实现或废弃，不要把单一时长当成自动判定。

### 阶段 A：纸上原型（短周期示例）

**在打开游戏引擎之前，先用物理物件模拟核心规则。**

这是整个原型流程中**被跳过最多、也代价最大**的一步。你不需要编程就能发现：
- 规则是否产生有意义的决策（还是只有唯一最优解）
- 随机性和策略冲突是否让人兴奋（而不是让人困惑）
- 平衡问题在纯数学模型层面就已经存在（代码只会把错误数值乘以 1000 倍）

工具：骰子、索引卡、筹码、纸笔。*Practical Game Design* 建议：**"用纸和剪刀做第一个版本——它能让你专注于规则本身，不被视觉效果分心。"**

案例——*BattleHand Heroes* 的战斗系统重做：
- 原版问题：战斗缺乏深度，玩家总是选择最强的卡
- 纸上原型：设计了新的多层石头剪刀布卡牌系统，加上连击机制
- 数字翻译后才暴露的问题：卡太多（8 张→砍到 3 张）、数值太显眼（从卡面移除数字）、认知超载
- 结果是 UI 更干净、决策更少但更有意义

**如果你连纸上的规则都不好玩，写在代码里也不会变好玩。**

### 阶段 B：Toy First（短周期示例）

**"先做玩具，再做游戏。"**

Toy First 是 EGP 团队最重要的方法论贡献之一。它的核心洞察是：**对于适合单独验证交互的项目，在添加完整游戏目标之前，核心交互本身应能产生可观察的兴趣。** 你不一定需要一个"赢"的条件来验证玩家是否愿意和这个世界互动；但若价值依赖目标、情境、叙事或长期状态，就应把最小必要上下文纳入原型。

最经典的案例来自 *World of Goo* 的早期开发。Kyle Gabler 讲过一个故事：

> 当 EGP 团队第一次实现软泥的物理模拟时——还没有关卡目标、没有收集条件、没有任何"游戏"元素——只是几个软泥球在屏幕上互相连接，团队成员就开始不自觉地玩了起来。他们拉伸泥球、搭出形状、看着它们摇晃，在一段持续观察中仍然不想停下来。**这是这个案例中的通过信号，不是跨类型的时长门槛。**

相反，如果一个 Toy 在无目标状态下很快让目标玩家感到无聊或困惑，那么即使你加上精美的关卡、华丽的奖励、动人的叙事——核心交互本身也可能仍然空洞。此时应先检查是否缺少最小必要情境，再决定重做或停止，而不是机械套用时长。

**Toy 通过测试的朴素标准：**
- 目标玩家是否愿意在项目预设的观察窗口内主动重复或探索？
- 这个交互在你脑海里留下了"还想再试试"的冲动吗？
- 有没有某个瞬间让你自己都感到意外和惊喜？

*Practical Game Design* 在第 7 章中强调：**"先玩起来"比"先设计完美"重要。** 原型代码不需要整洁、不需要优雅、不需要可维护——它需要在与问题匹配的观察窗口内让测试者产生可解释的行为证据。

### 阶段 C：Toy→Game（按目标复杂度）

Toy 通过测试后，加上**最简单的目标**。关键原则：优先选择**天然目标**而非人为目标。

| 天然目标 | 人为目标 |
|---|---|
| 搭塔→向上堆得更高（物理系统自然提供） | "收集 100 个星星"（外部强加的计数器） |
| 移动物体→到达远处（移动系统自然提供） | "消灭 20 个敌人"（外部强加的计数器） |
| 消除物块→清空棋盘（消除系统自然提供） | "获得 3 星评价"（外部强加的评估） |

天然目标来自核心交互的内在逻辑——如果 Toy 本身是"搭东西"，那"搭得更高"就是一个天然会浮现的目标。人为目标是你在 Toy 外面贴的标签。优先使用天然目标，因为它们让玩家觉得"是我自己想这么做的"，而不是"游戏让我这么做的"。

目标加上后，检查三件事：
1. 从 Toy 到 Game 的过渡是否流畅？玩家是否在知道目标后并没有改变与 Toy 的互动方式？
2. 循环是否闭合？"玩→得到反馈→想再玩"这个闭环是否通畅？
3. **有没有"再玩一次"的冲动？** 这是最有价值的信号。

### 阶段 D：Juicy（按反馈和实现成本）

**反馈不是"抛光"——是原型的基础设施。**

EGP 团队的经验：震动、粒子效果、音效本身不是装饰，而是**让玩家知道自己的动作产生了什么后果**的必要信息通道。一个没有声音反馈的射击，玩家不知道自己是否命中了。一个没有屏幕震动的爆炸，感觉不像是爆炸。

但在原型阶段，Juicy 的投入有严格的纪律：

| 可以加的 Juicy | 不该加的 Juicy |
|---|---|
| 命中时的简短音效（感受得到后果） | 完整的背景音乐轨道 |
| 关键动作的粒子反馈 | 复杂的粒子系统参数调整 |
| 基本的屏幕震动（受击反馈） | 精确的震动曲线调整 |
| 关键动作的 2-3 帧动画 | 完整的角色动画系统 |
| 颜色变化（状态提示） | 复杂的材质和光照 |

**Juicy 的核心原则：只加"理解游戏需要的信息"，不加"让游戏变漂亮的装饰"。** 一个原型看起来丑没关系——但如果关键动作的反馈缺失，测试者根本不知道该看哪里、发生了什么。

### 四阶段实例：*World of Goo* 的原型演变

| 阶段 | *World of Goo* 对应情况 |
|---|---|
| A. 纸上原型 | 团队在白板上推演软泥的连接规则：多少条腿支撑、重力下如何断裂。发现"不稳定结构最有趣"这个核心 insight |
| B. Toy First | 实现了软泥球的物理模拟——无目标、无关卡。团队成员持续搭建各种结构并主动探索。**这是这个案例中的 Toy 通过信号** |
| C. Toy→Game | 加上一个简单的目标：用尽可能少的泥球把管道连接起来。物理 Toy 瞬间变成了有目的的解谜游戏 |
| D. Juicy | 泥球挤压音效、拉伸视觉效果、结构断裂的粒子。这些反馈让"物理感"从计算变成了体验 |

### 四阶段实例：*Celeste* 的 Game Jam 原型

*Celeste* 在最初的 Game Jam 中只有 4 天开发时间——这本身就是对四阶段模型的极限压缩验证：

| 阶段 | *Celeste* Game Jam 原型 |
|---|---|
| B. Toy First | 核心机制在第一天就做出来了：跳跃 + 空中冲刺。在没有任何关卡目标的情况下，仅仅在山壁上跳跃移动，开发者就感受到了一种独特的节奏感和掌控感 |
| C. Toy→Game | 用 Tile 编辑器搭了一个屏幕的关卡，目标：爬到山顶。一个屏幕就足够验证"跳跃+冲刺→爬山"这个核心循环是否成立 |
| D. Juicy | 角色像素动画、冲刺的拖尾粒子、落地灰尘、短促的音效——这些反馈在 Game Jam 时间内就完成了，因为它们是"理解角色状态"的必要信息 |

*Celeste* 从一个 4 天 Game Jam 原型成长为 Metacritic 92 分的年度游戏，靠的不是在原型阶段就做到完美，而是**在原型阶段就找到了"跳跃+冲刺"这个 Toy 的内在节奏感**。之后的 2 年开发都是在不同的关卡中探索这个核心交互的可能性。

## 5.3 "Fake It"原则及其边界

> **这一节解决什么问题：** 原型阶段应该花时间在什么上面、不应该花时间在什么上面。错误地理解了"Fake It"，会导致你在验证错误的东西。

### 什么可以（而且应该）Fake

EGP 团队最重要的工程经验：**用最快的方法实现效果，不要过度工程。**

| 可以 Fake 的 | 替代方案 |
|---|---|
| 光照 | 方向光 + 烘焙纹理 = 够了。不需要 PBR 渲染 |
| AI 行为 | 用假数据模拟决策、手动摆放行为序列。不需要行为树 |
| UI 动画 | 即时显示/隐藏。不需要缓动曲线和过渡动画 |
| 音效 | 免费音效库。不需要原创配乐 |
| 关卡内容 | 灰盒块。不需要任何美术资产 |
| 模式识别/推荐系统 | 硬编码的行为触发。不需要机器学习 |

Kyle Gabler 的名言：**"玩家看不到伟大工程——也不在乎。"** 测试者不会因为你的代码架构优雅而觉得游戏好玩，也不会因为没有反射探针而觉得游戏不好玩。

### 什么绝对不能 Fake

| 不能 Fake 的 | 原因 |
|---|---|
| **核心机制本身** | 这是你要验证的假设。如果你的核心是程序化生成关卡，那 procgen 算法就是被测对象——不能用手工地图书架去"模拟"程序化生成的效果 |
| **核心交互的即时反馈** | 玩家按下按钮→角色跳起，这中间的延迟、动画取消窗口、手感曲线——这些不能靠"假装很流畅" |
| **核心循环的平衡** | 如果核心循环涉及资源获取和消耗，你不能手工分配资源然后说"平衡没问题"——你需要在系统自动运行时观察真正的平衡行为 |

**"Fake"的是支撑系统（光照、AI、UI），不是被测假设本身。**

*Rules of Play* 中提到了一个相关但更哲学化的概念——"战略性造假"的伦理边界。在设计低保真原型时，你需要对自己诚实地区分两种"简化"：第一种是"我用灰盒代替最终美术"（合法简化），第二种是"我用手动操作来模拟系统自动化"（危险的自我欺骗）。后者让你误以为一个不可规模化的机制是可行的。

### "Fake It"实战案例：EGP 的短周期原型

EGP 团队曾用一个短周期完成原型；下面的时间分布是该案例的示例，不是所有项目的排期模板：

| 做的事情 | 时间 | Fake 了什么 |
|---|---|---|
| 核心机制代码 | 3 天 | 什么都没 Fake——这是被测物 |
| 关卡布局 | 1 天 | 灰盒块代替最终美术；手工摆放代替程序化生成 |
| 角色动画 | 半天 | 只有 2-3 帧关键帧；无过渡动画 |
| UI | 半天 | 纯文字 + 色块。无图标、无过渡 |
| 音效 | 半天 | 免费音效库的 5 个音效循环用 |
| 光照/材质 | 半天 | 一个方向光 + 纯色材质 |

在这个案例中，收尾测试若支持“核心机制好玩”，短周期就达成了获取信息的目的；若不支持，也只承担了受控的实验成本，而不是先做完一套精美但不成立的产品。

## 5.4 交付物层级：Prototype → MVP → VS → Demo

> **这一节解决什么问题：** 混淆交付物层级是独立游戏最常见的浪费原因——用做 VS 的心力做原型，或者把 Demo 当成 VS 提交给投资人。本节给每个层级一个清晰的"工作合同"：它回答什么问题、做什么、给谁看。

### 四层对比表

| 维度 | **Prototype（原型）** | **MVP** | **Vertical Slice（VS）** | **Demo（试玩版）** |
|---|---|---|---|---|
| **回答的问题** | "这个机制能跑通吗？" | "应该继续做吗？" | "能以最终品质做出来吗？" | "能让玩家/媒体感兴趣吗？" |
| **范围** | 单一机制，可能不完整 | 核心循环 + 基础 UI，可从头玩到尾 | 一个完整截面（1 个关卡/回合） | 面向公众的精选片段 |
| **品质要求** | 粗糙，内部使用 | 可玩但不抛光 | 接近最终品质 | 可混合品质 |
| **参考时间** | 按假设和实现成本 | 按外部可玩范围 | 按代表性风险和品质要求 | 视营销需要 |
| **受众** | 你自己 + 团队成员 | 外部测试者（匿名玩家） | 团队 + 投资人 | 玩家、媒体、发行商 |
| **对应步骤** | Step 3（按假设分阶段） | Step 3 的阶段性产出 | Step 5 | Step 6（营销或测试动作） |
| **编程类比** | 草稿代码片段 | 功能完整的 v0.1 内部版 | 高保真可演示的功能模块 | 面向公众的 Beta / 宣传片 |

### 层级混淆的典型代价

| 错误做法 | 后果 |
|---|---|
| 用做 VS 的心力做原型 | 投入大量时间做了精美的"原型"，但核心机制一个假设都没验证。如果机制有问题，前功尽弃 |
| 把 Demo 当 VS 提交给投资人 | 投资人看到的是精选的"亮点集锦"，不能回答"管线能不能支撑规模化生产"——这会导致融资后生产崩盘 |
| 跳过 MVP 直接做 VS | 在核心循环还没验证通过的时候就开始做高保真内容。万一核心循环不好玩，所有 VS 资产都是浪费 |
| 把 Prototype 代码直接当 MVP 继续开发 | *Practical Game Design* 第 7 章明确警告：**"不要从原型代码演化成最终游戏。"** 原型代码为验证速度而写，不为可维护性而写。验证通过后，应该从零搭建生产级项目结构 |

> **关键理解：Prototype 和 MVP 不是两个独立交付物，而是同一条路径上的活动与产出。** Step 3 的前半段（A-B 阶段）在构建 Prototype——单机制、粗糙、快速试错。后半段（C-D 阶段）将验证通过的 Prototype 向 MVP 收敛——加目标、加反馈层，组装成可被外部玩家理解的闭合循环。Step 3 结束时交给玩家测试的，就是这个 MVP。

全书推荐的 Step 1-3 应设定一个项目自己的时间与资源预算，并在预算消耗到预设检查点时复盘。若单机制验证长期不收敛，不应只看日历决定 Kill：先判断是实验设计、实现方式、玩家分群、范围还是价值主张的问题；在低成本替代方案和重新验证仍不支持核心假设时，再回到 Step 1 或停止。

## 5.5 Playtest 的科学方法

> **这一节解决什么问题：** "找几个朋友试玩一下"是最常见的测试方式，也是最无效的方式——朋友会礼貌地说"挺有意思的"，而你需要的是"第 17 秒的时候你皱眉头了，为什么？"。本节提供从招募到提问的完整科学流程。

### 核心原则

Playtest 的目的不是"收集意见"，而是**观察行为**。*Rules of Play* 的警告最直白：**"设计文档在生产开始的那一刻就过时了——游戏总是会给你惊喜。"** 你无法从文档中预测玩家会做什么，你必须看。

*Practical Game Design* 第 13 章补充了一个关键框架：**Playtest 有层次。** 原型阶段（Step 3）的测试目标是"核心机制是否成立"，打磨阶段（Step 7）的测试目标是"体验是否完整"。不同阶段需要不同的样本量、测试方法和提问策略。

### 招募：找谁测

| 测试者类型 | 优势 | 劣势 | 适用场景 |
|---|---|---|---|
| **队友/同事** | 快速、免费、专业知识 | 极度偏见（知道你的设计意图） | 仅用于 A-B 阶段的内部试玩 |
| **朋友/家人** | 容易找到 | 会礼貌地说"不错"——这是无用的信息 | **不推荐用于任何正式验证** |
| **不认识的目标玩家** | 无偏见、真实的困惑和放弃 | 需要主动招募 | 当问题需要外部或目标玩家证据时使用 |
| **付费测试者** | 有专业反馈习惯、Think-aloud 能力 | 成本高 | VS 阶段及之后 |

原型阶段可以从少量目标玩家开始，以发现明显困惑和生成假设；样本量不是跨项目通用的“最小有效值”。

Jakob Nielsen 的“5 个用户”论点可以作为发现明显可用性问题的低成本起点，但它不能直接验证游戏乐趣、长期留存或市场需求。关键是找具有目标受众特征、且不参与开发的人；如果要比较版本，需记录样本是否重复、玩家分层和测试条件。多轮小样本有利于快速发现问题，但不自动优于一次更大或更具代表性的测试。

### 测试：怎么做

测试中最难的事，不是让玩家玩——是**闭嘴**。

| 你绝对不能做的 | 你应该做的 |
|---|---|
| 解释玩法（"你要先按这个再按那个"） | 说"请随意试试看"，然后闭嘴 |
| 在玩家困惑时提示 | 记录困惑发生的时间点（精确到秒），测试后再问 |
| 在玩家问"我应该做什么"时回答 | 记下这个问题。如果 5 个人中有 3 个在同一个地方问同样的问题——这就是你要修的地方 |
| 表现出失望或焦虑（"啊不是那样的……"） | 面无表情。你的微表情会影响玩家的行为 |

*Practical Game Design* 的"假装你不是开发者"原则非常有效：**告诉测试者"这是一个朋友做的游戏，我就是帮个忙"**——这会让测试者更愿意给出诚实（甚至是刻薄）的批评。

关键行为信号（比语言更真实）：
- 玩家在哪里停下来？停下来多久？
- 玩家操作前犹豫不决的位置
- 玩家反复尝试同一个操作失败的位置
- 玩家露出微笑或说"哈！"的位置
- 玩家提前退出的位置（和退出前做了什么）
- **玩家是否主动"再玩一次"？**

### 提问：问什么、怎么问

测试结束后，提问的顺序和措辞决定了你获得的信息质量。

| ❌ 无效提问 | ✅ 有效提问 |
|---|---|
| "你觉得好玩吗？" | "哪个部分最无聊？" |
| "你喜不喜欢？" | "如果让你删掉游戏里的一个东西，你会删什么？" |
| "有没有哪里不好？" | "你在哪里最想退出？为什么当时没退？" |
| "操作感觉怎么样？" | "在玩的过程中，有哪次你按了按钮但不确定有没有发生什么？" |

提问的三个原则：
1. **问具体，不问抽象。** "哪个部分最无聊"通常比"你觉得好玩吗"更容易提取可行动的信息。
2. **问负面，不问正面。** 正面评价不需要你引导——玩家如果真的喜欢，会主动说。你的任务是挖出他们不舒服但不好意思说的地方。
3. **问行为，不问态度。** "你在那里做了什么？"比"你觉得那个地方怎么样？"更可靠。玩家对自己行为的描述可能不准确，但至少比经过社交修饰的"态度"更接近真相。

早期理解检查（可借鉴“前 15 秒”测试思想）：把游戏放在一个完全没听过介绍的人面前，观察他何时看到关键信息、何时做出第一次有效操作、何时理解当前目标。15 秒可以是动作游戏的一个观察窗口，但不是所有类型的硬门槛。

### 早期理解检查：玩家知道当前要做什么吗

把游戏放在一个完全没听过任何介绍的人面前，记录他第一次主动行动、第一次询问和第一次正确解释分别发生在什么时候。

如果玩家在项目预期的理解节点前持续没有有效行动，或反复询问而无法从反馈中形成假设，FTUE 可能存在结构性问题。先区分是输入、信息、目标、情境还是玩家经验造成的，再决定是否简化或增加提示。

案例——*Celeste* 的原型说明了发现式引导在动作游戏中的价值：玩家可以通过角色反馈和空间布局逐步发现操作。但这不是“好的原型不需要解释”的普遍结论；需要显式说明、无障碍提示或复杂规则的项目应把这些纳入测试。

### 每轮只改 1 件事

为了保持因果可解释性，单轮实验最好只改变一个主要变量；如果需要同时修改多个相互依赖的变量，应把它们视为一个实验包并记录原因、预期影响和对照条件。

为什么？因为如果你同时改了跳跃高度、敌人速度和关卡布局，而测试结果变好了——你不知道是哪个改动起了作用。你可能保留了一个实际上让体验变差的改动，只是因为另一个改动把它遮盖了。

> 一次改很多件事会降低因果可解释性，但在设计空间探索阶段并非绝对禁止；关键是不要把多变量结果误写成某一个改动的证明。

### Playtest 记录模板

每次测试后填写——标准化记录有助于积累可复用的设计证据和判断经验。

| 字段 | 示例 |
|---|---|
| **测试编号** | PT-003 |
| **日期** | 2024-03-15 |
| **测试者** | 匿名 #2（目标玩家：喜欢解谜游戏） |
| **原型版本** | v0.3（C 阶段：加上了收集目标） |
| **测试时长** | 预测 15 分钟 → 实际 6 分钟 |
| **首次理解玩法耗时** | ~45 秒（可接受） |
| **困惑/停顿位置** | 00:32 ↔ 管道放置操作（试了 3 次才放对） |
| **放弃/提前退出位置** | 06:00（说"不太确定要做什么了"） |
| **微笑/"哈！"位置** | 01:15（第一个结构搭好后摇晃的样子） |
| **最有价值的一句原话** | "一开始那个摇摆的感觉挺好的，但后面就一直在重复……" |
| **本轮改了什么（1 件事）** | 把收集目标从"10 个球"改为"把 3 个球都接到管道" |
| **下一轮改什么** | 管道连接的视觉反馈（测试者表示"不确定有没有接上"） |
| **结论** | 目标改进方向正确（测试者理解了要做什么），但操作反馈不足导致中期失去动力。继续迭代反馈层。 |

## 5.6 双螺旋节点：原型结果驱动设计回流

> **这一节解决什么问题：** 原型验证结束后，测试结果需要转化为下一项低成本行动。不要让“再改改试试”变成无边界的投入，也不要把流程写成禁止重复实验的单行道。

原型验证是双螺旋模型中**设计线与原型线交汇最密集的节点**。测试结果不只是告诉你"这个原型怎么样"——它让你重新审视**之前的所有设计假设**是否正确。

| 测试结果 | 诊断 | 行动 |
|---|---|---|
| 玩家无法在预期节点理解核心目标 | 可能是表达、输入、情境或机制问题；不能仅凭轮数判断概念失败 | 修改表达或实验边界，做针对性复测；如果价值主张仍有潜力，可以换一种机制实现 |
| 玩家理解玩法但不愿继续，且反馈显示核心价值主张没有出现 | 核心体验假设可能不成立，但要先排除招募、引导、实现和测试条件问题 | 更换机制实现或缩小假设后复测；多种低成本实现仍失败时，回流 Step 1 或停止 |
| 玩家自发完成与项目相关的循环，主动继续或能解释其价值 | 当前假设得到支持，但仍可能有未验证的长期风险 | 进入 Step 4，列出剩余未知数并规划相应的系统/内容验证 |
| 证据不足、不同玩家反应分化明显 | 结论尚不足以支持下一阶段投资 | 增加目标玩家分层、补充定性观察或设计新的对照实验 |

> **这不是固定的三个出口，而是一组诊断分支。** 每个测试结果都应对应下一项低成本行动：可能是修正表达、替换机制实现、缩小实验边界、回到 Step 2/Step 1，或在证据不足时继续做针对性原型。重复原型不是拖延的借口，但也不应被流程禁止。

## 5.7 Kill Criteria：什么时候停下来

> **这一节解决什么问题：** 独立开发者最致命的陷阱是沉没成本——在一个已经验证不可行的机制上继续做，因为"已经花了这么多时间"。Kill Criteria 是你在进入原型验证之前就与自己签订的"退出合同"，它的唯一功能是在你已经失去理性判断能力时，替你做出停止的决策。

### Kill Criteria 决策表

| 触发条件 | 含义 | 行动 |
|---|---|---|
| 在预期理解节点前，多批目标玩家仍无法理解核心目标 | 可能是表达、输入、情境或机制问题；需先定位断点，不能仅凭轮数判断概念失败 | 修改表达或实验边界，做针对性复测；若多种低成本实现仍失败，再回 Step 1 或停止 |
| 多批目标玩家在明确体验时长内持续不愿继续，且定性反馈显示核心价值主张未出现 | 核心体验假设可能不成立，但要排除招募、引导、实现和测试条件问题 | 更换机制实现或缩小假设后复测；证据仍持续否定时 Kill |
| Devlog/GIF/短视频互动很弱 | 这是传播、素材或渠道信号，不能直接证明没人需要游戏 | 检查曝光基数、受众、素材和渠道；与试玩、访谈和页面漏斗交叉验证 |
| 一个核心机制长期验证仍未收敛 | 说明问题边界、变量或实验条件可能不清楚，也可能是机制本身高风险 | 拆成子假设，明确每轮证据和决策价值；当继续实验的收益低于成本时停止或转向 |

### Kill Criteria 的使用纪律

Kill Criteria 不是"建议"——是你与自己的合同。如果你在进入原型阶段前没有写下这些条件，你会在投入足够多时间后说服自己"再给一点时间"。

在编程中，你不会在 100 个测试用例全部失败后还声称"代码差不多对了"。Kill Criteria 就是游戏设计的测试用例失败条件——**没有什么"差不多"。**

### 按检查点安排的节奏示例

如果项目选择按周安排 Step 3 的原型验证，可使用下面的顺序作为示例；实际阶段长度和是否并行应由假设与证据决定：

| 周 | 阶段 | 关键动作 |
|---|---|---|
| 第 1 周 | 纸上原型（A） | 用纸笔验证核心规则，确认规则层面存在有趣决策 |
| 第 2 周 | 数字原型（B-C） | Toy First → Toy→Game。找 1-2 个队友做内部快速测试 |
| 第 3 周 | Juicy + 内部迭代（D） | 加反馈层，做 1-2 轮内部快速迭代 |
| 后续检查点 | 外部测试 | 找具有目标受众特征且不参与开发的玩家做正式测试；同时可发布 Devlog / GIF / 短视频，区分传播信号与玩法证据 |

## 实操清单

- [ ] **进入数字原型前建立版本控制（Git + LFS）和异地备份。** 这是基础设施级要求——如果原型阶段丢失了代码，你连"验证了什么"都说不清楚
- [ ] 根据问题选择纸上原型、数字原型、最小情境和反馈层；跳过低成本验证前，确认已经记录了为什么以及替代证据是什么
- [ ] 找不认识的目标玩家测试（从少量开始，根据假设和玩家分层增加）。先统一测试条件，再观察他们在哪里困惑、停顿、放弃或主动继续
- [ ] 每轮记录主要改变的变量；如果一次修改多个相互依赖的变量，写明实验包和对照理由
- [ ] 短周期节奏可以作为动作游戏等项目的参考；复杂系统或叙事项目按最大不确定性调整阶段长度，并在每轮结束时做证据复盘
- [ ] 可以发布 Devlog / GIF / 短视频观察传播信号，但不要把无人问津单独当作需求结论
- [ ] 每轮测试后填写 Playtest 记录模板（见 5.5 节），积累结构化数据而非模糊印象
- [ ] B 阶段的 Toy 如果在目标玩家和预期体验范围内没有产生主动重复、探索或有意义反馈，先记录失败原因；再决定改实验、加入最小必要情境、换机制实现或废弃，不把“10 分钟”当成跨类型硬门槛

## 骨架-血肉-灵魂自查

本章对应原型验证阶段，三层框架的侧重如下。使用以下问题对照你的原型成果进行自查：

### 骨架层（机制与系统）——本章重点

- [ ] 当前原型是否包含了验证假设所需的最小情境（有些项目适合无目标 Toy，有些项目必须加入目标、资源或叙事语境）？
- [ ] 目标循环层级是否明确？玩家的行动是否得到可理解的后果，并影响后续选择、状态、信息、空间/叙事进展或情绪？
- [ ] 核心规则是否产生有意义的决策——还是只有唯一最优解？
- [ ] Kill Criteria 是否在进入原型前就已明确写下——还是你正在"边走边定义"？

### 血肉层（表现与反馈）

- [ ] 关键动作的反馈是否即时、清晰——测试者是否知道自己做了什么、产生了什么后果？
- [ ] "Fake It"原则是否被正确使用——支撑系统简化了，但核心机制没有被"假装"？
- [ ] Juicy 层是否只加了"理解游戏需要的信息"——没有为了"让原型看起来更好"而过度投入？
- [ ] 视觉/听觉反馈是否统一——还是各种临时资源拼凑、风格混乱？

### 灵魂层（情感与体验）

- [ ] 测试者的情绪反应是否与 Design Pillars 的体验目标一致？如果 Pillar 是"紧张"，测试者是否真的看起来紧张（而非困惑或无聊）？
- [ ] 测试者是否主动说"可以想象这个做出来会很好"——还是在你的引导下勉强点头？
- [ ] 测试结束后，测试者是否主动询问"什么时候能玩到更多"？这是最真实的兴趣信号
- [ ] 这个原型给你自己的感觉是什么——兴奋？平淡？还是"做都做了，总得试试"？对自己的诚实比对测试者的诚实更难，但更重要

---

**本章在七步流程中的出口：** 证据足以支持当前体验假设，且主要未知数已列出 → 进入第 4 步设计深化；表达或实现有问题但价值主张仍有潜力 → 修改后重复原型；需要重新定义目标、Pillars 或范围 → 回流第 2 步；多种低成本实现都无法支持核心价值主张，且继续实验的决策价值很低 → 回流第 1 步或 Kill。没有固定的原型轮数，只有必须写清楚的假设、证据和下一步。
