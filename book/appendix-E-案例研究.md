# 附录E：案例研究

> **本附录的定位：** 前九章建立了方法论框架——七步流程、双螺旋模型、Kill Criteria 体系、骨架-血肉-灵魂三层模型。本附录将这些工具作为**分析透镜**，投向四个真实的独立游戏项目：三个成功的、一个失败的。每个案例的结构相同——**背景 → 七步映射 → 关键决策与 Kill Criteria → 方法论启示**——让你看到抽象框架如何在真实开发实践中显现、变形或被无视。

> **阅读建议：** 四个案例可以按顺序读，也可以根据你的兴趣跳读。如果你正在做一个机制组合型游戏，先看案例 1（Balatro）。如果你在做 solo 开发或担心 burnout，先看案例 2（Stardew Valley）。如果你在 Game Jam 里找到了一个原型想把它做完，先看案例 3（Celeste）。如果你怀疑自己的项目可能已经在不该走的方向上走了太久，**直接看案例 4**。

## 案例1：Balatro — 扑克机制 × Roguelike 的加法创新

> **核心方法论关键词：** 游戏域内回收、加法创新、"XX meets XX"公式、Toy First、水平切片、机制-市场契合

### 1.1 背景：一个加拿大 IT 运维的副业项目

LocalThunk 是一个化名——开发者选择保持匿名。他有一份全职 IT 工作，住在加拿大，2021 年开始用 Love2D 框架业余时间做一款"扑克 Roguelike"游戏。他没有团队，没有融资，没有发行商。2024 年 2 月 20 日，Balatro 以 $14.99 买断制正式发售，首月销量突破 100 万份，Metacritic 90 分，成为当年独立游戏的现象级作品。

从方法论角度看，Balatro 是**游戏域内回收**的教科书：它的每一个基础零件都是已知的——扑克规则、Roguelike 构筑、修正器叠加——但 LocalThunk 找到了三者的接口契合点，让它们产生了 1+1+1 > 3 的效果。

### 1.2 七步流程映射

Balatro 不是严格遵循本书方法论开发的（LocalThunk 大概率没有读过本书），但如果我们用七步流程作为回溯分析透镜，它的实际开发路径与本书方法论惊人地一致：

| 步骤 | Balatro 的实际行为 | 方法论对标 |
|------|-------------------|-----------|
| **① 概念孵化** | 受《幸运房东》（Luck be a Landlord）启发，想做一个"在已知规则上叠加 Roguelike 修正器"的游戏。扑克牌型是候选之一——因为牌型鉴定系统天然适合作为"战斗判定"。 | 游戏域内回收（来源 1）。"扑克 × Roguelike" = 经典 XX meets XX 公式。 |
| **② 一页纸概要** | 未写出正式的 One-Pager，但概念在脑内高度聚焦：Core Loop = 从手牌选≤5 张组成牌型 → 筹码×倍率得分 → 获得金币 → 买/升级小丑牌 → 应对下一轮更高的分数门槛。Scope 极窄：只有扑克牌、小丑牌、塔罗牌、星球牌、代金券几种卡牌类型。 | 符合一页纸精神：Core Loop 极度清晰，Scope 被严格约束在"牌"这个单一交互媒介内。 |
| **③ 原型验证** | 用 Love2D 做了极简原型——纯文字+数字界面，无动画、无音乐、无精美 UI。原型只有一个目的：验证"选牌→得分→买牌→再来"这个循环是否让人停不下来。测试者是他自己。他玩了 100 小时停不下来——这是最诚实的原型数据。 | Toy First 的经典执行。原型只验证一个假设："扑克牌型 + 修正器组合的循环有让人重复的引力吗？"——答案来自开发者自己玩 100 小时还不想停。 |
| **④ 设计深化** | 未写正式的 Ten-Pager，但隐式完成了范围估算：核心系统的"牌"约 150 种（含小丑、塔罗、星球、幻灵），每张牌只是一个数据条目（名称 + 效果 + 美术），不是手工关卡。这意味着内容生产的单位成本极低。 | 内容类型天然"可模板化"——每张牌 = 一个数据行。这是 Balatro 作为 solo 项目可行的结构基础。 |
| **⑤ 垂直切片** | Balatro 是**水平切片**（HS）的经典案例——不需要做垂直切片。因为其核心价值在系统深度而非逐关体验。没有"第一关""第二关"的概念——所有内容都是平行的"牌"数据条目。HS 的验证对象是：所有系统（小丑牌、塔罗牌、星球牌、代金券、盲注等级）协同运行时，是否能持续产生有趣的组合决策？ | HS 而非 VS 的正确选择。HS 验证了系统间交互的深度和长期可重玩性。游戏做 1 张牌和做 150 张牌的"单位生产成本"几乎相同——这是 HS 适用的核心条件。 |
| **⑥ 生产开发** | 生产阶段的核心工作是填充卡牌内容、调数值、做美术（像素化的牌面设计 + 复古 CRT 滤镜美学）、写音乐。设计在原型阶段就已冻结——"牌"这个交互媒介没有扩展为"再加一个战斗系统""再加一个地图探索"。 | 教科书式的设计冻结。LocalThunk 的纪律在于：他知道这款游戏是"牌"，不是"牌+别的"。 |
| **⑦ 迭代打磨** | 发售前进行了多轮外部 playtest。打磨重点是：数值平衡（不同小丑牌的组合不能有过强的唯一最优解）、UI 可读性（牌面信息在海量修正器叠加时仍然清晰）、视觉风格（霓虹复古 + CRT 扫描线的催眠感）。 | 数值打磨贯彻"无唯一最优解"铁律。UI 打磨解决了"信息过载但仍然可读"的核心挑战。 |

### 1.3 关键设计决策与 Kill Criteria 审视

**决策一：不发明新机制，只做加法组合。**

LocalThunk 没有试图创造一个前所未有的玩法。他拿了三个已知元素——扑克牌型判定（德州扑克规则）、Roguelike 构筑（每局不同的 build）、修正器叠加（小丑牌改变牌型行为）——找到了它们之间的接口契合点。这个决策让 Kill Criteria 第 6 条（原型可行性）自动通过：因为每个零件都是已知的，他可以在 1-2 周内做出可玩原型。不需要"先做完美术才能测试"。

**决策二：用水平切片代替垂直切片。**

Kill Criteria 第 5 步（管线可行性）的标准答案是"做两个完整截面到最终品质，第二切片的耗时收敛"。但 Balatro 天生不存在"截面"的概念——它没有关卡。这是方法论的一个重要提醒：**Kill Criteria 的具体形态因游戏类型而异。** 系统深度驱动型游戏（卡牌、策略、Roguelike）的"管线可行性"验证标准应该是"系统完整度"和"单位内容生产成本"，而非"第二切片耗时收敛"。

**决策三：保持匿名，隔绝外部噪音。**

LocalThunk 在整个开发过程中保持匿名，不与社区过度互动。这个"反市场线"决策看似违背了第 2.4 节的建议（"从 Step 1 开始做市场验证"），但实际上是一种对独立开发者心理健康的有意保护——早期市场反馈中的噪音（尤其是来自非目标玩家的负面反馈）可能动摇设计信心。等游戏接近完成、品质足以准确传达体验时再公开，是一种合法的节奏选择。注意：这并不意味着他跳过了市场验证——他对竞品（《幸运房东》《Slay the Spire》《杀戮尖塔》等）的深入研究本身就是一种被动的市场验证。

### 1.4 Kill Criteria 总结表

| 步骤 | 实际行为 | Kill Criteria 状态 | 方法论文本 |
|------|---------|-------------------|-----------|
| ① 概念孵化 | 明确卖点：扑克+肉鸽。目标玩家：喜欢构筑深度但想要更短单局的策略爱好者。 | ✅ 通过（卖点清晰、受众明确、有竞品参照） | "XX meets XX"公式降低概念风险 |
| ② 一页纸概要 | 隐式完成：Core Loop 极度清晰，Scope 被天然约束在"牌"内 | ✅ 通过（Scope 可控、Core Loop 可读） | 牌作为唯一交互媒介 = 自然 scope 约束 |
| ③ 原型验证 | 极简原型（纯文字+数字），开发者自测 100 小时不释手 | ✅ 通过（3 轮无趣未触发——相反，100 小时不想停） | Toy First 的极端版——"我自己停不下来"是比任何问卷都诚实的数据 |
| ④ 设计深化 | 隐式完成：内容 = 数据条目，单位生产成本极低 | ✅ 通过（Scope Budget 天然可收敛） | 数据结构驱动的内容生产 = 最低的单位边际成本 |
| ⑤ 垂直/水平切片 | 水平切片：所有系统协同运行，验证组合深度 | ✅ 通过（HS 验证了系统交互深度） | HS 而非 VS 的正确选择——游戏类型决定切片策略 |
| ⑥ 生产开发 | 设计冻结，仅填充卡牌内容和调数值 | ✅ 通过（设计未漂移、内容可复用） | 纪律："牌"不是"牌+别的" |
| ⑦ 迭代打磨 | 多轮外部 playtest，数值、UI、视觉打磨 | ✅ 通过（体验一致、无核心 Bug） | 打磨重点：信息过载下的可读性 |

### 1.5 方法论启示

**"XX meets XX"不是偷懒，是降低不确定性的策略。** 当一个创意由两个以上的已知元素组合而成时，你不必须从零验证每一个零件是否有趣——零件已经被市场验证过了。你需要验证的是"组合"是否成立。这个验证的成本远低于从零发明。

**游戏类型决定切片策略。** 系统深度驱动型游戏应该选择水平切片（HS），内容驱动型游戏应该选择垂直切片（VS）。混淆两者会导致在错误的维度上测试错误的问题。Balatro 如果被强制套用 VS 方法论，会浪费大量时间在"做一个高品质的'第一局'截面"上——而它的核心风险根本不在那里。

**Core Loop 清晰到"一句话能说完"是最大的竞争力。** Balatro 的核心循环——"从手牌选牌组成牌型，触发小丑牌修正器，得分，买牌，再来"——可以在 15 秒内向任何人解释清楚。核心循环的简洁不是设计的"简化"，而是设计的"提纯"。每一步设计深化都在加规则，但每一步都在问："这条规则让核心循环更有趣了，还是让它更复杂了？"

## 案例2：Stardew Valley — 单人开发者的七年回溯分析

> **核心方法论关键词：** 竞品差评驱动创新、设计冻结、骨架-血肉-灵魂三层内聚、单人开发的时间管理、Burnout 预防

### 2.1 背景：一个毕业生用四年回应一款自己热爱的游戏

2012 年，Eric Barone（网名 ConcernedApe）从华盛顿大学计算机系毕业。他没有找工作。他决定一个人做一款游戏——一款他从小就热爱的《牧场物语》类型游戏，但要做到"现代玩家想要的样子"。

他的起点本质上就是本书 3.3 节所描述的"从竞品差评中找机会"：他是《牧场物语》的忠实玩家，但他对这个系列后来的作品感到失望——他觉得系列"丢掉了最初让游戏感人的东西"。游戏变得更复杂了，但那种在小镇上日常生活的宁静感和归属感变淡了。

四年后，Stardew Valley 以 $14.99 发售。截至 2026 年，全球销量超过 4100 万份。一个人用四年做出来的游戏，成为了该品类（农场模拟 RPG）的定义者。

但 Barone 本人反复在采访中说：**"我不推荐任何人复制我的路径。"** 这个案例的价值恰恰在于——当我们用本书方法论回溯分析，可以看到哪些是他做对了的（方法论支持的），哪些是他幸运地"侥幸通过"的（Kill Criteria 本来应该停掉这个项目的地方），以及哪些是独立开发者应该避免的。

### 2.2 七步流程映射

| 步骤 | Stardew Valley 的实际行为 | 方法论对标 |
|------|--------------------------|-----------|
| **① 概念孵化** | 对标《牧场物语》，从"竞品差评"中提炼改进方向：1) 更深的农场自定义；2) 更丰富的村民故事线；3) 采矿战斗增加节奏变化；4) 保留田园生活的宁静核心。市场假设："怀念牧场物语式体验但觉得现有作品不够深度的 PC 玩家"。 | 竞品分析驱动。目标受众极其精准——"喜欢牧场物语但不满足的人"。这个群体当时确实存在一个大缺口。 |
| **② 一页纸概要** | Barone 没有写正式的设计文档，但他的 Core Loop 在开发之初就极其清晰：`起床 → 浇水/收获 → 探索/社交/采矿/钓鱼 → 回家睡觉 → 第二天`。三条核心线（农耕、采矿战斗、村民社交）在第一年就全部定义完成。 | Core Loop 的自然节律——"一天"的 13 分钟循环——是这款游戏的结构基础。 |
| **③ 原型验证** | **这是一个方法论红灯。** Barone 没有做最小原型——他几乎是从第一个像素开始就在做"最终游戏"。他花了约两年才有一个自己能完整玩的版本，期间没有外部 playtest。如果按照本书的 Kill Criteria——"连续 3 轮玩家无法理解核心玩法 → 停止"——这个项目在 Step 3 就会被杀死。 | ⚠️ Kill Criteria 会杀掉这个项目。这是本书方法论需要承认的边界案例。 |
| **④ 设计深化** | 未写正式 Ten-Pager。但隐式范围界定在第一年就完成了——三个核心系统 + 内容填充（更多作物/矿物/NPC），不扩展新系统。 | 隐式 Scope Budget 成立，因为 Barone 有极强的纪律——他不在开发中途加新系统。 |
| **⑤ 垂直切片** | 没有独立的 VS 阶段。但大约开发两年后，他有了一个"从春季第一天到夏季第一天"的完整可玩截面——这本质上就是一个自然生长出来的垂直切片。 | 虽然当时没有"测产能"的意识，但"能玩通一个季节"这件事客观上验证了管线可行性。 |
| **⑥ 生产开发** | 后两年是密集的内容填充：画像素图、写 NPC 对话、设计节日事件、调数值。设计在前两年完成后从未漂移——没有在中途加入"宠物对战"或"王国建设"。 | 本书第 8 章用 Stardew 作为"设计冻结"的正面案例，不是巧合。四年的开发中，核心系统始终是那三条，变化的是内容的深度而非广度。 |
| **⑦ 迭代打磨** | Barone 在发售前做了约 6 个月的打磨。他自己玩了无数遍，修 bug、调数值、补对话、优化 UI。发售后继续发布免费内容更新（1.5 版本增加了姜岛等大量内容）。 | 单人打磨的效率取决于开发者对自己游戏的"玩家视角"切换能力。Barone 的优势是——他真的爱玩这个类型的游戏。 |

### 2.3 Kill Criteria 为什么应该杀掉 Stardew Valley —— 以及为什么这个判断是对的

让我们诚实地面对一个方法论难题：如果 Eric Barone 在 2012 年找到一位遵循本书方法论的导师，这位导师大概率会建议他"先做一个 4 周的原型，找 5 个玩家测试，如果没人觉得好玩就换项目"。而 Barone 前两年的开发周期里，既没有外部测试，也没有可以独立运行的"最小原型"。

**Kill Criteria 会触发的环节：**

| Kill Criteria 条件 | Stardew 在 Step 3 的实际状态 | 触发结果 |
|-------------------|---------------------------|---------|
| Step 3: "连续 3 轮外部 playtest 无趣" | 前两年没有外部 playtest | 无法评估——但如果强制执行，项目可能被误杀 |
| Step 1: "Scope 严重超出资源" | 一个人开发一个需求 40+ 小时完整内容的农场 RPG | ⚠️ 从预算角度看，这明显超纲 |
| Step 3 时间上限: 60 天 | Barone 花了约 2 年才做出第一个可玩版本 | ⚠️ 远超时间上限 |

**但 Stardew Valley 最终成功了。这不是 Kill Criteria 错了，而是 Stardew 满足了一组极为罕见的前提条件：**

1. **开发者的"玩家身份"与"目标玩家身份"完全重合。** Barone 就是这个游戏的目标玩家——他不需要找外部测试者来验证"好不好玩"，因为他在为自己做一款自己想要的游戏。这种情况极度罕见——大多数独立开发者不是自己游戏的"目标玩家"（你可能是一个 25 岁的男性程序员，但你在做一款面向 12 岁女孩的换装游戏）。

2. **竞品差评是精确的导航地图。** Barone 不是在"探索未知领域"——他是在"修复一个已知产品线中已知的问题"。他知道《牧场物语》哪里做得好，哪里让粉丝不满。这个"已知问题集"替代了原型验证的部分功能。

3. **Core Loop 的节律感天然存在。** 农场模拟的 Core Loop 不需要被"发明"——《牧场物语》已经验证了"一天"的循环结构。"醒来→做事→睡觉"这个节奏是人类身体的本能节律，它在直觉层面就是成立的。

**Kill Criteria 的正确回应不是"所以 Kill Criteria 没用"，而是"Kill Criteria 需要配套的豁免条件"。** 如果你能同时回答以下三个问题为"是"，你可以考虑豁免 Step 3 的激进 Kill Criteria：

- 你自己就是这个游戏的铁杆目标玩家吗？（不只是"喜欢这个类型"——而是"如果别人做了这款游戏，你会第一时间买"）
- 你是在"修复一个已知品类中的已知缺陷"，还是在"探索一个无法对标的新方向"？（前者风险远低于后者）
- 你能承受 2 年没有收入、没有正反馈的开发周期吗？（Barone 能，因为他的生活成本极低，且有伴侣支持）

三条答案都是"是"的人，全世界可能不超过 1%。如果你不在其中，**Kill Criteria 仍然是最理性的决策工具。**

### 2.4 骨架-血肉-灵魂三层分析

**骨架（机制与系统）：**

Stardew 的骨架由三条互相咬合的核心循环线组成：

```
农耕线：开垦 → 播种 → 浇水 → 收获 → 售卖/加工 → 金钱 → 购买种子/升级工具 → 回到农耕
采矿战斗线：探索矿洞 → 战斗 → 获得矿石/宝物 → 升级工具/建造设施 → 回到农耕
社交线：送礼物 → 增加好感 → 触发事件 → 解锁新内容 → 回到农耕
```

三条线的交汇点是"农耕"——所有产出最终都服务于让农场变得更好。这个结构确保玩家不会在任何一个子系统里"迷路"，因为"回家做农活"永远是引力中心。

**血肉（表现与反馈）：**

Barone 亲自绘制了所有的像素美术（从角色肖像到作物生长的 4 个阶段），亲自创作了所有的音乐（超过 70 首原创曲目），亲自写下了 NPC 的每一句对话。这种"全栈式创作"在工业化游戏生产中是低效的——但在独立游戏中，它产生了一种罕见的**审美一致性**。像素绘画的朴实温暖、音乐的田园氛围、对话的日常质感——三个感官维度传达的是同一种情感。这就是本书第 0 章强调的"三层内聚"。

**灵魂（叙事与情感）：**

Stardew 的灵魂不是"振兴一个农场"——那是骨架。它的灵魂是**怀旧与归属**。你在游戏里不是在"肝"——你在"过日子"。每一天有 13 分钟的节奏，每一季有固定的事件。村民从陌生人变为朋友，甚至爱人。你离城市越来越远，离小镇越来越近。

这个灵魂不是通过一段煽情过场动画传达的——它是通过"你的农场慢慢从荒地变成家"这个机制过程自然产生的。玩家对一株作物产生感情，不是因为剧情告诉你要爱它——是因为你浇了 13 天的水，看着它从种子到开花。

### 2.5 Kill Criteria 总结表

| 步骤 | 实际行为 | Kill Criteria 状态 | 方法论文本 |
|------|---------|-------------------|-----------|
| ① 概念孵化 | 对标《牧场物语》差评，精准定位"想要更好牧场物语的 PC 玩家" | ✅ 通过（卖点清晰、竞品差异化成立） | 竞品差评驱动——已知问题 = 已知机会 |
| ② 一页纸概要 | 隐式完成：Core Loop = 一天的自然节律，Scope = 三条核心线 | ✅ 通过（Core Loop 极度清晰） | 节律感天然的 Core Loop 不需要被"发明" |
| ③ 原型验证 | 无外部 playtest，完全 solo 开发约 2 年才有可玩版本 | ⚠️ 会触发 Kill Criteria | ⚠️ 边界案例：开发者=目标玩家、竞品提供精确导航、Core Loop 天然成立——三个豁免条件均满足 |
| ④ 设计深化 | 隐式范围控制：三条核心系统在第一年冻结 | ✅ 通过（Scope 冻结完成，无设计漂移） | 隐式 Ten-Pager——范围冻结的纪律替代了正式文档 |
| ⑤ 垂直切片 | 自然生长的 VS：开发约 2 年时可玩通一个完整季节 | ✅ 通过（自然 VS 验证了管线可行） | VS 不一定需要"刻意制作"——有时它只是你做到某个节点后回头看 |
| ⑥ 生产开发 | 后两年密集内容填充，设计从未漂移 | ✅ 通过（冻结纪律执行到极致） | 本书正面案例。三年填充不扩展新系统 |
| ⑦ 迭代打磨 | 约 6 个月打磨 + 发售后持续免费更新 | ✅ 通过（打磨换来了品类定义权） | 持续免费更新产生的口碑效应是 Stardew 长销的核心 |

### 2.6 方法论启示

**"禁止复制"的成功模式。** Stardew Valley 不是一个方法论模板——它是一个方法论边界案例。它的成功依赖了一组不可复现的前提条件（开发者=目标玩家、竞品缺口巨大、极低的生活成本、极强的创作纪律）。把它当作"一个人做 4 年也能成功"的励志模板，是对独立开发者最大的误导。

**Scope 控制的本质不是"砍功能"，而是"冻结新系统"。** Barone 没有在一页纸上列出"明确不做"的东西，但他的实际行为比任何一页纸都严格：核心系统在第一年确定后，三年不加新东西。他的游戏有深度不是因为系统多——是因为每一个冻结的系统都被内容填到了令人满足的深度。

**骨架-血肉-灵魂三层的内聚性是单人开发的隐藏优势。** 当设计、美术、音乐、对话全部出自同一人之手时，三层的内聚性几乎是自动达成的——因为创作者的审美直觉会在潜意识层面统一所有输出。团队开发需要大量沟通来维护这种一致性；单人开发天然拥有它。代价是：你必须是那个"能同时做好这三层"的罕见的人。

**Burnout 是 Solo 开发最危险的 Kill Criteria。** Barone 在开发中承受了巨大的心理压力——孤独、自我怀疑、经济焦虑。他在多个采访中描述了"感觉像在黑洞里"的日子。本书方法论没有直接定义"心理健康 Kill Criteria"，但这是一个值得你为自己设定的硬性条件：**如果连续 4 周你打开引擎时感到的不是期待而是恐惧，你需要暂停——不是暂停项目，是暂停你自己。**

## 案例3：Celeste — Game Jam 原型到完整产品的路径

> **核心方法论关键词：** Toy First、Game Jam 约束、FTUE 打磨、难度曲线设计、叙事即机制、渐进式复杂度递进

### 3.1 背景：四天 Game Jam 种下的种子

2015 年，Matt Thorson（Maddy Thorson）和 Noel Berry 在一次 4 天 Game Jam 中做了一个 Pico-8 平台跳跃游戏——玩家控制一个角色向上攀登一座山。核心机制只有四个动作：**移动（跑）、跳跃、冲刺（八方向 Dash）、攀爬（抓墙）**。

这个 Jam 版本被放到了 itch.io 上供免费游玩，获得了游戏社区意想不到的热烈反响。Thorson 和 Berry 意识到：这个核心交互中有什么东西，在 4 天的简陋原型里就已经让人上瘾了。

他们随后成立 Matt Makes Games，用了约 2 年时间将这个 Game Jam 原型扩展为一款 Metacritic 92 分的完整游戏。2018 年 1 月，Celeste 发售，定价 $19.99。截至 2026 年，全平台销量超过 500 万份。

Celeste 是本书方法论中最"标准"的成功路径——它从 Game Jam 到完整产品的每一步，都可以完美映射到七步流程和 Toy First 原则上。

### 3.2 七步流程映射

| 步骤 | Celeste 的实际行为 | 方法论对标 |
|------|-------------------|-----------|
| **① 概念孵化** | Game Jam 的主题是"登一座山"。Thorson 选择了纯平台跳跃类型——不依赖道具、技能树或数值成长，只靠"操作精进"。创意来源是混合的：游戏域内回收（《超级肉肉哥》的硬核平台跳跃） + 情绪目标先行（"攀登的挫败是成长的一部分"）。 | 时间约束（4 天 Jam）是概念孵化期的极限压缩器。Game Jam 的约束力天然限制了 scope——你只有 4 天，只能做一件事。 |
| **② 一页纸概要** | Jam 版本本身就是一页纸：Core Loop = `进入屏幕 → 观察 → 尝试 → 死亡 → 重生 → 再尝试 → 通过`（5-30 秒/屏幕）。Design Pillars 在 Jam 阶段是隐式的，但从最终成品回溯，三条 Pillar 始终成立：(1) 攀登的挫败是成长的一部分；(2) 速度感来自精准；(3) 内心的山比外界的山更难爬。 | Game Jam 的 4 天时限本身就是最强的一页纸——你做不了任何超出单屏交互核心的东西。 |
| **③ 原型验证** | Jam 版本是"Toy First→Toy→Game→Juicy"四阶段在 4 天内的极限压缩。核心验证结论来自 Jam 版本发布后社区的狂热反馈——不是几个赞，是大量玩家自发录制通关视频、讨论路线、请求更多内容。 | 原型在 Jam 期间完成了最关键的验证：Dash + 攀爬的核心交互是不是"连续玩 10 分钟还不想停"？答案从社区的反应中得到——远超 10 分钟。 |
| **④ 设计深化** | Jam 后进入正式预生产。Thorson 做了完整的关卡结构规划（7 个章节，每章一个核心机制主题）、难度曲线设计（B 面与 C 面的高难度挑战）、叙事整合（Madeline 的心理旅程）。Scope Budget：约 700 个单屏关卡，每个屏幕的"单位生产成本"在确立模板后可预测。 | 从 Jam 的"无意识正确"到预生产的"有意识规划"。这是从"探索者"到"规划者"的教科书式切换。 |
| **⑤ 垂直切片** | Celeste 是垂直切片的经典适用场景——线性关卡制游戏。团队先做完第一章到接近最终品质——包括完整的像素美术、音乐、音效、叙事过场、B 面关卡——然后测算：做第二章要多久？（这个问题 == 第二切片耗时是否收敛？） | 内容驱动型游戏的 VS 标准路径。第一切片确立管线，第二切片验证复用性。 |
| **⑥ 生产开发** | 核心机制（移动+跳跃+冲刺+攀爬）在开发启动时就已冻结。生产阶段的工作是：按模板制作剩余的 6 个章节、每个章节的 B 面和 C 面、草莓收集品、隐藏内容。每章的关卡设计围绕一个核心机制变体展开（第二章=梦境方块、第三章=清理灰尘、第四章=强风……）。 | 设计冻结 + 模板化内容生产。每章的"单位产能"因模板固定而可预测。关卡设计的"一章一主题"策略同时保证了多样性和生产效率。 |
| **⑦ 迭代打磨** | Celeste 的打磨在多个维度上都是教科书级别的：(1) **FTUE 打磨**——前几屏的平台间距恰好是 Dash 的极限距离，不教而会；(2) **难度打磨**——辅助模式（Assist Mode）让不擅长平台跳跃的玩家也能体验完整故事；(3) **叙事打磨**——"死亡"本身被整合进叙事（Madeline 的焦虑和自我否定）。 | 三层同时打磨。尤其是 FTUE——"Don't tell me, involve me"原则的极致执行。 |

### 3.3 关键设计决策：难度作为叙事，而非惩罚

Celeste 在设计史上最重要的贡献之一，是证明了**高难度不一定是"惩罚"——它可以是叙事本身**。

在《Celeste》中，你死亡数百次、数千次。但每次死亡后：
- 你**即刻重生**在本屏开头（死亡到重生的间隔 < 0.3 秒）——愤怒还没来得及消解，你已经在新一轮尝试中
- 没有生命数限制、没有游戏结束画面、没有"返回标题"
- 死亡动画短暂、安静——角色缩成一团然后重新出现，没有惨叫声，没有血腥
- 关卡设计将死亡变成"实验"而非"失败"——每一个屏幕都是一个微型谜题，死亡告诉你"刚才的路线不对，试试另一种"

这与《Flappy Bird》的成瘾机制同源（本书第 0 章分析过）：**死亡到重生间隔的极致缩短，将"挫败"转化为"执着"。** 但 Celeste 在此基础上加了一层叙事深度——Madeline 攀登山峰的过程，就是她与自己的焦虑、自我否定、和完美主义斗争的过程。你作为玩家在游戏里反复死亡、反复尝试的过程，与 Madeline 在剧情中"反复跌倒、反复爬起"的过程是**同构的**。

> **骨架-血肉-灵魂三层在此合为一体：** 骨架（Dash + 攀爬 + 即刻重生）→ 血肉（像素拉伸动画 + 安静重生 + 柔和色调）→ 灵魂（焦虑与自我接受）。三层不是三个独立的"部门"——它们是同一种设计意图的三种表达方式。

### 3.4 辅助模式（Assist Mode）：一项违背"硬核"传统但完全正确的设计决策

Celeste 在发售时内置了辅助模式——玩家可以调整游戏速度、获得无限 Dash、或直接无敌。这在平台跳跃社区中是一个高度争议的决定。"硬核游戏还加辅助模式？"——但 Thorson 的回应展示了优秀设计师的思维：

> 辅助模式不是降低难度——是让更多玩家能够体验 Madeline 的故事。如果你需要辅助模式来通关，你体验到的故事和不需要辅助模式的人体验到的故事，是同一个故事：一个关于坚持、失败、和自我接受的故事。

从方法论角度看，这个决策完全符合 Design Pillar(1)："攀登的挫败是成长的一部分"——**不是"攀登的挫败只有高手才有资格体验"**。辅助模式是 Pillar 的自然延伸，而非妥协。Pillar(3) "内心的山比外界的山更难爬"也得到了加强——当游戏的机制本身不再成为障碍时，叙事层的"内心攀登"反而更加突出。

### 3.5 Kill Criteria 总结表

| 步骤 | 实际行为 | Kill Criteria 状态 | 方法论文本 |
|------|---------|-------------------|-----------|
| ① 概念孵化 | Game Jam 4 天：核心机制在极端时间约束下自动聚拢 | ✅ 通过（4 天 Jam = 强制收敛） | Game Jam 是概念孵化的天然加速器——时间约束杀死一切不必要的东西 |
| ② 一页纸概要 | Jam 版本本身 = 一页纸；社区反馈 = 可读性测试 | ✅ 通过（Jam 游戏 = 最小可读 GDD；社区理解 = 通过） | 如果你的原型在 itch.io 上有人自发录制通关视频，你的 Core Loop 是可读的 |
| ③ 原型验证 | Jam 版本获社区热烈反响——玩家自发传播 | ✅ 通过（远超 3 轮无趣的标准） | 社区自发行为是最强的 Kill Criteria 反证——玩家在替你传播 |
| ④ 设计深化 | 从 4 天 Jam 到 2 年完整产品，关卡结构系统规划 | ✅ 通过（Scope Budget 建立，单位产能可预测） | Jam → 完整产品的切换点是"规划者思维"的启动时刻 |
| ⑤ 垂直切片 | 第一章到最终品质，第二切片验证产能 | ✅ 通过（管线可行、产能收敛） | 内容驱动型游戏 VS 的经典路径 |
| ⑥ 生产开发 | 核心机制冻结，"一章一主题"模板化生产 | ✅ 通过（设计不漂移、内容可复用） | 模板化 ≠ 单调——每章的机制变体保证了多样性 |
| ⑦ 迭代打磨 | 多维度打磨（FTUE + 难度 + 叙事），辅助模式解决 accessibility | ✅ 通过（体验一致、辅助模式扩展了受众） | Pillar 驱动的打磨——辅助模式不是妥协，是 Pillar 的延伸 |

### 3.6 方法论启示

**"4 天 Game Jam → 2 年完整产品"不是路径的缩短，而是验证的前置。** Celeste 没有"跳过原型验证"——它把原型验证挪到了最早的可能时间点（Game Jam），用社区的真实反馈替代了内部 playtest。如果你有任何机会参加 Game Jam，你得到的不是"一个参赛作品"，而是"一个潜在核心机制的免费验证数据"。这笔交易在任何时间预算下都是划算的。

**核心机制做到"极少但极深"。** Celeste 只有 4 个动作（移动、跳跃、Dash、攀爬），但每个动作都被探索到了极限——Dash 的距离、方向、次数限制、恢复条件、与环境的交互（穿越特定方块、被风影响、被果冻弹射）。大多数独立游戏的机制是"多而浅"——10 个系统，每个只做到了表面。Celeste 的证据是：**4 个动作 × 700 个屏幕 = 一款 Metacritic 92 分的游戏。** 深度不是来自机制的数量，而是来自每个机制与环境交互的可能性空间。

**难度是设计，不是参数。** Celeste 的难度不是"把敌人的血量调高 2 倍"——它的难度被设计进了每一个屏幕的空间布局、每一帧的输入窗口、每一个 Dash 的恢复时机。难度不是结果的修饰，而是过程的构造。这就是为什么即使是最难的 B 面、C 面关卡，玩家也极少感到"被系统不公平对待"——因为挑战的来源是可理解的（空间布局），而非隐藏的（数值作弊）。

## 案例4：失败案例 — 当 Kill Criteria 被忽视

> **核心方法论关键词：** Kill Criteria 的现实代价、Scope Creep、原型拖延、市场信号忽视、沉没成本陷阱

### 4.1 背景：一个真实的独立游戏失败案例

**Towns（2012）** 是 Steam Early Access 历史上最早的游戏之一，也是该领域最著名的失败案例之一。开发者 Xavi Canal（SMP 工作室）的构想是"一款城镇建设模拟游戏，Dwarf Fortress 的简化版，但有图形界面和更直观的操作"。

初期信号非常积极：Towns 在 Kickstarter 式预购中获得超过 20 万美元收入，Steam Greenlight 高票通过，Early Access 上线后迅速积累数万名玩家。从"有人想玩吗"的角度来看，Towns 的市场验证是**通过的**。

但接下来 2 年——游戏从未完成。开发者最终宣布停止开发，留下一款半成品，成为 Steam 早期争议最大的"废弃游戏"之一。开发者发布了公开道歉声明，承认"我们迷失了方向"。

用本书方法论回溯分析，Towns 的失败几乎每一步都可以在 Kill Criteria 框架中"提前预测"——但它从未触发任何一个 Kill Criteria。或者更准确地说：**它触发了，但被无视了。**

### 4.2 七步流程回溯：Kill Criteria 在哪里被错过

#### Step 1（概念孵化）：✅ 通过，但忽略了关键警告信号

**市场假设：** "喜欢 Dwarf Fortress 式深度但被其学习曲线劝退的玩家，会购买一款有图形的简化版城镇建设游戏。"

这个假设本身是成立的——2012 年确实存在大量"Dwarf Fortress 好玩但看着头疼"的玩家。Kickstarter 收入也验证了这一点。

**但被忽略的警告信号：** "简化 Dwarf Fortress"这个定位意味着——你需要同时做到两件事：足够深度以保留 Dwarf Fortress 粉丝，足够简单以吸引非 Dwarf Fortress 粉丝。这两个目标在同一个产品中可能互斥。Kill Criteria 第 3 条（竞品差异化）在这个案例中被"模糊地通过"了——"有图形的 Dwarf Fortress"听起来差异化清晰，但它没有回答"简单 vs 深度"这对核心矛盾。

#### Step 2（一页纸概要）：⚠️ 模糊通过，Scope 未收敛

Towns 的一页纸（如果存在的话）没有完成 Scope 收敛。"城镇建设模拟"这个品类天然容易 scope 膨胀——你可以加农业、工业、军事、外交、地城、天气、疾病、经济循环……每一个子系统都能找到"为什么需要它"的理由。SMP 工作室最终加入了英雄系统（让玩家控制一个英雄探索地城）、装备系统、战斗系统、贸易系统——每一个单独看都合理，但没有任何一个系统被一个清晰的 Pillar 做过减法决策。

**Kill Criteria 第 5 条（Scope 可控）在此处应该触发。** "一个城镇建设游戏 + 地城探索 + 英雄养成"的 scope 已经远超一个小团队的能力——但这个信号没有被识别。

#### Step 3（原型验证）：⚠️ 原型被做成了"early access 产品"，不是信息获取工具

Towns 最大的方法论错误是：**把原型卖给了玩家。**

如果 SMP 遵从本书的原型方法——做一个灰盒原型，找 5 个目标玩家测试，观察"建造城镇→吸引居民→满足需求→扩大城镇"这个 Core Loop 是否在 10 分钟灰盒体验中让人想继续——他们可能在早期就发现：城镇建设的核心循环本身还不够紧密，玩家在中期容易迷失目标。

但 Towns 的做法是：**在核心循环尚未被验证"持续好玩"之前，就把原型挂到 Steam 上卖钱。** 一旦开始收玩家的钱，原型的性质就变了——它不再是"可以推倒重来的实验"，而是"玩家已经付了钱的产品承诺"。SMP 被困在了一个无法回头的轨道上。早期的积极收入——本应是验证信号——反而成为了沉没成本陷阱的强化剂。

> **本书方法论的核心警告（第 5 章）："原型可以成为掩盖优柔寡断的借口。"** Towns 的"原型"不是原型——它是披着 Early Access 外衣的、未完成的、未验证的 alpha 版本。把原型卖钱不是"获得收入"——是"提前锁定无法回头的方向"。

#### Step 4（设计深化）：❌ 从未发生

因为 Step 3 从未真正完成（Core Loop 从未被独立验证为"持续好玩"），Step 4 的规划基础是空的。SMP 没有做过 Scope Budget——如果他们做了，在"城镇建设 + 地城探索 + 英雄养成"的组合下算出来的总工时，会告诉他们这不可能被一个小团队完成。

**Kill Criteria 第 4 步的"Scope Budget 超 2 倍预算"在此处被彻底跳过。**

#### Step 5（垂直切片）：❌ 从未发生

Towns 没有在早期做一个接近最终品质的截面来验证管线可行性。它一直处于"所有系统都在开发中但没有任何系统被做到最终品质"的状态。结果是——当 SMP 试图推进到"完成"时，他们发现许多系统在"粗糙可行"和"最终品质"之间有一道无法跨越的鸿沟。

#### Step 6（生产开发）：❌ 设计永动

由于设计从未冻结，新功能持续加入——英雄、装备、贸易、地城层数扩展——每一个新系统都引入了新的 Bug、新的平衡需求、新的玩家期待。SMP 陷入了本书第 8 章警告的"设计永动"（Design Perpetuum Mobile）陷阱：不是在完成游戏，而是在不断扩张游戏的定义。

#### Step 7（迭代打磨）：❌ 在应该打磨的阶段，还在做 Step 3 的设计

当一个游戏进入打磨阶段时，设计的核心工作应该是"让已经存在的东西感觉对"。但 Towns 在应该打磨的时候还在扩展新系统——因为核心系统本身从未被验证为"足够好玩"，团队用"再加一个系统"来补救"核心系统不够深"的问题。这是"在烂地基上继续盖楼"的经典案例（本书第 0 章警告过：在骨架成立之前添加血肉，等于在烂地基上装修——迟早要砸掉）。

### 4.6 从失败中提取的警示原则

**原则一：原型是信息工具，不是商品。永远不要卖你的原型。**

Towns 的核心错误不是"设计不对"——而是"在原型阶段就把自己锁进了无法回头的轨道"。当你收了玩家的钱，你的原型就不再是可以推倒重来的实验——它是承载承诺的产品。本书第 5 章反复强调：**原型做完验证后应该扔掉，从零开始写生产代码。** 如果你把原型变成了产品，你就同时失去了"验证的自由"和"推倒的自由"。

**原则二：收入信号在早期是危险的——它可能掩盖产品信号。**

Kickstarter 收入和 Early Access 收入是真实的钱——但它们回答的是"有人想买这个愿景吗"，不是"这个 Core Loop 持续好玩吗"。Towns 的早期财务成功让 SMP 误以为"市场验证已通过"——但实际上通过的只是"概念的市场吸引力"，不是"游戏的玩法质量"。这两个是完全不同的问题。

**原则三：Core Loop 不成立的游戏，"加系统"就是"挖坟"。**

当一个游戏的 Core Loop 本身不够深、不够持续时，设计师的本能反应往往是"再加一个系统"。这是游戏设计中最危险的直觉之一——因为新系统永远能带来暂时的新鲜感，这会被误认为"设计在改善"。但这不是改善——这是用新东西的初次好奇来掩盖旧东西的深层缺陷。Towns 从城镇建造到英雄战斗到贸易系统——每一次扩展都带来短期的玩家活跃度上升，但每一次上升后都是更深的回落。因为没有一个系统本身是足够深的。**正确的做法是在 Step 3 就停止：回到 Core Loop，找到"再加一个规则能让它有趣 10 分钟"的改进——而不是"再加一个系统能让它显得新鲜 2 天"。**

**原则四：没有 Scope Budget 的生产开发 = 盲飞。**

如果 SMP 在进入开发前花 2 周做一份简单的 Scope Budget——列出所有计划中的系统、每个系统的预估子内容数量、单位生产时间——他们会在纸面上看到"这需要 3 倍于我们团队资源的时间"。Scope Budget 不是为了"精确预测"，而是为了**在成本还是纸面数字的时候，就发现哪些东西不该做**。

### 4.7 方法论启示

本附录的四个案例放在一起，形成了一组完整的"参考系"：

- **Balatro** 代表的是"完美遵循方法论核心精神"——极简原型、核心循环自证、加法创新、设计冻结
- **Stardew Valley** 代表的是"方法论边界案例"——它违反了 Kill Criteria 的多个条件但仍然成功，因为一组极罕见的豁免条件被满足；它不是模板，是例外
- **Celeste** 代表的是"理想路径"——Game Jam 原型 → 社区验证 → 垂直切片 → 模板化生产 → 多层打磨，每一步都是方法论的标准实践
- **Towns** 代表的是"未定义路径"——它有一个正确的开始（市场验证通过），但在第一个核心节点（原型验证）就偏离了方向，之后每一步都在错误的方向上累积沉没成本

四个案例回答了同一个问题：**本书方法论不是"成功公式"——它是"失败预防机制"。**

你不会因为遵循方法论就自动成功。但你会因为**在有信号的地方停下来检查信号**——而非在所有节点上都按"我觉得"硬闯——而避免那些可预防的、已经被无数前人踩过的、有时是不可逆的失败。

## 附录E小结：四项核心教训

1. **加法创新 > 从零发明。** 把两个已知的、已被市场验证的元素组合起来，比发明一个前所未有的东西风险低得多。但组合不是"拼凑"——你必须找到两个元素的接口契合点（Balatro 的牌型鉴定 = 天然的战斗判定）。

2. **Solo 开发的可行性取决于三根支柱：自己是否是目标玩家、是否有竞品提供"已知问题集"、是否能承受长期无反馈的开发周期。** 缺任何一根，Kill Criteria 都是你的朋友而非敌人。

3. **Game Jam 是低成本的 Kill Criteria 前置器。** 在 4 天内验证一个核心交互是否有人喜欢——比花 2 个月做原型才发现的成本低 15 倍。Jam 不是"没时间做正事的借口"——它是"在正事开始之前获得免费验证数据的工具"。

4. **在 Core Loop 验证通过之前，不要收任何人的钱，不要承诺任何结果，不要锁定任何方向。** 一旦你收了钱，你就从"探索者"变成了"债务人"——而探索者是允许失败的，债务人不允许。这是 Towns 留给所有独立开发者最昂贵的教训。
