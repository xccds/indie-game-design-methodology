# 附录E：案例研究

> **本附录的定位：** 前九章建立了方法论框架——七步流程、双螺旋模型、Kill Criteria 体系、骨架-血肉-灵魂三层模型。本附录将这些工具作为**分析透镜**，投向四个公开资料较多的独立游戏案例。这里的映射是事后重构，用来生成可验证的设计假设，不是对真实开发因果链的证明。每个案例都应区分**公开可确认的信息、基于本书框架的推断、无法确认的部分和适用边界**。

> **阅读建议：** 四个案例可以按顺序读，也可以根据你的兴趣跳读。如果你正在做一个机制组合型游戏，先看案例 1（Balatro）。如果你在做 solo 开发或担心 burnout，先看案例 2（Stardew Valley）。如果你在 Game Jam 里找到了一个原型想把它做完，先看案例 3（Celeste）。如果你怀疑自己的项目可能已经在不该走的方向上走了太久，**直接看案例 4**。

## 案例1：Balatro — 扑克机制 × Roguelike 的加法创新

> **核心方法论关键词：** 游戏域内回收、加法创新、"XX meets XX"公式、Toy First、水平切片、机制-市场契合

### 1.1 背景：一个加拿大 IT 运维的副业项目

公开资料显示，LocalThunk 使用化名并以个人开发者身份制作了《Balatro》，游戏于 2024 年发售并取得显著商业和口碑表现。关于其工作安排、原型细节、预算、测试样本和各阶段耗时，应以开发者访谈、官方资料和可靠统计分别核验；本案例不把未经核验的数字当作流程证据。

从方法论角度看，Balatro 可以作为**游戏域内回收**的启发式案例：它把扑克规则、Roguelike 构筑和修正器叠加组合起来，公开成品呈现出清晰的接口契合点。这里不能据此证明“组合公式”必然降低风险或导致成功。

### 1.2 七步流程映射

Balatro 不是严格遵循本书方法论开发的（开发者是否接触过本书也无法据此确认）。如果用七步流程作为回溯分析透镜，可以提出如下**待核验的对应关系**；“方法论对标”不是“实际采用流程”的证据：

| 步骤 | Balatro 的实际行为 | 方法论对标 |
|------|-------------------|-----------|
| **① 概念孵化** | 受《幸运房东》（Luck be a Landlord）启发，想做一个"在已知规则上叠加 Roguelike 修正器"的游戏。扑克牌型是候选之一——因为牌型鉴定系统天然适合作为"战斗判定"。 | 游戏域内回收（来源 1）。"扑克 × Roguelike" = 经典 XX meets XX 公式。 |
| **② 一页纸概要** | 未写出正式的 One-Pager，但成品呈现出相对聚焦的循环：从手牌组成牌型 → 得分 → 获得资源 → 购买或升级修正器 → 应对下一轮挑战。Scope 主要围绕牌类内容展开，具体早期范围无法从成品完整反推。 | 可作为“核心循环清楚、内容媒介集中”的启发式案例，但不能由成品证明当时的文档或范围控制过程。 |
| **③ 原型验证** | 公开访谈和成品信息可以支持“先验证核心组合，再逐步完善表现”的推断；具体原型版本、测试者构成和游玩时长需要以开发者一手资料核实。 | 可作为 Toy First 的候选案例，但开发者自测不能替代目标玩家证据。 |
| **④ 设计深化** | 未写正式的 Ten-Pager，但隐式完成了范围估算：核心系统的"牌"约 150 种（含小丑、塔罗、星球、幻灵），每张牌只是一个数据条目（名称 + 效果 + 美术），不是手工关卡。这意味着内容生产的单位成本极低。 | 内容类型天然"可模板化"——每张牌 = 一个数据行。这是 Balatro 作为 solo 项目可行的结构基础。 |
| **⑤ 垂直/水平切片** | Balatro 这类系统深度型游戏未必有传统关卡截面；更合理的取样方式可能是覆盖不同复杂度的内容单元，并观察系统协同运行时是否持续产生有趣的组合决策。具体采用哪种切片方式需要开发资料确认。 | HS 可能比传统 VS 更匹配，但不是免检。仍需验证系统交互、可读性、内容生产和平衡风险。 |
| **⑥ 生产开发** | 成品呈现出以卡牌内容、数值、表现和音频为主的结构。是否在原型阶段“冻结”以及哪些设计曾被舍弃，公开资料不足以完整还原。 | 可讨论“稳定核心支柱、控制范围”的启发，但不能写成设计冻结导致成功的证明。 |
| **⑦ 迭代打磨** | 发售前进行了多轮外部 playtest。打磨重点包括数值平衡（避免某些组合形成过强的唯一最优解）、UI 可读性（牌面信息在修正器叠加时仍然清晰）和视觉风格。 | 可作为“减少单一最优策略、控制信息负担”的启发式案例，具体测试效果需要版本和测试资料支持。 |

### 1.3 关键设计决策与 Kill Criteria 审视

**决策一：不发明新机制，只做加法组合。**

LocalThunk 没有试图创造一个前所未有的玩法。他拿了三个已知元素——扑克牌型判定（德州扑克规则）、Roguelike 构筑（每局不同的 build）、修正器叠加（小丑牌改变牌型行为）——找到了它们之间的接口契合点。已知零件可能降低部分实现和理解风险，但不会让原型可行性自动通过；仍需用低成本原型验证组合后的体验，不必先做完美术。

**决策二：用水平切片代替垂直切片。**

Kill Criteria 第 5 步可以要求代表性生产风险得到验证，但 Balatro 这类系统深度型游戏未必有传统意义上的关卡截面。这是方法论的一个重要提醒：**Gate 的证据形态因游戏类型而异。** 卡牌、策略、Roguelike 可能需要验证系统交互、不同复杂度的内容单元、经济平衡和长期重玩性，而非机械套用某个单一切片的耗时。

**决策三：保持匿名，隔绝外部噪音。**

LocalThunk 在整个开发过程中保持匿名，不与社区过度互动。这个"反市场线"决策看似违背了第 2.4 节的建议（"从 Step 1 开始做市场验证"），但实际上是一种对独立开发者心理健康的有意保护——早期市场反馈中的噪音（尤其是来自非目标玩家的负面反馈）可能动摇设计信心。等游戏接近完成、品质足以准确传达体验时再公开，是一种合法的节奏选择。注意：这并不意味着他跳过了市场验证——他对竞品（《幸运房东》《Slay the Spire》《杀戮尖塔》等）的深入研究本身就是一种被动的市场验证。

### 1.4 Kill Criteria 总结表

| 步骤 | 实际行为 | Kill Criteria 状态 | 方法论文本 |
|------|---------|-------------------|-----------|
| ① 概念孵化 | 成品呈现出“扑克+肉鸽”的明确组合，目标玩家和竞品关系仍需从资料与测试核实。 | **支持性线索**，不是自动通过 | “XX meets XX”可降低已知元素风险，但组合仍需验证 |
| ② 一页纸概要 | 核心循环和内容媒介相对集中。 | **可作为范围假设** | 牌作为内容媒介可能约束范围，但不保证生产成本可控 |
| ③ 原型验证 | 公开资料可支持“先处理核心组合”的推断；具体测试样本与结果需核实。 | **证据不完整** | 自测、社区反应与目标玩家测试要分开解释 |
| ④ 设计深化 | 卡牌结构具有数据化、模板化的可能。 | **需要检查** | 仍需验证不同复杂度内容、平衡和工具成本 |
| ⑤ 垂直/水平切片 | 以系统协同和内容单元作为主要取样方向更合理。 | **策略匹配，但不是免检** | HS 需要覆盖系统交互、可读性和长期体验风险 |
| ⑥ 生产开发 | 成品主要呈现为卡牌内容、数值和表现的扩充。 | **公开结果与推断部分** | 是否完全冻结、哪些设计被舍弃无法从成品反推 |
| ⑦ 迭代打磨 | 成品呈现出数值、UI、视觉和音频的持续完善。 | **结果线索** | 不能仅由成品推导测试轮次或因果关系 |

### 1.5 方法论启示

**"XX meets XX"可以作为降低部分不确定性的策略。** 当一个创意由已知元素组合而成时，可以复用对规则和受众的已有认知，但不能跳过组合后的体验、实现、内容成本和市场验证。需要验证的是“组合是否成立”，而不是把零件的既有知名度当作结论。

**游戏类型决定风险取样策略。** 系统深度驱动型游戏可能更需要 HS、系统交互实验和多种内容单元，内容驱动型游戏可能更需要 VS；两者也可以组合使用。Balatro 不一定需要传统“第一关”式 VS，但仍要验证可读性、内容生产、经济平衡和长期体验。

**Core Loop 能否被目标玩家用自己的话理解，是重要的竞争力。** Balatro 的核心循环可以作为简洁表达的案例，但不应规定统一解释时长。每一步设计深化都应问：“这条规则让目标体验更清楚、更有趣，还是只增加了复杂度？”

## 案例2：Stardew Valley — 单人开发者的七年回溯分析

> **核心方法论关键词：** 竞品差评驱动创新、稳定支柱与变更控制、骨架-血肉-灵魂三层内聚、单人开发的时间管理、Burnout 预防

### 2.1 背景：一个毕业生用四年回应一款自己热爱的游戏

公开资料显示，Eric Barone（网名 ConcernedApe）独立制作了《星露谷物语》，作品受到《牧场物语》等农场模拟游戏的影响。关于其具体开发起点、工作安排和阶段划分，应以本人访谈和项目记录核验。

他的起点本质上就是本书 3.3 节所描述的"从竞品差评中找机会"：他是《牧场物语》的忠实玩家，但他对这个系列后来的作品感到失望——他觉得系列"丢掉了最初让游戏感人的东西"。游戏变得更复杂了，但那种在小镇上日常生活的宁静感和归属感变淡了。

游戏发售后取得了显著的商业和口碑表现，并成为农场模拟 RPG 中具有影响力的作品。销量、工期和“定义品类”等结论需要注明统计口径和来源；它们不能单独证明某个开发流程导致成功。

这类案例的价值在于帮助读者提出问题：哪些做法可能支持了结果，哪些条件不可复制，哪些信息仍然未知。不能把公开成功结果倒推成“Kill Criteria 本来应该杀掉、但例外放过”的因果证明。

### 2.2 七步流程映射

| 步骤 | Stardew Valley 的实际行为 | 方法论对标 |
|------|--------------------------|-----------|
| **① 概念孵化** | 对标《牧场物语》，从"竞品差评"中提炼改进方向：1) 更深的农场自定义；2) 更丰富的村民故事线；3) 采矿战斗增加节奏变化；4) 保留田园生活的宁静核心。市场假设："怀念牧场物语式体验但觉得现有作品不够深度的 PC 玩家"。 | 竞品分析驱动。目标受众极其精准——"喜欢牧场物语但不满足的人"。这个群体当时确实存在一个大缺口。 |
| **② 一页纸概要** | Barone 没有写正式的设计文档，但成品呈现出清晰的 Core Loop：`起床 → 浇水/收获 → 探索/社交/采矿/钓鱼 → 回家睡觉 → 第二天`。农耕、采矿战斗和村民社交等核心线在成品中彼此咬合；具体何时定义完成，需要开发记录确认。 | Core Loop 的“游戏日”节律是这款游戏的结构基础，但具体会话时长应作为项目参数验证，而不是直接照搬。 |
| **③ 原型验证** | 公开资料可支持“长期独立开发、逐步形成完整版本”的叙述，但无法仅凭成品确认原型轮次、外部测试覆盖或核心循环在何时成立。 | **证据不完整**；应补充目标玩家测试或明确承担未验证风险 |
| **④ 设计深化** | 未写正式 Ten-Pager。但隐式范围界定在第一年就完成了——三个核心系统 + 内容填充（更多作物/矿物/NPC），不扩展新系统。 | 隐式 Scope Budget 成立，因为 Barone 有极强的纪律——他不在开发中途加新系统。 |
| **⑤ 垂直切片** | 公开成品和开发过程可以让人提出“完整季节/会话可能承担代表性样本”的推断，但不能仅据此确认其当时是否被当作 VS 或足以代表全量产能。 | **可能的自然样本**；仍需检查复杂内容、依赖和后期整合 |
| **⑥ 生产开发** | 成品包含大量内容、表现和系统迭代；具体哪些设计在何时稳定、哪些被放弃，不能从最终版本完整反推。 | **可讨论稳定核心支柱的价值**，不能证明“完全冻结”导致成功 |
| **⑦ 迭代打磨** | 成品和后续更新显示出持续的 Bug 修复、内容和体验完善；具体测试轮次、打磨时长和因果关系需要一手资料。 | **结果线索**；不能把个人偏好或长期更新直接当作通用方法 |

### 2.3 这个案例对 Kill Criteria 的边界提醒

如果只看最终成功结果，很容易把“没有公开外部测试”“长期独立开发”解释成方法论被证明错误，或反过来把它当成任何人都能复制的豁免。更稳妥的读法是：该项目公开可确认的信息不足以完整重建每个验证节点，因此不能判断它是否“触发后被放过”，也不能用成功结果证明省略验证是正确的。

可以把以下内容作为需要核验的风险维度，而不是豁免条件：

| 风险维度 | 本案例可观察到的线索 | 正确用法 |
|----------|----------------------|----------|
| 目标玩家 | 开发者长期熟悉目标品类，可能具备较强领域经验 | 仍需区分个人偏好与目标玩家证据 |
| 竞品知识 | 项目受到既有农场模拟游戏影响 | 竞品问题可以形成假设，但不能替代原型和受众测试 |
| 核心节律 | “一天”的会话结构在成品中清晰可见 | 结构可借鉴，具体节奏和长期价值仍需验证 |
| 资源承受力 | 长期独立开发需要可承受的生活与资金安排 | 明确自己的时间、预算、机会成本和退出点，不复制他人的期限 |

因此，Kill Criteria 不应设置“豁免”来绕过证据，而应允许项目在已知条件、风险承担和替代验证方式被明确记录后，做出不同于标准路径的决策。

### 2.4 骨架-血肉-灵魂三层分析

**骨架（机制与系统）：**

Stardew 的骨架由三条互相咬合的核心循环线组成：

```
农耕线：开垦 → 播种 → 浇水 → 收获 → 售卖/加工 → 金钱 → 购买种子/升级工具 → 回到农耕
采矿战斗线：探索矿洞 → 战斗 → 获得矿石/宝物 → 升级工具/建造设施 → 回到农耕
社交线：送礼物 → 增加好感 → 触发事件 → 解锁新内容 → 回到农耕
```

三条线的交汇点是"农耕"——许多产出最终会回到农场经营或生活节律上。这个结构为玩家在子系统之间移动提供了清晰锚点，但不代表玩家在任何情况下都不会迷路。

**血肉（表现与反馈）：**

公开资料常将 Barone 描述为同时承担像素美术、音乐和文本创作；具体资产数量和完成范围应以原始访谈或项目资料核验。这种"全栈式创作"在工业化游戏生产中可能低效，但在独立项目中有机会形成审美一致性——同时也会受到技能、时间、工具和反馈的限制。像素绘画的朴实温暖、音乐的田园氛围、对话的日常质感可以被用来讨论本书第 0 章强调的"三层内聚"。

**灵魂（叙事与情感）：**

Stardew 的灵魂不只是"振兴一个农场"——那是骨架。它也传达了**怀旧与归属**。你在游戏里不是只追求效率——你在"过日子"。游戏日和季节事件形成稳定节律，村民从陌生人变为朋友，甚至爱人。你离城市越来越远，离小镇越来越近。

这个灵魂不是只通过煽情过场动画传达的——它也通过"你的农场慢慢从荒地变成家"这个机制过程产生。玩家对一株作物产生感情，不是因为剧情要求你爱它，而是因为你持续照料它、看着它从种子成长为收成。

### 2.5 Kill Criteria 总结表

| 步骤 | 实际行为 | Kill Criteria 状态 | 方法论文本 |
|------|---------|-------------------|-----------|
| ① 概念孵化 | 成品与公开叙述呈现出对既有农场模拟作品的借鉴和差异化意图 | **支持性线索** | 竞品问题可以形成机会假设，但需要受众验证 |
| ② 一页纸概要 | “一天”的节律和多条系统线在成品中清晰可见 | **可作为结构假设** | 节律结构可借鉴，不等于不需要范围文档 |
| ③ 原型验证 | 外部测试覆盖、原型轮次和何时成立无法从成品确认 | **证据不完整** | 不用事后成功替代缺失的验证记录 |
| ④ 设计深化 | 成品显示核心系统和内容范围经过长期组织 | **部分可观察** | 无法确认正式文档、冻结时间和未采用方案 |
| ⑤ 垂直切片 | “完整季节”可作为一种可能的代表性样本 | **需要核验** | 仍应检查高复杂度内容、管线和资源估算 |
| ⑥ 生产开发 | 大量内容、表现和系统被持续扩充 | **结果线索** | 不把最终稳定性反推为完全冻结的原因 |
| ⑦ 迭代打磨 | 成品和后续更新显示持续修复与完善 | **结果线索** | 具体效果和因果关系需有测试/版本资料支持 |

### 2.6 方法论启示

**不要复制成功结果的表面形式。** Stardew Valley 不是一个方法论模板——它是一个方法论边界案例。它的结果可能依赖一组难以复制的前提条件（开发者与目标品类的关系、竞品机会、生活与资金安排、创作纪律）。把它简化成“一个人长期开发也能成功”的励志模板，会误导独立开发者。

**Scope 控制不等于永久冻结新系统。** 这个案例可以启发我们先稳定核心支柱、再围绕它填充内容；但具体哪些系统何时加入、哪些被舍弃，仍需项目记录确认。生产中若有新证据改变优先级，应通过影响评估和受控回流处理，而不是把“冻结”当作不可修改的规则。

**骨架-血肉-灵魂三层的内聚性可能是单人开发的优势之一。** 当设计、美术、音乐、对话由同一创作者主导时，审美方向更容易保持一致；但这不是自动达成，也会受技能、时间、工具和反馈限制。团队可以通过共同支柱、规范和评审维护一致性。

**Burnout 是 Solo 开发必须显式管理的项目风险。** Barone 曾在采访中描述孤独、自我怀疑和经济焦虑；具体经历应以原始访谈核验。本书方法论没有规定统一的心理健康阈值，但你应记录自己的持续疲劳、恐惧、睡眠和工作能力变化，并在风险持续或恶化时暂停、调整范围或寻求支持。

## 案例3：Celeste — Game Jam 原型到完整产品的路径

> **核心方法论关键词：** Toy First、Game Jam 约束、FTUE 打磨、难度曲线设计、叙事即机制、渐进式复杂度递进

### 3.1 背景：四天 Game Jam 种下的种子

公开资料显示，Matt Thorson（Maddy Thorson）和 Noel Berry 曾在 Game Jam 中制作平台跳跃原型，之后将其扩展为《Celeste》。原型阶段的具体时长、测试样本和每个机制的形成过程应以开发记录核验。

这个 Jam 版本被公开游玩并获得社区反馈。Thorson 和 Berry 因此有了继续探索该核心交互的理由；社区反应是传播和兴趣信号，不等于完整产品的玩法、规模或商业成功已被验证。

他们随后将这个原型扩展为完整游戏并于 2018 年发售，取得了显著的口碑和商业表现。具体工期、评分、价格和销量需要注明来源与统计口径，不能单独作为流程因果证据。

Celeste 可以作为从 Game Jam 原型走向完整产品的启发式案例，但公开资料不能证明它逐步采用了本书流程，也不能说明每个阶段都顺利或“完美”映射。

### 3.2 七步流程映射

| 步骤 | Celeste 的实际行为 | 方法论对标 |
|------|-------------------|-----------|
| **① 概念孵化** | Game Jam 的主题是"登一座山"。Thorson 选择了纯平台跳跃类型——不依赖道具、技能树或数值成长，主要依靠"操作精进"。创意来源是混合的：游戏域内回收（《超级肉肉哥》的硬核平台跳跃） + 情绪目标先行（"攀登的挫败是成长的一部分"）。 | 短期 Jam 约束有助于压缩决策空间，但不保证每个项目都能在约束内验证核心价值；其作用仍取决于目标、团队和可交付范围。 |
| **② 一页纸概要** | Jam 版本集中表达了 `进入屏幕 → 观察 → 尝试 → 失败/重生 → 再尝试 → 通过` 这一核心体验。Design Pillars 在 Jam 阶段可能是隐式的；从最终成品回溯，可以提出“攀登的挫败与成长、精准操作、心理旅程”等候选支柱，但不能把回溯结果当作当时的文档。 | Game Jam 的约束有助于聚焦，但并不自动等同于一页纸，也不保证没有超出单屏交互核心的内容。 |
| **③ 原型验证** | Jam 版本提供了低成本核心交互样本，公开反馈显示有人愿意继续接触；具体的玩家行为、样本和测试设计需要核验。 | 可作为“快速原型 + 外部反馈”的启发式案例，但不能把传播量直接等同于持续好玩。 |
| **④ 设计深化** | Jam 后进入正式预生产，逐步形成章节结构、难度曲线、挑战变体和叙事整合。公开成品可以支持这些结构的存在，但不能仅由成品确认当时的Scope Budget、单屏单位成本或具体规划顺序。 | 可作为从探索性原型转向有意识规划的启发式案例；若要下更强的流程结论，需要开发记录支持。 |
| **⑤ 垂直切片** | 线性关卡制游戏需要验证关卡、表现和管线协同；具体是否按“第一章/第二章”作为正式 VS 样本，需要开发资料确认。 | 可讨论内容驱动项目的 VS 取样，但不应把最终成品回溯成已证实的产能测试。 |
| **⑥ 生产开发** | 成品呈现出稳定的操作支柱、章节主题和大量内容变体。哪些机制在何时冻结、模板如何测产能，不能仅由最终版本确认。 | 可讨论“稳定支柱 + 内容变体”的设计策略，不等于证明完全冻结或固定模板导致成功。 |
| **⑦ 迭代打磨** | 成品将关卡教学、难度调节、辅助模式和叙事表达结合起来。具体迭代轮次和每项决策的因果关系需要开发资料。 | 可作为“多层体验协同”的案例，不应推出单一 FTUE 原则适用于所有游戏。 |

### 3.3 关键设计决策：难度作为叙事，而非惩罚

Celeste 展示了**高难度不一定只能被设计成惩罚——它也可以参与叙事表达**。

在《Celeste》中，玩家可能反复死亡；而每次死亡后：
- 你**很快重生**在本屏开头——挫败还未积累到无法承受，就能进入新一轮尝试
- 没有生命数限制、没有游戏结束画面、没有"返回标题"
- 死亡动画短暂、安静——角色缩成一团然后重新出现，没有惨叫声，没有血腥
- 关卡设计将死亡变成"实验"而非"失败"——每一个屏幕都是一个微型谜题，死亡告诉你"刚才的路线不对，试试另一种"

这种低等待、低惩罚的失败反馈可能降低重复尝试的心理成本，但不能简单归结为“成瘾机制”，也不保证在其他项目中产生相同效果。Celeste 在此基础上加了一层叙事深度——Madeline 攀登山峰的过程，就是她与自己的焦虑、自我否定、和完美主义斗争的过程。玩家在游戏里反复死亡、反复尝试的过程，与 Madeline 在剧情中"反复跌倒、反复爬起"的过程形成了可讨论的同构关系。

> **骨架-血肉-灵魂三层在此合为一体：** 骨架（Dash + 攀爬 + 即刻重生）→ 血肉（像素拉伸动画 + 安静重生 + 柔和色调）→ 灵魂（焦虑与自我接受）。三层不是三个独立的"部门"——它们是同一种设计意图的三种表达方式。

### 3.4 辅助模式（Assist Mode）：一项有争议但可解释的设计选择

Celeste 在发售时内置了辅助模式——玩家可以调整游戏速度、获得无限 Dash、或直接无敌。这在平台跳跃社区中是一个高度争议的决定。"硬核游戏还加辅助模式？"——但 Thorson 的回应展示了优秀设计师的思维：

> 辅助模式不是降低难度——是让更多玩家能够体验 Madeline 的故事。如果你需要辅助模式来通关，你体验到的故事和不需要辅助模式的人体验到的故事，是同一个故事：一个关于坚持、失败、和自我接受的故事。

从方法论角度看，辅助模式可以被解释为对“挫败与成长”这一体验支柱的延伸：它让不同能力和需求的玩家调整挑战，同时保留叙事体验。这是该项目的设计选择，不应被概括为所有高难度游戏都必须采用的正确答案。

### 3.5 Kill Criteria 总结表

| 步骤 | 实际行为 | Kill Criteria 状态 | 方法论文本 |
|------|---------|-------------------|-----------|
| ① 概念孵化 | Game Jam 为核心交互提供了极短周期的原型约束 | **支持性线索** | 时间约束有助于收敛，但不保证概念成立 |
| ② 一页纸概要 | Jam 版本集中表达了核心交互；是否等同于一页纸需谨慎 | **可作为表达样本** | 原型可读性仍需通过目标玩家行为判断 |
| ③ 原型验证 | Jam 版本公开后获得社区反馈 | **部分支持** | 社区传播是兴趣/传播信号，不等于长期玩法验证 |
| ④ 设计深化 | 后续扩展包含章节、难度和叙事结构 | **结果可观察** | 不能从最终结构确认当时的预算和规划质量 |
| ⑤ 垂直切片 | 线性关卡项目需要验证代表性关卡和生产管线 | **需要资料核验** | 不把“第一章/第二章”假设成已证实产能样本 |
| ⑥ 生产开发 | 成品呈现稳定操作支柱与章节变体 | **结果线索** | 稳定支柱不等于完全冻结设计 |
| ⑦ 迭代打磨 | 关卡、难度、叙事和辅助模式共同形成最终体验 | **结果线索** | 需要版本记录和测试资料支持因果判断 |

### 3.6 方法论启示

**Game Jam 可以把低成本原型和早期反馈前置。** 但从 Jam 到完整产品之间仍有大量规模、受众、管线、内容和商业风险；Jam 反馈应被当作支持性线索，而不是在任何时间预算下都“划算”的保证。公开传播、点赞或通关视频可以帮助判断兴趣和可读性，但仍需和目标玩家测试交叉验证。

**核心机制可以做到“少而深”。** 《Celeste》提供了一个通过空间、节奏和环境交互扩展少数操作的案例；但机制数量、关卡数量和评分之间不存在可直接套用的公式。深度来自规则与内容、反馈、目标和玩家学习之间的交互。

**难度是设计，不只是参数。** 《Celeste》的难度主要通过空间布局、输入窗口、恢复时机和失败成本构造，提供了可理解挑战的案例；不同项目也可以通过数值、信息、资源、节奏或对手行为塑造难度，最终仍需测试公平性和情绪效果。

## 案例4：失败案例 — 当 Kill Criteria 被忽视

> **核心方法论关键词：** Kill Criteria 的现实代价、Scope Creep、原型拖延、市场信号忽视、沉没成本陷阱

### 4.1 背景：公开资料中的失败案例（事实与推断分开）

**Towns（2012）** 常被用作 Steam Early Access 早期的失败案例。公开资料通常将其描述为一款受 Dwarf Fortress 等作品影响的城镇建设游戏，但开发团队、预购、收入、玩家规模和停止开发过程的具体信息需要以当时的公告、采访和平台资料核验。

初期曾出现预购、平台曝光和玩家兴趣等积极信号；这些最多说明愿景或传播在特定渠道获得了反应，不能直接推出核心循环、生产能力或项目可持续性已经验证。

之后项目停止开发并留下未完成体验，具体时间线和原因应以开发者公开声明为准。这里把它作为“产品承诺、范围和生产能力没有对齐”的分析案例，而不是把单一原因当作已证实结论。

用本书方法论回溯分析，可以提出多个可能的风险假设：愿景与可交付范围不一致、原型与商品承诺混淆、生产能力未被验证、变更控制不足等。但公开资料不足以证明每个风险何时出现、是否被团队识别或哪一个直接导致失败；回溯分析不能替代当时的项目记录。

### 4.2 七步流程回溯：Kill Criteria 在哪里被错过

#### Step 1（概念孵化）：✅ 通过，但忽略了关键警告信号

**市场假设：** "喜欢 Dwarf Fortress 式深度但被其学习曲线劝退的玩家，会购买一款有图形的简化版城镇建设游戏。"

这个假设在特定渠道获得了兴趣信号，但兴趣、预购和实际长期游玩回答的是不同问题，不能把收入直接当作品类需求或玩法成立的验证。

**但被忽略的警告信号：** "简化 Dwarf Fortress"这个定位意味着——你需要同时做到两件事：足够深度以保留 Dwarf Fortress 粉丝，足够简单以吸引非 Dwarf Fortress 粉丝。这两个目标在同一个产品中可能互斥。Kill Criteria 第 3 条（竞品差异化）在这个案例中被"模糊地通过"了——"有图形的 Dwarf Fortress"听起来差异化清晰，但它没有回答"简单 vs 深度"这对核心矛盾。

#### Step 2（一页纸概要）：⚠️ 模糊通过，Scope 未收敛

Towns 的一页纸（如果存在的话）没有完成 Scope 收敛。"城镇建设模拟"这个品类天然容易 scope 膨胀——你可以加农业、工业、军事、外交、地城、天气、疾病、经济循环……每一个子系统都能找到"为什么需要它"的理由。SMP 工作室最终加入了英雄系统（让玩家控制一个英雄探索地城）、装备系统、战斗系统、贸易系统——每一个单独看都合理，但没有任何一个系统被一个清晰的 Pillar 做过减法决策。

**按本书框架，这里应当审查 Scope 是否可控。** “城镇建设 + 地城探索 + 英雄养成”需要分别估算内容、系统依赖和高风险样本；是否超出团队能力，必须由当时的资源和记录判断，不能仅凭最终失败结果倒推。

#### Step 3（原型验证）：⚠️ 需要区分原型、试玩和商品承诺

按本书框架，一个重要风险是把尚未验证的内部原型直接包装成商品承诺；Towns 的公开版本是否经历了哪些内部验证，需要以项目资料核实。

如果采用本书的原型方法，可以先用低成本版本和匹配目标的玩家测试“建造城镇→吸引居民→满足需求→扩大城镇”在目标会话中的理解、继续意愿和中期目标，再决定是否公开售卖。这样的测试可能暴露核心循环、范围或可读性问题，但不能预先假设结果。

如果在核心循环、范围和更新能力尚未被充分验证前就收取玩家的钱，版本性质会从内部实验变成带有交付义务的 Early Access 或产品承诺，回流成本和沟通要求都会上升。早期收入仍然只是愿景/传播/购买意愿信号，可能强化沉没成本，但不能据此断言具体团队的动机或唯一因果。

> **本书方法论的核心警告（第 5 章）：** 内部原型、免费试玩和 Early Access 商品承担的承诺不同。把未完成版本公开或售卖前，应明确版本状态、可交付范围、更新能力和回流成本。

#### Step 4（设计深化）：公开资料不足以确认

如果核心循环、范围和资源估算没有在公开版本前充分验证，Step 4 的规划基础就可能不足。是否做过 Scope Budget、如何估算“城镇建设 + 地城探索 + 英雄养成”的总工时，必须查项目记录；不能从项目失败倒推“肯定没有做过”。

#### Step 5（垂直切片）：公开资料不足以确认

可以提出的风险假设是：如果没有覆盖代表性系统、复杂度和最终品质的样本，生产管线和整合成本可能被低估。Towns 是否确实没有这样的样本，需要一手开发资料；最终未完成不能单独证明垂直切片缺失是原因。

#### Step 6（生产开发）：可能存在范围和变更控制风险

如果公开资料确实显示新功能持续加入而核心内容未收敛，那么可以将其解释为范围扩张和变更控制风险；但新增功能、修复和玩家承诺的具体顺序、规模及影响需要资料支持，不能把“设计永动”当作唯一原因。

#### Step 7（迭代打磨）：可能未形成稳定的发布候选版本

如果一个项目在发布承诺期间仍不断扩展范围、而核心体验和稳定性没有形成可交付基线，就会同时承担设计、技术、沟通和社区风险。正确诊断需要版本、缺陷和决策记录；不能只用最终停止开发证明“加系统”必然是原因。

### 4.3 警告信号时间线

如果把本书的 Kill Criteria 作为分析框架，以下是**当时可能需要检查的风险**；这不是对团队当时实际决策的还原：

| 时间节点 | 关键事件 | 可观测的 Kill Criteria 信号 | 当时应该做的 |
|---------|---------|--------------------------|------------|
| **概念形成** | “有图形的 Dwarf Fortress” | 卖点可能同时包含简单与深度的张力 | 用不同目标玩家和低成本原型分别验证价值主张 |
| **出现预购/收入** | 愿景获得购买兴趣 | 收入 ≠ 核心循环、交付能力或长期需求已验证 | 在扩大承诺前补做玩法、范围和资源验证 |
| **公开/售卖早期版本** | 版本进入玩家和社区视野 | 实验自由减少，产品承诺和支持成本增加 | 明确版本状态、范围、路线图、更新能力和回流规则 |
| **新增英雄、战斗等系统** | 玩法范围可能扩大 | 变更是否波及核心、管线和截止日期 | 做影响评估，必要时暂停扩张并回到相应验证步骤 |
| **社区质疑完成度** | 玩家感知到不完整或承诺落差 | 产品信号可能与开发者内部进度不一致 | 分析可交付范围、沟通和稳定性，决定缩减、延期或退出 |
| **停止开发** | 项目进入终止状态 | 需要区分理性止损与之前哪些证据被忽略 | 记录决策依据，形成可复用的复盘假设 |

### 4.4 七步回溯：错误地图

```
步骤     Towns 可观察路径/待核验信息         更稳妥的分析路径
──────  ──────────────────    ──────────────────
① 概念   卖点与受众关系待核验       拆分价值主张并做低成本验证
② 概要   范围和依赖是否收敛待核验   明确内容单元、资源和变更边界
③ 原型   早期版本与商品承诺发生交叠  区分内部实验、试玩和 Early Access
④ 深化   预算、复杂度和交付范围待核验 以区间和风险样本估算
⑤ 垂切   代表性品质和管线待核验       补充能覆盖高风险内容的样本
⑥ 生产   可能存在范围/变更风险        以稳定基线和变更评审控制扩张
⑦ 打磨   未形成可交付的稳定基线？      用发布标准和玩家证据决定修复/缩减/退出

公开结果：项目停止开发；具体因果链仍需资料支持
```

### 4.5 Kill Criteria 总结表（可观察信号与分析假设）

| 步骤 | 实际行为 | Kill Criteria 应该触发 | 被忽略的信号 | 代价 |
|------|---------|----------------------|------------|------|
| ① 概念孵化 | 卖点和目标受众的关系需要核验 | 简单与深度的价值张力 | 购买兴趣可能掩盖玩法问题 | 取决于承诺规模 |
| ② 一页纸概要 | 范围、依赖和优先级需要核验 | 内容和资源无法解释 | 每个系统都被认为“有道理” | 取决于影响 |
| ③ 原型验证 | 早期版本与商品承诺发生交叠 | 核心体验、交付能力或更新能力证据不足 | 收入被误读为完整产品验证 | 高，因承诺不可逆性上升 |
| ④ 设计深化 | Scope Budget 和内容单元需要核验 | 无法解释总成本与主要未知项 | 用感觉替代区间估算 | 取决于范围 |
| ⑤ 垂直切片 | 代表性品质、管线和复杂度样本需要核验 | 生产能力未被覆盖 | 粗糙可行被误认为接近完成 | 取决于返工成本 |
| ⑥ 生产开发 | 可能存在范围/变更控制风险 | 新增和返工波及已生产内容 | 新系统带来的短期新鲜感被误读为改善 | 取决于承诺和依赖 |
| ⑦ 迭代打磨 | 是否形成稳定发布候选版本需要核验 | 核心体验、稳定性或交付范围不收敛 | 社区反馈未被纳入可解释的决策 | 取决于剩余风险 |

### 4.6 从失败中提取的警示原则

**原则一：明确原型、试玩和商品版本承担的不同承诺。**

当你收了玩家的钱，公开版本就承担了产品承诺，实验自由、回流成本和沟通要求都会改变。内部原型不必然要“扔掉”，也可以演化为实验分支或试玩版本；关键是明确版本状态、可交付范围、更新能力和退出方案，避免把未验证的承诺包装成确定产品。

**原则二：收入信号与产品信号必须分开解释。**

预购和 Early Access 收入是真实的钱，但主要回答“有人愿意在当时的承诺和渠道条件下购买吗”，不等于核心循环、生产能力或长期需求已经成立。应把收入、试玩行为、玩家反馈和交付能力作为不同证据线交叉解释。

**原则三：Core Loop 不成立的游戏，"加系统"就是"挖坟"。**

当 Core Loop 的证据不足时，直接叠加系统可能掩盖问题并扩大范围；但也可能存在通过系统交互改变价值的合理设计。正确做法是回到 Step 3，把“修改现有规则”和“加入新系统”作为不同假设分别做低成本实验，记录玩家行为、后果、成本和下一步，而不是用短期新鲜感替代核心体验验证。

**原则四：没有 Scope Budget 的生产开发 = 盲飞。**

Scope Budget 不是为了精确预测，而是为了在成本仍是纸面数字时显式列出内容单元、依赖、复杂度、区间和高风险样本，从而知道哪些东西需要删减、拆分、延后或补验证。不能用一个固定倍数概括某个项目的资源缺口。

### 4.7 方法论启示

本附录的四个案例放在一起，形成了一组完整的"参考系"：

- **Balatro** 可作为“系统组合与内容媒介”的启发式案例，但公开资料不足以证明其完整遵循本书流程
- **Stardew Valley** 可作为“长期独立开发、稳定核心支柱与成功结果并存”的边界案例，不能用成功倒推省略验证是正确的
- **Celeste** 可作为“Game Jam 原型、内容驱动关卡和辅助模式”的启发式案例，Jam 反馈不等于完整产品验证
- **Towns** 可作为“公开承诺、范围和生产能力可能错位”的失败案例，具体因果链需要事实资料支持

四个案例共同说明：**本书方法论不是成功公式，也不是自动的失败预防机制，而是一套帮助团队提出假设、收集证据、暴露风险和做出取舍的工具。**

遵循方法论不会自动成功；它的价值在于让团队在关键节点停下来检查信号，并明确哪些结论是事实、推断还是未知，从而降低可预防的风险，而不是承诺避免所有失败。

## 附录E小结：四项核心教训

1. **加法创新可以降低部分不确定性，但不能替代验证。** 把已知元素组合起来可以复用规则和受众认知；组合后的体验、实现、内容成本和市场仍需独立验证。

2. **Solo 开发的可行性取决于多项条件：**目标玩家理解、领域经验、竞品知识、时间/资金储备、技能覆盖、测试渠道和可持续节奏。个人是目标玩家或熟悉竞品只能减少部分未知，不能免除验证。

3. **Game Jam 是低成本的早期实验机会。** 它可以帮助团队在短周期内暴露核心交互和传播风险，但 Jam 反馈不等于完整产品验证，不能用固定倍数比较成本收益。

4. **在核心体验、范围和交付能力尚未明确前，谨慎收钱和作出不可逆承诺。** 如果选择试玩、众筹或 Early Access，应清楚说明版本状态、可交付范围、更新能力、退款/支持责任和回流成本；收入信号不能替代玩法验证。
