# 第14章：UI/UX与信息设计

> **本章在全书中的位置：** 第13章解决了“玩家的空间体验如何设计”（关卡），本章转向“玩家如何感知和操控游戏信息”。UI/UX 是连接游戏系统与玩家认知的重要桥梁——这座桥如果断了，再好的机制也难以被玩家体验到。

---

## 本章解决什么问题

独立开发者最常见的 UI/UX 错误有三个：

1. **把游戏 UI 当成 App UI 来做。** 直接套用移动端设计规范（Material Design / Human Interface Guidelines），结果界面又"干净"又"专业"，但彻底破坏了游戏世界的沉浸感。
2. **HUD 信息失控。** 要么屏幕上堆满数字和图标（"玩家需要知道一切"），要么什么都没有（"要让画面干净"），两个极端都毁了体验。
3. **前期体验失去目标感。** 游戏开始后的早期阶段会影响玩家是否愿意继续，但具体时间取决于类型、平台、价格、玩家经验和体验承诺。如果 FTUE（首次用户体验）是文字墙、强制教程或信息缺失，测试和评价会暴露问题。

> **编程类比：** UI/UX 设计 ≈ API 设计。好的 API 让调用者不需要读源码就能用对；坏的 API 让调用者反复查文档、踩坑、最后放弃。你的 UI 就是玩家调用游戏系统的 API——它的易用性决定了玩家是流畅地体验到你的设计，还是被信息噪音淹没后关闭游戏。

## 14.1 游戏 UI 的特殊性

> **这一节解决什么问题：** 为什么不能直接用 App UI 的方法做游戏界面？游戏 UI 面临的独特约束是什么？信息水平（谁该知道什么）如何影响界面设计？

### 14.1.1 游戏 UI ≠ App UI：三个根本矛盾

App UI 的终极目标是**效率**——用户用最少的时间完成一个任务（下单、查天气、发消息）。App 设计师追求的是"用户不需要思考"。

游戏 UI 的终极目标是**有意义的体验**——包括困惑（迷雾中的探索）、紧张（残血时的压迫）、惊喜（隐藏区域的发现）。游戏设计师需要的是"在正确的时刻给玩家正确的信息，同时保留发现和掌握的快感"。

这就产生了 App UI 设计中不存在的三个矛盾：

| 矛盾 | App UI 的解法 | 游戏 UI 的要求 |
|------|-------------|-------------|
| **信息透明度** | 越多越好，一眼看穿 | 按需提供：有些信息就该让玩家不知道（如怪物血量、隐藏门） |
| **操作效率** | 最少点击到达目标 | 操作本身可以是乐趣（如手动瞄准 vs 自动锁敌） |
| **风格一致性** | 遵循平台设计规范 | 风格必须服务于世界构建（科幻游戏的信息面板不该像 iOS 设置页） |

*Practical Game Design* 将游戏信息按优先级分为三层，这比任何"少即是多"的口号都要具体：

| 信息层级 | 定义 | 显示策略 | 示例 |
|----------|------|----------|------|
| **关键信息** | 离了它玩家难以正常游玩 | 通常持续可见，或在玩家需要时容易取得 | 生命值、当前目标标记 |
| **支持信息** | 频繁需要但不要求即时反应 | 在固定位置但非视觉焦点，或一键呼出 | 小地图、弹药数、技能冷却 |
| **情境信息** | 只在特定情境下需要 | 隐藏在菜单后或情境触发时弹出 | 完整地图、背包、任务日志 |

**决策原则：不要仅因为“玩家可能需要”就把信息放上 HUD。** 每一条 HUD 元素都在消耗注意力——这是玩家最稀缺的资源。增加一条 HUD 信息前，检查它是否服务于当前目标、是否需要持续可见，以及是否有更合适的呈现方式。

### 14.1.2 信息水平：公共信息 vs 私有信息

*Rules of Play* 第16-17章从信息理论的角度切入游戏设计，其核心洞见是：**信息本身就是一种游戏资源。** 信息论的基本概念——信息 = 不确定性的消除，噪音 = 干扰信号传递的东西——直接映射到游戏设计中。

对 UI 设计而言，最关键的信息论概念是区分**信息水平**：

- **完美信息（Perfect Information）：** 所有玩家都知道完整的游戏状态。如国际象棋——棋盘对所有玩家完全透明。这类游戏的 UI 挑战是"如何让复杂状态一目了然"。
- **不完美信息（Imperfect Information）：** 玩家只知道部分游戏状态。如《星际争霸》的战争迷雾——你不知道视野外发生了什么。这类游戏的 UI 挑战是"如何让玩家理解自己不知道什么"。

从中可以引出对 UI 设计影响更深的一对概念：

- **公共信息（Public Information）：** 所有玩家都能看到的信息（游戏公告、公开比分、世界地图）。公共信息的 UI 应该一致化——同一个信息在所有玩家屏幕上呈现方式相同。
- **私有信息（Private Information）：** 只有该玩家自己能看到的（手牌、背包、技能树）。私有信息的 UI 可以个性化——玩家自己的意图和计划不需要"翻译"给别人看。

**为什么这俩概念对独立游戏设计重要：** 很多设计困惑本质上是混淆了这两类信息。例如，多人在线游戏中把某个玩家的私有信息（如隐藏任务进度）意外暴露给所有人 → 剧透体验。反过来，把本应公开的信息（如队友血量）藏在个人界面里 → 合作混乱。

**实践案例：** 《Among Us》的信息设计可作为信息不对称的案例。谁还活着、任务进度和内鬼身份分别承担不同的信息权限；这种信息边界不只是 UI 问题，也会直接影响玩法。

### 14.1.3 信息设计的不对称原则

从信息水平出发，可以推导出一条设计铁律：

> **玩家应该拥有的信息量 = 他在游戏世界中的角色理应知道的信息量。**

这条铁律在两种偏离方向上都会出错：

- **信息过剩：** 给玩家看怪物血量、隐藏门位置、未来剧情走向——玩家获得了"上帝视角"，但失去了探索和发现的意义。
- **信息不足：** 不给玩家看队友血量、任务目标变化、自己中了什么 debuff——玩家觉得游戏"不尊重他的时间"，在黑暗中乱撞。

*通关！* 第8关的"清爽屏幕策略"给出了实操方向：HUD 不活动时自动渐隐/滑出；能借助声音/动画/特效传达的信息就不要放 UI 元素；暂时性 HUD——需要时弹出，不需要时滑出。这些策略的共同目标是在信息透明度这个光谱上找到**动态平衡**，而不是一个静态位置。

## 14.2 HUD 设计的科学原则

> **这一节解决什么问题：** HUD 上到底该放什么？怎么放？本章给出一个可操作的决策框架，而不是空泛的"放最重要的信息"。

### 14.2.1 HUD 元素决策矩阵

每一个可能出现在 HUD 上的信息，都需要通过以下四个维度检验。任何一个维度不通过，就把它移出 HUD。

| 检验维度 | 问题 | 通过标准 | 不通过时放哪里 |
|----------|------|----------|---------------|
| **反应时间** | 玩家需要在很短的操作窗口内对此信息做出反应吗？ | 是 → 考虑 HUD | 暂停菜单 / 状态页面 |
| **持续可见性** | 玩家需要在注意力不离开游戏画面的前提下持续监控此信息吗？ | 是 → 考虑 HUD | 一键呼出界面 |
| **动作关联** | 此信息是否与当前正在进行的核心动作直接关联？ | 是 → 考虑 HUD | 情境提示弹出 |
| **频率** | 玩家在目标会话中是否频繁需要查看此信息？ | 是 → 考虑 HUD | 状态页面 |

使用示例：以一款 Roguelike 动作游戏为例——

| 信息项 | 反应时间 | 持续可见 | 动作关联 | 频率 | 结论 |
|--------|:--:|:--:|:--:|:--:|------|
| 生命值 | ✅ | ✅ | ✅ | ✅ | HUD |
| 当前武器 | ✅ | ✅ | ✅ | ✅ | HUD |
| 金币数量 | ❌ | ❌ | ❌ | ✅ | 一键呼出（Tab） |
| 完整地图 | ❌ | ❌ | ❌ | ✅ | 暂停菜单 |
| Buff 剩余时间 | ✅ | ✅ | ✅ | ✅ | HUD（小图标+计时） |
| 技能冷却 | ✅ | ✅ | ✅ | ✅ | HUD |
| 经验值进度 | ❌ | ❌ | ❌ | ❌ | 状态页面 |
| Boss 血量 | ✅ | ✅ | ✅ | ✅ | HUD（Boss 战专属） |

注意最后一行：Boss 血条不是永远在 HUD 上的——它是 Boss 战时才出现的**临时 HUD 元素**。这是一个容易被忽视的设计技巧：**HUD 不需要是静态的，它可以根据游戏状态动态地显示或隐藏元素。**

### 14.2.2 HUD 的呈现形式：从血条到环境

*通关！* 第8关列举了血槽的多种形态，本质上是在讨论一个更深层的问题：**信息的媒介是什么？**

| 媒介类型 | 说明 | 优势 | 劣势 | 适用场景 |
|----------|------|------|------|----------|
| **传统 HUD 元素** | 矩形血条、数字、图标叠加在屏幕上 | 精确、直观、开发成本低 | 破坏沉浸感、占用屏幕空间 | 动作游戏、RPG |
| **Diegetic 界面** | 信息嵌入游戏世界（如《死亡空间》主角脊柱上的生命槽） | 极致沉浸、世界构建的一部分 | 精确度低、开发成本高、难以复用 | 恐怖游戏、沉浸式模拟 |
| **Meta 界面** | 屏幕效果（如暗红边框=低血量、屏幕抖动=受击） | 不占用 UI 空间、直觉性强 | 无法精确传达数值、对色盲不友好 | 所有类型都可用作补充 |
| **Spatial 界面** | 3D 空间中的标记（物品发光、敌人头上的感叹号） | 信息与空间位置直接关联 | 需要 3D 空间、可见性问题 | 3D 动作、开放世界 |

**实践案例：《塞尔达传说：旷野之息》** 的 HUD 使用了混合策略：生命值用心形（传统 HUD），但声音提示（心跳加速）、屏幕边缘红色渐变（Meta）也同时传达同一信息。这种**冗余设计**不是浪费——不同玩家在不同状态下依赖不同感官通道。被围攻时你不可能去看左上角的心形，但你能感受到屏幕变红和手柄振动。

**实践案例：《死亡空间》** 是所有 3D 沉浸式游戏都该研究的反面教材。它的 diegetic UI（脊柱血条 + 全息投影背包 + 枪支弹药数直接显示在武器模型上）证明了：**当信息嵌入世界时，玩家不需要"离开游戏世界去查看状态"。** 这对恐怖游戏和沉浸式模拟游戏尤其关键——每切换一次菜单，都是在提醒玩家"这是一款游戏"，恐惧感就会消退一层。

### 14.2.3 HUD 与暂停菜单的分工边界

一个常见的决策困扰：某个功能（如技能升级、地图查看、物品合成）该放在 HUD、一键呼出界面，还是暂停菜单？

| 界面层级 | 定义 | 何时使用 | 示例 |
|----------|------|----------|------|
| **HUD** | 始终或条件性显示在游戏画面上 | 需要即时反应或持续监控 | 血量、弹药、Buff 计时 |
| **一键呼出** | 按键/触控后叠加在游戏画面上（游戏不暂停） | 频繁需要但可中断查看 | 快捷背包、小地图放大、技能轮盘 |
| **暂停菜单** | 按暂停键后全屏覆盖（游戏暂停或时间大幅减慢） | 深度操作、复杂决策、配置修改 | 技能树、完整地图、设置、存档管理 |

**决策原则：如果玩家需要一边看着游戏画面一边做决定，就不能放暂停菜单。** 例如即时切换武器应该用一键呼出的武器轮盘（时间在流逝），而分配属性点应该进暂停菜单（没有画面需求，且决策需要冷静思考）。

## 14.3 Shell 导航设计

> **这一节解决什么问题：** 从"玩家启动游戏"到"玩家进入核心玩法"再到"玩家暂停退出"，中间的每一次跳转都在消耗耐心。如何设计一条认知负荷最低的导航路径？

### 14.3.1 Shell 导航图模板

"Shell"指的是包裹在核心玩法外面的所有菜单和界面——主菜单、设置、存档、暂停、商店、图鉴。一个独立游戏的完整 Shell 导航图通常如下：

```
┌─────────────────────────────────────────────────┐
│                   启动画面                       │
│         （跳过动画/加载必要资源）                 │
└─────────────────┬───────────────────────────────┘
                  │
    ┌─────────────▼─────────────┐
    │         主菜单            │
    │  开始   读档   设置   退出 │
    └───────────┬───────────────┘
                │
    ┌───────────▼───────────┐
    │      选择存档位        │
    │  槽1  槽2  槽3  新游戏  │
    └───────────┬───────────┘
                │
    ┌───────────▼───────────────────────────┐
    │              核心玩法层                │
    │                                       │
    │  ┌─ HUD ─┐         ┌─ 一键呼出 ─┐     │
    │  │ 血量   │         │ 快捷背包   │     │
    │  │ 弹药   │  ←──→  │ 技能轮盘   │     │
    │  │ 小地图 │         │ 合成台    │     │
    │  └────────┘         └───────────┘     │
    │       │                               │
    │  ┌────▼────────┐                      │
    │  │  暂停菜单     │                     │
    │  │ 属性/技能树  │                     │
    │  │ 完整地图    │                     │
    │  │ 背包/装备   │                     │
    │  │ 图鉴/日志   │                     │
    │  │ 设置/存档   │                     │
    │  │ 回到主菜单   │                     │
    │  └─────────────┘                     │
    └───────────────────────────────────────┘
```

### 14.3.2 减少认知负荷的五条规则

*Rules of Play* 的信息论框架指出：**冗余（重复信息）帮助克服噪音（干扰），但过多冗余导致可预测和无聊。** 在 Shell 导航设计中，这个理论翻译成以下五条实操规则：

**规则1：控制导航深度。**
从主菜单到常用功能不应有不必要的层级；深度功能可以通过标签、搜索、历史位置或快捷入口降低负担。“3 层”可以作为某些项目的起始目标，但不是所有游戏、平台和复杂度都适用的硬门槛。

**规则2：暂停菜单是"家"，玩家应该随时知道怎么"回家"。**
无论玩家在暂停菜单的哪个子页面，按同一个键（通常是 ESC/B/返回）应该回到上一级，最终回到暂停菜单主页面，再按一次回到游戏。如果玩家在某个深层菜单里按 ESC 直接被弹回了游戏→他失去了上下文，下次会犹豫要不要再打开这个菜单。

**规则3：每屏突出主要动作。**
主菜单页面应突出玩家当前最可能的目标；按钮数量、信息密度和通知徽章需按屏幕尺寸、玩家任务和游戏类型测试，不要用“超过 5 个”自动判定失败。

**规则4：保持"返回"和"退出"的一致性。**
同一个键位在全游戏中的所有 Shell 页面中行为一致。不要在某页面 ESC 是返回、另一页面 ESC 是退出游戏。玩家对 UI 的操作模式是一种**肌肉记忆**——打破一致性等于在认知肌肉记忆上刻一刀。

**规则5：不可避免的等待需要反馈。**
只要玩家无法判断加载是否仍在进行，就应提供进度、动画或状态反馈；具体何时显示进度条取决于平台和等待时长。提示内容应可跳过、简短且不会打断玩家当前目标。

### 14.3.3 导航一致性的自检方法

在纸面上画出完整导航图后，做一个简单的自检：

```
- 从"启动游戏"到"进入玩法"，经历了多少屏？____ 屏
  （记录目标和不必要步骤，按项目平台设定起始目标）

- 暂停菜单有多少个子页面？____ 个
  （按玩家任务、频率和信息密度检查是否需要合并或重组）

- 最深的导航路径是多少层？____ 层
  （区分常用路径和深度功能，检查是否存在不必要的层级）

- 有没有"死胡同"页面——除了返回没有别的操作？____
  （如果有，考虑它是否可以融入其他页面）

- 所有返回操作是否始终导向同一个"家"？是 / 否
```

## 14.4 FTUE（首次用户体验）设计

> **这一节解决什么问题：** 游戏开始后的早期阶段，玩家需要逐步形成对操作、目标和体验承诺的理解。如何设计一个让显式教学与发现式学习相互配合的 FTUE？

### 14.4.1 FTUE 的早期体验如何展开

Steam 等平台有自己的退款规则，但平台规则不等于玩家体验规律。玩家是否继续游玩会受到类型、价格、平台、受众、推荐来源和早期体验共同影响，不能压缩成统一的 30-90 秒判断。

项目定义的早期体验窗口里，玩家在做什么？

| 时间窗口 | 玩家在做什么 | 设计目标 |
|----------|------------|----------|
| 早期情境建立 | 画面出现，辨识这是什么样的游戏 | **建立世界感**——画面风格、音乐氛围、空间感 |
| 初次操作 | 尝试输入并观察结果 | **建立操作感**——关键输入有反馈、角色有动作、没有无意义阻塞 |
| 目标形成 | 发现第一个交互，尝试理解"游戏要我做什么" | **建立目标感**——环境、文字或角色共同传达行动方向 |
| 初次结果 | 完成一个与核心承诺相关的交互 | **建立反馈感**——让玩家知道行动产生了什么后果，并愿意继续探索 |

*通关！* 第7关描述的“乱搓手柄法”可以作为动作游戏的一个案例：玩家会通过试按探索输入与反馈。但菜单驱动、慢节奏、推理或信息密集型游戏不一定需要每个按键都触发动作，应确保与核心承诺相关的输入可理解、可反馈。

### 14.4.2 显式教学与发现式学习并用

独立游戏最常见的 FTUE 失误是**教学形式单一**：花了大量心血设计机制，唯恐玩家不理解，于是只用文字墙、强制引导箭头或锁定操作来“教”玩家，或者反过来把所有显式说明都删掉。

问题在于：**只依赖强制教程或只依赖完全发现，都可能与项目目标和玩家画像不匹配。** 被教会的玩家不一定喜欢冗长教程；没被教会的玩家也不一定会把困难归因于自己。

可选方案是**发现式设计（Discovery-Based Design）**，它应与显式说明、渐进式练习和可访问性支持组合使用。以下策略需要按项目测试：

| 策略 | 说明 | 示例 |
|------|------|------|
| **环境教学** | 用环境布局暗示操作（狭窄通道暗示侧身通过，发光平台暗示可踩） | 《超级马里奥》第一屏：砖块在你上方，你不按跳跃就什么都做不了。没有任何文字告诉你"按 A 跳跃"——关卡本身就是教程。 |
| **情境触发** | 在玩家第一次需要某个操作时才提示，而不是提前预讲 | 《塞尔达》的"按 A 打开"提示：只在玩家走到宝箱旁边时才出现，不在开场时罗列所有操作。 |
| **失败即教学** | 让玩家在安全的环境中失败，通过失败理解规则 | 《Celeste》前几屏的平台间隔精确地教会你冲刺距离——掉下去只会回到同一屏开头，没有真正惩罚。 |
| **正面强化** | 玩家做对时给即时、饱和的反馈（不是文字表扬） | 击杀第一个敌人的慢动作镜头 + 音效放大 + 粒子特效，比任何文字说明都有说服力。 |
| **自然递增** | 先给最简单的挑战，成功后再加一层复杂度 | 《传送门》逐步引入传送门机制：先单向 → 再双向 → 再配合物理 → 再配合激光 → 再配合时间。每一步都在前一步的基础上只加一个变量。 |
| **可跳过/可调整** | 为熟悉玩家提供跳过、加速或重看选项，同时保证首次玩家可理解 | 标题画面或设置中提供教程跳过/重播、提示强度和输入辅助选项。 |

**实践案例：《传送门》的 FTUE 是发现式教学的案例。** 开局通过空间和交互逐步建立规则，并在必要处提供提示。它说明环境可以承担教学功能，但不意味着所有项目都应删除文字或强制引导；输入复杂度、语言、平台和玩家经验都需要单独测试。

**实践案例：《Celeste》的 FTUE 同样精巧。** 前几屏的平台间距恰好是冲刺的极限距离——稍微差一点就够不到。掉下去不惩罚（只是回到本屏开头），但跳过去的那一刻，"我懂了"的快感替代了"我被教会了"的被动感。

### 14.4.3 FTUE 设计检查表

以下是进入原型测试之前可以使用的 FTUE 自检：

```
□ 早期情境：画面加载完成后，玩家能理解当前情境或下一步目标，而不是长期停留在无关界面

□ 初次操作：玩家能通过尝试、提示或说明获得与核心承诺相关的可见反馈

□ 早期目标：玩家面前有一个与项目类型相符、可以通过环境、文字或角色理解的行动目标

□ 初次结果：玩家在项目预设的早期节点完成了至少一个有反馈的交互
  （击杀/跳跃/拾取/推动/选择——应与项目的核心承诺相关）

□ 教学形式经过测试：发现、文字、语音、演示、练习和辅助选项的组合能被目标玩家理解

□ 有没有文本墙？（如果有，拆成可读、可跳过或可回看的信息，并验证它是否必要）

□ 有没有强制锁定？（如果有，确认它服务于理解、节奏或叙事，并提供合理的跳过/重试/辅助方式）

□ 有没有跳过、重播或调整教程的方式？（根据目标玩家和平台决定）

□ 早期失败成本是否符合项目目标？玩家能否理解失败原因并方便重试？

□ 玩家能否在项目预设的早期节点用自己的话描述“这个游戏在做什么”？
  （按目标玩家和体验复杂度招募测试者，结合行为、访谈与可访问性反馈判断）
```

## 失败信号

| 信号 | 说明 | 行动 |
|------|------|------|
| **玩家反复打开同一菜单** | 信息架构有问题——玩家找不到想要的东西 | 重组菜单结构，把高频操作提升层级 |
| **玩家在教程后仍不知道核心操作** | 教学信息没有转化为可执行的理解，可能是形式、顺序、输入或可访问性问题 | 观察玩家卡点，调整发现式、显式教学和练习的组合 |
| **HUD 元素被 playtest 中无人提及** | 这些信息是多余的——玩家根本不需要它们 | 从 HUD 移除，如果后续有玩家抱怨再加回来 |
| **玩家频繁跳过加载提示或不阅读** | 信息可能与当前等待、玩家目标或阅读条件不匹配 | 缩短等待、提高信息相关性，或提供可选的回看入口 |
| **FTUE 早期出现无解释的静止或重复尝试** | 玩家可能不知道下一步、输入或失败原因 | 结合录屏和访谈定位引导、反馈、输入或节奏问题 |
| **菜单按钮在不同页面上行为不一致** | 认知负荷激增，玩家要"学"而非"用"你的 UI | 统一导航行为，做一份 Shell 行为规范文档 |
| **玩家通关后不知道某些系统存在** | 该系统的入口藏太深或触发条件不明确 | 用情境触发而非菜单深度来引导发现 |
| **玩家反馈"看不懂"或"不知道干什么"** | FTUE 没有在预期节点建立足够的目标感或操作理解 | 回到 14.4 检查教学形式、信息层级、输入和可访问性 |

## 骨架-血肉-灵魂自查

| 层 | 自查问题 | 通过标准 |
|----|---------|---------|
| **骨架（机制与规则）** | HUD 上的每个元素是否通过了"删除后游戏还能玩吗"的测试？ | 每个元素都有可解释的实时价值，信息密度符合目标平台和情境 |
| **骨架（机制与规则）** | Shell 导航是否清晰——从主菜单到游戏内暂停的完整路径是否可达？ | 常用功能路径短且可预测，深度功能有搜索/标签/返回等支持 |
| **骨架（机制与规则）** | 信息架构是否区分了公共信息（HUD）和私有信息（暂停菜单）？ | 信息的可见范围符合多人规则、角色权限和玩家预期 |
| **血肉（表现与动态）** | 关键信息是否至少通过两种感官通道传达（如颜色+形状、声音+动画）？ | 色盲模式下仍然能区分所有关键信息 |
| **血肉（表现与动态）** | UI 的视觉风格是否与游戏的整体美术方向一致？ | UI 像"长在游戏世界里"而不是"贴在屏幕上的面板" |
| **血肉（表现与动态）** | 交互反馈是否足够及时、清晰、一致？ | 测试者能知道输入是否被接受，不会因无反馈重复点击 |
| **灵魂（情感与意义）** | FTUE 是否在项目预设的早期节点传达了核心情感承诺？ | 新玩家能用自己的话说明游戏在做什么、为何值得继续 |
| **灵魂（情感与意义）** | UI 的"存在感"是否与游戏类型匹配？ | 沉浸式游戏：UI 退到背景中；策略游戏：UI 是核心工具 |
| **灵魂（情感与意义）** | 玩家是否在"使用 UI"而不是"对抗 UI"？ | 测试者不会说出"这个菜单好烦"或"我找不到 X" |
